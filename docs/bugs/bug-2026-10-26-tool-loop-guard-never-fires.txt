日期：2026-10-26

问题现象：
agent 的工具循环防护形同虚设。三处叠加：① 同结果熔断阈值 MAX_SAME_TOOL_RESULT_CALLS=53，
在 maxSteps=20（单 agent）/8（worker）下物理上不可能触发，等于没有快速熔断；
② 指纹只含「工具名+结果」不含参数，同参数但结果略有不同的重复调用永远检不出来；
③ 全部防护只写在 BaseAgent.runStream()，图编排 worker 走的同步 run() 一层循环检测都没有，
  而 token 计量已证明 worker 占整轮成本约 95%。

影响范围：
两条 agent 执行路径。单 agent 流式路径只剩 maxSteps/5 分钟时限兜底；图 worker 只剩
WORKER_MAX_STEPS=8 兜底，参数级紧循环（如反复用同一 query 调 searchWeb）会烧满步数，
直接对应实测「同一 run 12 次 searchWeb」与 worker 轮数 6→16 的成本方差。

原因：
防护逻辑早期一次性写死在 runStream 内联代码里：阈值取了过大的安全值从未校准；
指纹维度缺参数；后来新增同步 run() 路径（WorkersNode 复用）时没有把防护一起带过去。

解决方式：
新增 agent/core/ToolLoopGuard（纯确定性 Java，不经模型判断），run 与 runStream 共用：
- 参数指纹（工具名+参数）：同一工具相同参数的非生产性调用累计 3 次（MAX_SAME_ARGS_CALLS）→ 停机；
- 结果指纹（工具名+归一化结果）：连续 5 轮（MAX_NO_PROGRESS_ROUNDS）无「未见过的有效结果」→ 停机；
- 有新有效结果的轮次视为有进展：豁免参数循环判定并清零无进展计数，
  保护「同参数重试后成功」「同参数翻页拿新内容」等正当场景；
- 原 53 阈值与其内联逻辑删除；run() 命中防护时按「任务已按策略终止」收尾并触发 fireOnInterrupted，
  runStream() 命中时走既有 requestStop → 中断摘要（已完成工作列表）路径。

验证结果：
mvn clean test 全量 262 项通过（0 失败 1 跳过）。重写 BaseAgentTerminationTest 4 例
（5 轮无进展改用变参数避免被参数指纹抢先触发；53 次用例改为 3 次同参数熔断），
新增跨步同参数熔断、有进展豁免、同参数重试成功放行、同步 run() 路径熔断 4 例，
新增 ToolLoopGuardTest 4 例。mvn clean package 出包后 launchctl kickstart 重启，/api/health=ok。

后续注意事项：
- 阈值 3/5 是按「同参数重试两次仍失败即放弃」定的；若真实运行出现误杀（日志里搜
  「已按策略终止」「没有获得新的有效结果」对照业务预期），优先调 MAX_SAME_ARGS_CALLS 而不是回退机制。
- isMeaningful 的「失败/无法」子串启发式未动：正文里恰好含这些词的有效结果仍不计为进展，
  极端情况下会让无进展计数提前到 5 轮触发，属已知取舍。
- 尚未做的两级：循环检测到后的「软干预」（往消息历史注入提醒让模型自纠，第三次才硬停）、
  跨 worker 的每 run 重复调用统计（可挂在 TokenUsageAdvisor 同位置做进 RunInspector 用量页）。
