日期：2026-11-10（随 2026-11-11 批次修复提交）

问题现象（外部评审 P0 #1/#3/#4 的三个缺陷，一并记录）：
1. 兄弟扩展（expandSiblings）用「命中块文本当 query 再做一次向量检索」取同章节块：
   章节超过 6 块会漏；返回按相似度序而非 chunkIndex 阅读序（跨行表格/条款编号乱序）；
   每次扩展多花一次 query embedding。
2. rerank 池截断藏在 DashScopeRerankService 内部（静默 limit(20)）：融合候选 15+15=30 时
   第 21~30 名无日志消失，评审无法发现池被砍。
3. 词法通道三连：ILIKE 写在 SELECT 的 CASE 里、外层过滤 lexical_score>0，content 上的
   trgm GIN 无法下推成索引条件（scope 内逐行扫描）；无停用词（"的是/什么"等 gram 假命中）；
   limit(20) 按插入顺序截断，30 字问题后半句词项整体丢失。

影响范围：
AgentKnowledgeRagService 召回/兄弟扩展/词法链路；长文档、长问题、多候选场景最明显。

原因：
兄弟扩展误用向量检索做集合查询；截断逻辑与服务上限耦合无观测；词法 SQL 结构使索引失效。

解决方式：
1. 兄弟扩展改 JdbcTemplate 元数据直查（documentId+sectionPath，ORDER BY chunkIndex，
   LIMIT extra+1），KnowledgeVectorSchemaInitializer 补复合表达式索引 idx_kv_document_section。
2. recall() 显式按融合序截到 rerankService.maxDocuments() 并 log.info；rerank 索引映射改用截后池。
3. ILIKE 挪进内层 WHERE（trgm GIN 可下推）；新增 LEXICAL_STOPWORDS（中文虚词 gram+英文短词）；
   词项上限 20→32；平局按短内容优先（length(content)）。
另捎带：兄弟扩展预算门禁（核心检索超 sibling-expansion-budget-ms 默认 1800ms 跳过扩展）；
parseQuality=degraded 标记（parser≠mineru）+ 回答侧提示；Micrometer 分段 timer/
rerank 降级/向量池不足计数。

验证结果：
定向 15/15 绿（FilterSafety 2 + LexicalTerms 4 + RerankPool 1 + SiblingExpansion 3 +
VersionFilter 3 + Metrics 2）；全量 650 例失败 9 个均为既有基线（创作模块 + DashScope 欠费），
knowledge 零涟漪。mvn -DskipTests package 通过。

后续注意事项：
- 效果数字待阶段 1 golden set（语料待定）基线对比，不预设提升幅度。
- 兄弟扩展 SQL 依赖 idx_kv_document_section，首次启动自动创建（IF NOT EXISTS）。
- macOS target/ 出现「类名 2.class」副本会让 surefire 报 wrong name，先 mvn clean 再查。
