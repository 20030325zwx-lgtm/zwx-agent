# Aster AI 工作台：GitHub 设计借鉴与方案修订

日期：2026-10-28。状态：方案讨论，未开始业务实现。

## 1. 产品方向修订

用户澄清：Aster 要成为 AI 工作台，对话只是交互方式之一；后续可能覆盖个人资料/文档/研究、开发项目/终端、团队业务/工作流，以及拖拽画布。

建议把产品中心从“会话”提升为“项目中的工作对象”。以工作区和项目组织任务、资料、产物、画布与工作流；以 AI 协作入口操作当前对象。首页应是可直接工作的入口，有快速任务、最近项目、待处理任务和最近产物，而非宣传首页或固定聊天页。

修订原计划的工作区定义：原草图可保留为“专注对话视图”，不能成为所有功能必须嵌入的主页面。原计划中的 macOS arm64、本机免注册、免部署、供应商配置和可选依赖仍有效。用户尚未要求立即实现全部长期能力。

## 2. 研究口径

本轮读取 GitHub 公共 README、许可证文本及部分仓库链接的官方演示截图。实际查看 n8n 流程编辑器、AFFiNE 文档演示画面、OpenHands 自动化控制台。未部署这些产品做完整交互评测；下表“建议借鉴”是结合资料作出的设计判断，不是已经验证的接入能力。

GitHub 元数据 API 本次触发匿名速率限制，因此不比较 star 数、提交活跃度或未经验证的版本排名。使用仓库 HEAD 的公开内容，具体实现与许可证后续引入时应固定版本复核。

## 4. 建议的工作台结构

### 应用层级

工作区（个人 / 后续团队）→ 项目 → 任务、资料、产物、画布、工作流。

个人用户首次可落在自动创建的个人工作区，快速任务无需先创建项目。项目也不必绑定代码目录：研究项目可有资料，开发项目可绑定授权本地目录，业务项目可关联外部系统。设置拥有者/作用域应从一开始清晰，但首版不需要实现多人协同系统。

### 界面分区

1. 全局导航：工作台、项目、资源、自动化、设置。能力未上线时不显示空入口。
2. 左侧项目资源树：当前项目下的任务、文档、文件、画布和流程；可收起。
3. 中央工作区：可切换或并排的对象标签页。打开文档显示编辑/预览，打开流程显示节点图，打开任务显示执行现场，打开代码显示代码工具。
4. 右侧辅助区：AI 协作、选中对象属性、运行详情按场景切换，不同时永久占据三栏。允许把 AI 协作独立分屏。
5. 底部按需工具区：日志、终端、运行历史；办公场景默认不展示开发工具。

宽度不够时，资源树、辅助区和底部工具渐进折叠；不能在普通笔记本上同时常驻五块窄面板。统一记录布局、标签页、草稿和当前对象，离开设置能回到原工作状态。

### 三种使用方式，共用对象

- 快速任务：描述目标 → Agent 规划执行 → 查看产物，保留当前简单入口。
- 内容工作：文档/文件/白板占主区，选中内容后让 AI 总结、改写、生成或比较。
- 流程工作：画布占主区，AI 帮助生成或修改流程草稿，用户检查后测试运行；执行详情可追溯。

AI 入口随当前对象变化，但上下文必须可见：显示所引用的文件/选区/节点，允许移除。仅因为打开了一个标签页，不应默认为模型上传全部内容。

## 5. 两种画布必须区分

| 类型 | 自由内容画布 | 可执行工作流画布 |
| --- | --- | --- |
| 目的 | 整理资料、研究、构思、展示 | 定义可复用、可测试的自动化 |
| 元素 | 文档引用、图片、网页、便签、任务、产物 | 输入、模型、工具、条件、循环、人工确认、输出 |
| 连线 | 语义关联/视觉组织 | 控制流或数据依赖 |
| 操作 | 拖拽、缩放、分组、排列、关联 | 连接校验、参数设置、变量映射、试运行、发布版本 |
| AI 辅助 | 基于选中内容归纳、生成与整理 | 生成流程草稿、解释节点、定位失败 |

两者共享资源 ID 与引用，不把可视连线自动解释为可执行逻辑。普通用户看到的是不同视图/对象；内部也应分别保存自由布局和流程定义。

建议用户路径：先让 AI 完成一次任务 → 用户选择“整理为可复用流程草稿” → 补齐明确输入/输出和依赖 → 检查权限与凭据 → 测试 → 保存版本。一次临时 Agent 计划包含动态决策和副作用，不可直接承诺“一键转为可靠流程”。

## 6. 两个具体场景

研究报告：把材料拖入项目 → 在自由画布整理证据与观点 → 选中材料让 AI 起草报告 → 文档主区修改 → 把每周重复调研整理为工作流模板 → 运行后产物回到同一项目。

开发任务：打开项目目录 → AI 分析并提出修改 → 主区并排代码/差异/预览 → 底部查看验证日志 → 需要时保存测试或发布流程。发布仍遵守该任务的执行权限与人工确认规则。

团队业务以后增加工作区成员、角色、共享资源、审批和审计，复用相同项目/任务/产物关系；多人实时编辑另行规划，不假定加一个“团队模式”开关就能实现。

## 7. 技术方向：现在铺哪些基础

- 共用 Workbench Shell：导航、对象标签页、分屏、辅助面板、布局恢复，避免把新功能全部塞进 `SuperAgent.vue`。
- 视图扩展点：按对象类型注册打开方式、图标、工具栏、可执行动作。先做内部模块注册，不在首版做任意第三方代码插件加载。
- 统一对象引用：稳定 ID、所属工作区/项目、类型、版本、来源任务；现有会话和文件保留兼容，拟议对象不是当前已有表结构。
- 持久化产物：报告、代码文件、图片、流程定义独立于聊天消息，可在项目中找回、预览和复用。
- 运行模型：区分 WorkflowDefinition/Version（定义）与 Run（一次执行）；运行绑定定义版本，前端通过统一事件展示状态、错误、输出和人工确认。
- 引擎适配边界：Aster Agent 保留现有任务运行；以后通过适配器关联 n8n 或 BPMN 引擎的实例 ID 和状态，处理取消、恢复、幂等和凭据归属。不强行把三种引擎的状态完全等同。
- 画布库是交互底座，不提供业务执行引擎。[xyflow](https://github.com/xyflow/xyflow) 当前 README 明确是 React Flow/Svelte Flow，不能直接当成 Vue 组件接入。Aster 使用 Vue 3，选型应先验证 Vue 兼容方案或隔离组件成本，不能为了一个画布仓促重写全部前端。
- 优先验证 [Vue Flow](https://github.com/bcakmakoglu/vue-flow)：已核对其 README 明确支持 Vue 3、自定义节点/边、拖动、缩放和平移；官方 npm 元数据标示 MIT。可用于工作流画布原型，但还需验证现有 Vue/Vite 版本、性能、键盘交互、撤销/重做和序列化兼容。此前旧地址 `bcakmak/vue-flow` 返回 404，已从官方包元数据确认当前仓库地址。
- 自由白板与富文档编辑器也需单独评估；不要默认与节点图使用相同库。具体库尚未定案。

### 已有 n8n / Flowable 探索如何利用

本仓库 `evaluation/n8n-document-poc/README.md` 记录了文档上传、索引、人工审核与 n8n 生命周期试点；源码存在 `N8nReviewEventNotifier` 和 `KnowledgeAdminController` 的 `workflow-status` / `resume-info` / `review-events` 接口。本轮只核对存在，没有复测当前运行状态。

`evaluation/flowable-document-poc/README.md` 明确：嵌入式 Flowable 7.2 是 mock delegate POC；独立 Flowable UI 6.8 不可直接当作 7.2 的前端。后续若需要 BPMN 和长周期人工流程，再评估该路线。

优先从已有 n8n 文档流程做“工作台展示统一运行状态”的一个垂直试点。把编辑器导航/嵌入、统一身份、运行事件适配分开评估；iframe 嵌入不等于完成工作台集成。独立本机核心功能不能依赖外部 n8n 服务才能启动。

## 8. 修订后的推进顺序

1. 工作台基础 + 桌面验证：以模块化工作区代替聊天页外壳；验证本机启动与模型配置，保留快速对话。对象标签页至少能容纳任务和文件预览。
2. 任务—产物闭环：项目资源列表、任务运行详情、文件/文档预览、引用当前资料给 AI、草稿和布局恢复。选一个“研究报告”或“项目任务”完整验收。
3. 工作流垂直试点：接通一个已有 n8n 文档流程，统一查看状态、待确认事项与产物；再判断原生编辑器和外部编辑器的边界。
4. 原生画布：按真实使用优先级交付可执行流程编辑或自由内容画布之一，补版本、撤销/重做、自动保存与错误恢复，避免两套复杂编辑器同时铺开。
5. 扩展开发与团队能力：代码/终端视图、定时/事件自动化、团队权限、协作与审计；Windows 支持沿用原后续规划。

当前就保留架构扩展点，但只交付能闭环的模块。长期兼容三个场景，不等于首版把三个成熟产品合并实现。

## 9. 直接使用代码的边界

设计借鉴与代码复用分开：Dify LICENSE 为 Apache 2.0 加附加条件；n8n 为 Sustainable Use/企业授权；LobeHub 为 Community License；AFFiNE、Flowise 按目录有不同授权。OpenHands 本次根 LICENSE 为 MIT，xyflow 为 MIT。引入源码或分发第三方产品前按具体模块与固定版本确认，不能仅凭 README 徽章假定无限制商用。

本轮结论是交互与架构借鉴，不建议 fork 某个产品作为 Aster 的新主体，也未执行安装、部署或业务代码修改。

## 10. 正式开发的组件库选择

用户要求正式开发采用成熟组件库，优先适合 Agent 界面的方案。选择 **Ant Design Vue + Ant Design X Vue + Vue Flow**；当前交互原型只用于设计讨论，不直接作为生产组件实现。

| 层次 | 选择 | 使用范围 |
| --- | --- | --- |
| 基础 UI | [Ant Design Vue](https://github.com/vueComponent/ant-design-vue) | 导航、标签页、表单、选择器、树、表格、弹窗、抽屉、提示与主题 |
| AI 交互 | [Ant Design X Vue](https://github.com/wzc520pyfm/ant-design-x-vue) | Sender、Bubble、Conversations、Attachments、Prompts、ThoughtChain 等展示/输入基础组件，按需使用 |
| 流程节点画布 | [Vue Flow](https://github.com/bcakmakoglu/vue-flow) | 自定义节点、连线、拖动、缩放；业务执行引擎与运行状态另行接入 |
| Aster 业务组件 | 自有封装 | 项目工作区、工具调用卡、权限确认、执行计划、引用、产物与运行检查器 |

选择理由：现有前端是 Vue 3，Ant Design Vue 能覆盖从个人工作台到团队业务管理的通用组件；X Vue 提供同体系的 AI 交互组件；Vue Flow 对应未来节点流程。统一主题变量调整密度、圆角、色彩和边界，保留轻量桌面应用视觉，不直接套用后台管理模板。

本次核对 npm latest 元数据：Ant Design Vue 4.2.6（Vue >=3.2）、Ant Design X Vue 1.6.0（Vue >=3.5、Ant Design Vue >=4）、Vue Flow 1.48.2（Vue ^3.3），均标记 MIT。当前 `frontend/package-lock.json` 实际锁定 Vue 3.5.14，满足这些声明的 peer 范围；`package.json` 仍声明 ^3.2.47，实施时应统一声明和锁定，避免依赖解析结果不清晰。这只证明版本约束相容，未安装构建验证。

Ant Design X Vue 是独立维护的 Vue 实现，不等同于 `ant-design/x` 官方 React 包。已核对其 README 和发布包中的 Sender/Bubble/Attachments/Conversations/ThoughtChain 类型目录；Ant Design Vue README 也将其列为生态项目。正式使用通过内部组件封装隔离升级影响，不把库的请求 hooks 当成必须替换现有 SSE/恢复协议的理由。

对比过的候选：Element Plus + Element Plus X 同样有 AI 组件，当前后者声明 Vue ^3.5.17，现有锁定版本还需升级；Naive UI 适合通用 Vue 工作台，但此次优先同体系的 Agent 交互配套；官方 Ant Design X 与 assistant-ui/react 属于 React 栈，不为此迁移现有前端。

实施验证范围：主题与弹层、长消息/Markdown 渲染、流式追加与滚动、输入法与附件、停止/重连、任务事件到组件状态的映射、网页与 Electron 构建。ThoughtChain 仅展示可公开的执行步骤/状态，不承诺获取或展示模型内部推理。自由内容画布不自动等同 Vue Flow 的流程节点图，富文档/白板编辑器仍按后续需求评估。

本轮只确定组件选型与适配边界，没有安装依赖或修改业务代码。
