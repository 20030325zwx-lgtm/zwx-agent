# Infinite Canvas 对照评审与 Aster 渐进改造建议

日期：2026-10-31。本文是源码评审与建议，不是实施完成记录。

## 1. 结论与范围

**值得重点学习它的创作交互和扩展边界；Aster 应在现有 VueFlow、工作流引擎、媒体任务和素材库之上渐进改造。** 不建议因为界面观感而更换 React、另建执行引擎或整体搬运代码。

两者解决的问题有重叠，但核心不同：

- Infinite Canvas 主要把素材、提示词、参数、生成与迭代组织在浏览器画布上，连线主要表达生成引用。
- Aster 已有项目归属、工作流版本/运行快照、服务端媒体任务与素材归集；需要把这些执行能力呈现成易理解、可操作的创作体验。
- 节点连接丰富不等于持久工作流调度成熟；后台任务可靠也不等于创作体验已闭环。这两个维度要分别验收。

审查基线：

- 外部仓库：[basketikun/infinite-canvas](https://github.com/basketikun/infinite-canvas)，浅克隆固定提交 `9cd3deacbcc598361807afc16c059a80dd18b6f9`。
- 本地 Aster：`2061b7a`，路径 `/Users/zhuwenxuan/Desktop/agent/yu-ai-agent`。
- 外部项目仅检查源码、README、功能/操作/待测文档；未安装依赖、未运行或实际操作界面，未测性能或真实模型效果。浏览器打开 GitHub 尝试超时，因此布局评价依据组件结构及操作文档。
- 本轮未重跑 Aster 构建/测试、未执行计费请求。此前测试结果不作为此次改造通过证据。
- README 的赞助商产品介绍不视为本项目功能。项目自身明确处于开发阶段、不保证历史数据兼容，另有待测清单。

## 2. 对照结果

| 维度 | Infinite Canvas 已见实现 | Aster 当前情况 | 建议 |
| --- | --- | --- | --- |
| 产品重心 | 以内容和节点操作为中心的视觉创作 | 项目、工作流、运行记录与创作页面并存 | 在项目内贯通素材→操作→结果→复用 |
| 画布技术 | React + 自研指针/缩放画布，并非 React Flow | Vue 3 + VueFlow | 继续 VueFlow，用自定义节点提升体验 |
| 节点呈现 | 文本/图片/视频/音频/配置/分组；预览及节点附近工具 | 工作流节点主要展示类型、名称、状态；参数检查器 | 先做图片、文本、生成配置与产物预览 |
| 引用方式 | 上游资源、缩略图、类型标签、@引用、分组展开 | 素材选择已有，但跨节点仍依赖表达式和参数名 | 提供角色化引用 UI，保留高级表达式 |
| 连线语义 | `fromNodeId/toNodeId`；未含类型化输入输出端口 | `from/to` + 参数字符串引用 | 两者都不足以直接充当完整数据契约；补端口与绑定 |
| 运行语义 | 前端请求及节点状态；视频任务号可保存并恢复轮询 | 服务端执行、媒体任务、WAITING_EXTERNAL、运行图快照 | 保留后端职责，继续完善恢复与幂等 |
| 编辑体验 | 多选、分组、复制粘贴、快捷键、撤销重做 | 已有拖拽、连线、空白处加下游、自动布局等；当前编辑器未见撤销重做实现 | 优先补编辑历史与可理解的复制规则 |
| 节点扩展 | 集中 registry；Content/Panel/toolbar/resource/Host 接口 | NODE_TYPES、默认参数、帮助和后端分支分散 | 建统一节点契约和静态注册表 |
| Agent | 结构化画布操作、本机桥接、client/turn 绑定 | 已有 Agent 与工具体系 | 扩展现有 Agent 的项目/画布工具 |
| 数据 | localforage/IndexedDB，媒体 blob 分离，导入导出，WebDAV | 服务端数据库、素材存储与权限归属 | 借鉴资源清单和导出格式，不替换权威存储 |

## 3. 最有价值的六项借鉴

### 3.1 把“看结果、改参数、再生成”放在一个创作现场

外部项目在节点内预览内容，选中节点后显示配置和相关操作；图片可继续裁切、编辑、派生。其专业感的重要来源是反馈与操作靠近内容。

Aster 建议布局：

- 顶部：项目名、工作流版本、保存状态、运行入口。
- 左侧可折叠：本项目素材、模板、节点搜索。
- 中央：足够大的画布；结果卡直接展示缩略图/文本摘要、运行状态和来源。
- 右侧按需出现：所选节点的业务参数；日志、原始 JSON 放高级详情。
- 底部可折叠：本次运行进度、失败步骤、结果版本对比。

避免同时常驻素材、参数、Agent、运行记录四个宽面板。Agent 与属性面板可切换；小屏使用抽屉。颜色表示稳定含义，状态同时用文字/图标，悬浮工具提供点击及键盘替代入口。

第一版应保留原输入与已选结果，新生成作为新结果版本展示；不用“同一张卡始终覆盖”掩盖创作过程。

### 3.2 引用要有业务含义

外部项目的引用条和 @ 资源引用让用户看到使用了什么素材。Aster 可在其基础上提供“商品图、人物图、风格参考、文案”等角色，而不要求用户理解 UUID。

建议引用契约包含资源身份、版本、角色、顺序；具体字段命名需实施时与现有模型对齐。缩略图/签名 URL 只是展示数据，持久身份继续使用服务端素材标识。

必须处理：缺失引用、素材权限、模型参考图数量上限、角色与提供商能力不匹配。@ 标签由稳定资源身份解析，不能仅按当前连线顺序决定业务含义。模型不支持精确角色控制时，应如实说明只是提示词约定。

### 3.3 统一节点定义，驱动表单、连线校验和 Agent 工具

外部 registry 将创建菜单、默认尺寸、默认数据、节点内容、面板和工具栏关联起来，这一点适合借鉴。Aster 还应补业务执行契约。

建议分工：

- 后端维护节点类型/版本、输入输出 schema、参数约束、所需能力、执行副作用与权限校验。
- 前端静态注册组件，关联标题、图标、表单、预览、帮助；消费后端可用能力描述。
- Agent 使用相同业务校验，不绕过工作流 API 写数据库。
- 新增节点时，提供一种注册方式和契约测试，不再四处修改列表和长条件分支。

这不意味着把前端组件塞进 Java 配置，也不要求立即开放第三方插件。

### 3.4 编辑历史与运行记录分开

外部源码已有历史快照，约 50 个历史项、180ms 合并窗口；历史包含节点等状态，并非服务端命令日志。

Aster 建议先建立编辑命令层：新增/删除/移动/改参数/连线/分组。一轮拖动形成一次撤销，复制时重映射节点和内部引用，删除节点可恢复。

必须划清：撤销画布编辑不能撤销已产生的模型费用，不能删除数据库运行事实，也不能把运行状态退回过去。取消请求、终止上游任务、撤销编辑是三个操作；上游不支持取消时，UI 明示其能力边界。

分组默认只影响展示和移动，不改变执行顺序；“分组作为批量输入”应是显式操作。

### 3.5 让 Agent 操作结构化画布

外部已有 `add_node/update_node/connect_nodes/run_generation` 等操作及会话目标 client 绑定，值得借鉴的是“明确操作对象和操作协议”。

Aster 可复用已有 Agent，提供获取选区、读取图摘要、提出图修改、校验修改、应用修改、发起运行、读取运行结果等工具。建议操作请求带项目、工作流、基础修订号和请求幂等标识；这些是建议契约，不是现有接口。

先校验整批修改，再原子应用；返回受影响节点和差异。修订冲突重新读取，不能盲覆盖。发起计费、外发或其他副作用操作继续走用户配置的权限/授权策略；普通编辑不必反复确认。

验收要覆盖多标签切换、编辑途中 Agent 返回、重复请求、跨项目素材及权限失效。外部 apply helper 主要是状态转换，其浅层检查不能直接作为 Aster 的服务端验证器。

### 3.6 把成功作品沉淀为可复用模板

外部导出把 JSON 与按 storageKey 收集的媒体打包；提示词库支持来源和本地缓存。这对 Aster 的“创作后复用”很有价值。

Aster 模板应包含流程结构、参数、变量说明、预览和资源依赖清单。导入时重映射身份、检查权限及能力版本；密钥不进入模板，短期签名 URL 不作为唯一资源来源。先做本项目内另存模板，再考虑跨项目资源包。

## 4. 工作流与创作画布如何共存

遵循已确认的 `2026-10-31-workflow-creative-integration.md`：复用现有工作流引擎和画布，不建设第二套独立引擎。

建议在同一编辑器中明确三类对象：

1. 资源展示：素材、文本、结果版本、说明、分组；不因摆在画布上就被执行。
2. 可执行节点：生成、编辑、理解、合成、导出等，沿用现有工作流类型及执行服务。
3. 运行投影：某次 run 的状态、输出与错误叠加到节点；不是工作流定义本身。

画布位置与大小进入编辑布局；执行参数与类型化绑定进入可版本化定义；任务状态与结果进入运行数据。不能把这三部分继续都堆入一个节点 metadata 并由不同异步回调覆盖。

连线需要区分“数据绑定”和“仅执行依赖”。数据边明确来源输出、目标输入、类型与可选角色，并产生执行依赖；纯展示关联不参加拓扑调度。连接动作尽量完成输入绑定，避免用户画完线还要手填同一关系。

旧图仍可读取。先建立旧表达式→新绑定的兼容层，无法可靠转换时保留为高级表达式并提示，不静默猜测。运行继续冻结定义、模型与已解析输入；改稿不改变在途运行。

单节点/局部重跑应是显式新运行或关联尝试：锁定所用上游结果版本、仅执行选定子图。上游输入变化后标记下游结果过期，禁止把旧结果当作新版本结果。

## 5. 不宜直接照搬的设计

- **全浏览器直连与本地权威存储**：适合个人本地创作工具；Aster 已承担服务端归属、任务恢复与审计，迁回前端会改变产品边界。
- **动态远程插件加载**：源码 fetch JS 后用 Blob + dynamic import 在当前前端上下文执行，不是隔离沙箱。先做第一方静态节点，后续有真实生态需求再设计插件能力权限和隔离。
- **把引用图当作执行 DAG**：外部连线未带完整类型端口，不能解决 Aster 输入契约、依赖校验、幂等、崩溃恢复问题。
- **直接移植历史快照机制到任务系统**：异步结果与 UI 撤销需要独立语义，不能只恢复节点状态。
- **主页面继续堆功能**：外部编辑器也很大。Aster 宜按编辑命令、节点注册、运行投影、资源引用和业务表单拆分；后端按图校验、节点执行器、运行生命周期拆分，先保行为再迁移。
- **一次追齐视频、音频、插件市场**：接口中出现支持字段不代表所有模型都支持，也不代表已实测。Aster 先完成当前图片主链路；小说复用文本编辑/版本确认能力，正文长编辑保留适合的章节工作区。

## 6. 分阶段实施与验收

以下是推荐顺序，不是工期承诺。每阶段提交代码、验证记录、兼容说明后再扩大范围。

| 阶段 | 交付物 | 必须通过的验收 |
| --- | --- | --- |
| A：契约与状态边界 | 节点静态注册、输入输出契约、文档/UI/运行状态分离、旧图兼容 | 既有海报/试穿/小说流程可读取；未知节点、缺失输入、类型不匹配在提交前被定位到具体节点；后端独立拒绝非法输入；编辑在途图不改变运行快照 |
| B：一个创作闭环 | 图片/文本/配置/结果卡、角色引用、模型能力驱动表单、结果版本对比、编辑撤销 | 从项目素材选择→生成→挑选→继续编辑→导出均可完成；不手填素材 UUID；参考图丢失明确报错；两次结果可对比；撤销不删除运行事实；刷新后素材和选定版本恢复 |
| C：可靠迭代 | 局部运行、失败项重试、输入快照、幂等、结果来源及恢复 | 双击提交不产生重复意图任务；一支失败不误标所有分支；只重试目标失败项；后台重启有可解释恢复；同步提交结果未知时不自动盲重提；旧结果不能覆盖新运行 |
| D：Agent 与复用 | 结构化编辑工具、修订冲突处理、模板导入导出 | Agent 整批操作校验后应用；跨项目越权拒绝；切换标签不改错项目；重复请求幂等；导出不含密钥；导入后节点/引用映射正确且依赖缺失可见 |

阶段 B 的最小主场景建议使用现有电商能力：商品图/人物图 → 多方案生成或试穿 → 人工选定 → 文案/海报合成 → 素材归档与导出。先做两个候选结果，闭环稳定后再扩大批量。

人工选定必须成为显式状态。第一版可由用户选定后发起下一次运行；确需单次运行跨人工等待时，再增加持久 WAITING_USER 和恢复接口，不用页面弹窗伪装可恢复等待。

验证分层：图契约/迁移/编辑命令做单元测试；幂等、恢复、权限及事务做集成测试；完整创作与跨标签操作做 E2E；提供商真实能力另记模型/协议/调用结果，Mock 通过不算真实出图通过。

建议性能基线（尚未测量）：固定设备/浏览器，分别用 100 和 300 个节点及明确连线数、缩略图规格测试；100 节点常用操作反馈 P95 目标 ≤100ms，300 节点连续拖拽目标 ≥30fps。记录首屏时间、长任务和内存；不达标先用视口裁剪、缩略图懒加载、选择器订阅和按需预览定位问题，再决定是否需要底层替换。
