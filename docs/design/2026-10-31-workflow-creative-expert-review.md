## 2. 需要优先解决的具体问题

### R01 / P1：工作流完成通知与运行状态不具备原子性

证据：`WorkflowService.java:791` 创建媒体任务后，`:796` 写等待节点，再由 `:458` 将运行置 WAITING_EXTERNAL；`:845` 先更新节点 SUCCEEDED，再更新 steps、恢复运行，均为独立 JDBC 写入。恢复器 `WorkflowMediaResumeScheduler.java:46` 仅扫描 WAITING_EXTERNAL 节点。

风险：进程在节点写 SUCCEEDED 后、运行推进前退出，节点会退出扫描范围，而运行仍在等待；创建媒体任务后、写等待关系前退出，也会留下无法正常续跑的运行。恢复将运行置 RUNNING 后才向内存线程池提交，存在额外崩溃窗口。当前未找到普通 RUNNING 工作流的租约恢复机制。

建议：把节点终态与运行就绪态转换放入短事务；通过持久化待执行记录或 outbox 通知 worker。运行/节点认领使用租约与版本，启动后扫描可恢复记录。远程 HTTP 调用在事务外。副作用节点使用稳定幂等键；不支持上游幂等/对账时明确 UNKNOWN，不能承诺网络调用 exactly-once。

验收：在上述每个写入边界中断并重启，运行最终能继续或明确进入待处理状态，不无限等待、不重复提交已受理生图。

### R02 / P1：等待恢复器存在队首阻塞

证据：`WorkflowMediaResumeScheduler.java:41` 查询全部等待节点，按 `e.updated_at` 排序 LIMIT 20，之后 Java 才判断媒体任务是否终态；非终态分支不更新扫描位置。

风险：前 20 个任务长期生成或停留 INGEST_FAILED，后续已完成任务无法进入本轮扫描，持续卡在等待。批量运行前必须处理。

建议：SQL 优先筛选需要推进的媒体终态并匹配运行状态；非终态监控使用独立公平扫描。状态推进带条件更新/认领，完成事件可加速，定期对账负责补漏。

验收：构造 20 个长期未结束任务与第 21 个已完成任务，第 21 个在约定恢复 SLA 内推进。

### R03 / P1：创作首页与编辑器不是同一套运行契约

证据：`CreativeHome.vue:147` 的弹窗只有工作流、项目、关键词，`:288` 不传素材 input；`WorkflowEditor.vue:756` 才扫描参数并生成素材字段。后端 `WorkflowService.java:400` 只检查 input 非空，未对模板必填参数预检。

影响：从创作首页选择淘宝试穿模板，无法填写必需的模特/上衣/裤子；错误延迟到执行节点才暴露。

建议：提供版本化 inputs/outputs schema（字段 ID、中文标签、类型、角色、必填、默认值、数量限制、示例），首页、项目、编辑器、Agent 共用同一运行表单和后端预检。运行前校验素材、引用、模型操作能力、必需服务；精确指出哪个字段需要补充。启动请求固定 definitionVersion，并增加用户意图级幂等键，避免重试 HTTP 创建两个不同 run 后分别计费。

验收：同一模板从各入口得到相同字段与校验；缺上衣时不创建 run/job、不调用模型；同键重试只产生一次运行。

### R04 / P1：试穿结果“继续创作”会丢失编辑语义

证据：`CreativeProject.vue:782` 只复制 prompt、size、watermark；`:708` 新提交固定为 text_to_image，未保留参考图。实际页面可见试穿结果卡片有该按钮。

影响：用户期待在原模特和服装上调整，下一次却变成无参考图生成，可能花费一次生成费用后得到完全不同的人和商品。

建议：区分“使用相同输入再做一版”“编辑这张结果”“只复用提示词”。前者恢复 operation、参考素材顺序、模型与参数；编辑结果将选中 asset 作为新的参考输入。尚未支持的操作隐藏或明确禁用。再次运行形成新版本并保留父任务关系。

验收：对 image_edit 结果继续创作，请求仍为 image_edit，参考图及其角色准确；不得静默降为文生图。

### R05 / P1（本地部署）/ P2（来源与体验）：海报仍存在两套存储和输出协议

证据：`WorkflowService.java:631` 先 storeArtifact，`:1200` 直接写 OSS；之后 `:638` 用 CreativeAssetService.upload 再存一份，失败仅日志告警；`:645` 返回 objectKey。`CreativeAssetService.java:87` 将该路径固定记录为 UPLOAD，source job 字段为空。

影响：无 OSS 的本地创作虽然可生图，海报链路仍失败；工作流成功不保证项目素材库可找到海报；自动生成海报会被当前代码归为“上传”，与评审材料的来源描述不一致。多个 poster 节点还共享 runId/poster.png 对象键，可能覆盖前一个输出。

建议：让海报渲染也通过统一资产登记/入库服务，返回 `{assetId, mediaType, ...}`；使用 run/node/outputIndex 唯一键，登记 workflowRunId、nodeKey、输入资产与渲染模板版本。归集失败进入可重试状态；只重新入库，不能重跑试穿。对象链接按需派生，不作为节点永久契约。旧 Artifact 输出保留兼容读适配。

验收：纯 LOCAL 模式完成海报；重复登记无重复素材；两个海报节点互不覆盖；生成筛选可找到海报；归集失败可恢复且模型调用数不增加。

### R06 / P2：引用解析与持久化输出不适合更复杂模板

证据：`WorkflowService.java:1038` 递归 Map、不递归 List；缺失引用在 `:1057/:1080` 返回空串。`:464` 持久化输出截断到 4000 字符，恢复时 `:437` 直接用该输出继续执行；JSON 可被截断为无效值。

建议：表达式保持原始类型，递归处理对象/数组；保存时验证引用节点存在、是上游且输出类型匹配。持久化完整结构化结果或不可变结果对象引用，UI 摘要另行截断。必填引用失败应报具体字段错误，不能替换为空串。

验收：数组内素材引用正确解析；拼错节点保存即报错；超过 4000 字符的结构化输出在等待恢复前后语义一致。

### R07 / P2：模型能力档案在读取时被重写

证据：`MediaModelResolver.ensureProfile` 对已有标准适配器每次 resolve 都 upsert；openai-compatible 默认声明 image_edit，DashScope 默认 VERIFIED；`MediaModelProfileRepository.java:61` 覆盖能力/schema/验证状态并无条件 revision+1。

影响：协议兼容不代表具体模型支持多参考图编辑；人工维护能力和验证结论会在解析时被覆盖，revision 也不再代表实际契约变化。

建议：仅首次创建默认档案；能力按 provider/model/operation 维护，区分声明与实测。契约内容变化才升版本，校验失败关闭对应操作。prompt 长度、尺寸、quality、图数由模型操作 schema 驱动前后端，移除重复硬编码的 500 字和 DashScope 尺寸选项。

验收：人工验证/禁用编辑能力后再解析不被覆盖；无修改时 revision 不变；只支持文生图的模型不能接受试穿请求。

## 3. 架构建议：保留模块化单体，明确职责

目前不建议为此拆微服务或换整套工作流引擎。先在现有 Spring 应用内形成清楚的边界：

| 模块 | 职责 | 不应承担 |
| --- | --- | --- |
| 模板定义与编译 | 版本、输入输出 schema、依赖检查、运行预检 | 调用模型、处理存储细节 |
| 工作流运行器 | 持久化节点调度、等待/恢复/人工确认、失败范围 | 每个供应商的 HTTP 协议 |
| 创作任务服务 | 生成、编辑、幂等、配额、成本与不确定结果 | 工作流画布布局 |
| 资产与产物服务 | 统一登记、不可变版本、存储适配、来源和引用关系 | 决定用户是否认可图片 |
| 海报渲染器 | 按模板版本确定性排版、字体、导出 | 再次生成人物或重新生成文案 |

- `WorkflowService` 1420 行，混合 SQL、调度、模型调用、HTTP/DB 工具、存储和表达式；沿上述职责渐进抽离，先拆执行生命周期与产物写入，不做一次性重写。
- `MediaJobScheduler` 采用单线程循环，适配器同步 HTTP 可能阻塞 90–240 秒；这期间取消/查询/恢复都可能延迟。将短调度循环与有界执行池分开，按可用槽位认领，持有任务心跳续租，保留冻结令牌。批量提交前用慢供应商 Mock 验证公平性与取消延迟。
- 工作流图当前按拓扑排序串行执行。可以先在 UI 明示；之后对就绪节点做受限并行，例如文案与试穿可独立执行，依赖输出汇合时再合成。先完成恢复与幂等，再引入并行。
- 生图响应使用 BodyHandlers.ofString 后整体解析 b64，当前未见总响应大小限制。需限制 JSON/解码字节/输出数量，并在超限时保留“供应商可能已执行”的事实，防止内存压力扩大到整个工作台。
- VPN 兼容开关实际按配置布尔值放行主机名，不是自动识别桌面部署。仅可信本地环境开启；共享部署应拒绝危险组合、优先使用受控供应商主机白名单/代理出口，避免把任意主机名跳过 DNS 检查作为常规方案。

## 4. 代码规范：围绕可验证契约收敛

- 状态、操作、来源使用枚举/类型；节点执行接口返回结构化结果，减少 Map 与字符串状态在服务间穿透。
- 前后端共用节点 manifest/schema：中文名、输入/输出、默认值、能力、风险与费用类型统一声明，减少 NODE_TYPES、前端 palette/default/help 多处手工同步。
- 为节点实现定义独立 executor，依赖注入统一 ObjectMapper、Clock、HTTP client；将数据库操作放入 repository。统一时间来源，尤其租约的 JVM Instant 与 SQL now() 不应混用到依赖容器时钟一致。
- 消除空 catch：按业务区分可降级、明确失败、上游结果未知。降级在运行详情可见并记录原因；素材读取发生在 HTTP 提交前，应记本地失败，而非泛化为 UNKNOWN/可能计费。
- 前端 `WorkflowEditor.vue` 1042 行、`CreativeProject.vue` 1361 行。抽出共用 RunForm、AssetPicker、RunTimeline、ArtifactGallery 与请求/轮询 composable；共享表单错误和加载状态。
- 对关键行为写测试：崩溃边界、租约、幂等、引用、越权、计费次数、成功产物复用。颜色/间距等低影响改动以视觉回归检查为主。

## 5. 产品流程：将模板使用与模板编辑分开

建议普通用户路径为：选择“服饰试穿海报”模板 → 准备三张角色明确的图片 → 填商品事实与卖点 → 检查模型/调用计划 → 生成试穿预览 → 确认图与文案 → 选择版式/导出。

- 模板使用页只展示业务字段；“编辑工作流”作为高级入口，继续使用现有 Vue Flow。两种视图共用同一版本化模板与执行引擎。
- 试穿是概率性输出。增加可选的人工作品确认节点（WAITING_USER）：替换失败参考图、重做试穿、选择候选图，然后才合成。无人值守批量运行可作为后续显式模式。
- 区分“生成已完成”和“已确认可交付”。完成状态只代表计算结束，不保证衣服款式、颜色、标识与原商品一致。
- 重新排版只调用渲染器；改文案只重跑文案及下游合成；改服装只使相关试穿及其下游失效。每次动作展示复用与重做范围，沿 run/node/asset 记录版本谱系。
- 成本提示同时覆盖试穿图、视觉理解、LLM 文案；未知单价显示未知，不写 0。提供预计调用次数、批量总数、重试上限及不确定费用状态。按“每张通过人工验收的海报成本”评估价值。
- 参考图采用 role（模特/上衣/裤子）和顺序，而不是没有含义的 UUID 数组；在适配器处转换成供应商要求的有序文件。

## 7. 评审材料中应修正的表述

- “中文零错字”应改为“文字由确定性渲染器绘制”：LLM 仍可能写错事实，当前标题按 14 字截断，缺字体可能缺字，且图片解码失败会输出空白面板。
- “工作流更便宜”的表格缺少同条件对照，宜标架构预期。视觉理解与 LLM 文案也可能计费；用实测总成本、合格率和人工耗时验证。
- “服务不可用自动降级”不覆盖本地素材视觉调用：`understandLocalAsset` 缺绑定/异常直接抛错；需明确可选节点的降级策略。
- “每步落库、重启续跑”需限定已覆盖状态；R01 表明不能推广为整个工作流任意位置可恢复。
- “海报自动归为生成结果”与 R05 当前写入路径不一致，历史页面结果不能替代新运行验证。
- 在 src/frontend/evaluation 中未找到淘宝模板本身的完整版本化图定义，只找到文档与通用节点。现有模板可能保存在本地数据库；建议导出脱敏 template bundle 并纳入仓库，提供显式幂等导入，不能让新环境依赖某人的本地库。

## 8. 推荐执行顺序与验收

| 阶段 | 交付物 | 可检查的完成条件 |
| --- | --- | --- |
