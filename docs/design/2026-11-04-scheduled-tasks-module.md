# 自动化模块改为可配置定时任务：产品与实施规划

日期：2026-11-04

状态：规划稿，尚未实施。本文新增的页面、接口、数据表和类名均为建议设计，不表示仓库已有。

参考边界：用户已确认参考智谱 Z Code。已核对其官方《自动化》文档（https://zcode.z.ai/cn/docs/automations）。其中明确提供表单/会话/模板创建、周期规则、项目/权限/模型/推理强度、立即运行、暂停编辑、运行历史，以及本机唤醒限制。本文只借鉴与本项目有关的交互和语义，不承诺一比一复刻。

## 与 Z Code 对齐的决定

| Z Code 已确认行为 | 本项目建议 |
| --- | --- |
| 自动化包含定时任务与闲时任务两类 | 先只做定时任务；不要在界面预留一个无法使用的“闲时任务”标签。保留模块名“自动化”，页面标题“定时任务”，或按产品最终文案统一。 |
| 表单、会话、模板三种创建路径 | 首期交付表单和只读模板；会话中一句话建任务第二阶段接入，提交前仍显示结构化时间预览。 |
| 每小时、每天、工作日、每周、每月、自定义；自定义支持间隔、具体日期/星期与结束日 | 首期一次性、每天、工作日、每周；第二阶段补每小时、每月和自定义，时间规则引擎按完整能力设计。 |
| 指令、项目、权限、模型、推理强度配置 | 首期映射现有智能体能力；推理强度只有在模型调用链能实际传递并验证时才开放选项。 |
| 立即运行不改变下次执行时间与自动运行次数；运行中不会叠加第二条 | 作为验收标准，手动实例单独计数和标记触发来源。 |
| 设置/历史切换，历史含成功、失败及睡眠错过的跳过记录，并可跳到会话 | 首期交付。详情页使用双标签，不在列表塞完整运行日志。 |
| 本机唤醒、可选保持唤醒，最多 20 条，本地项目限定 | 先实现真实的“服务运行/本机唤醒”状态提示与错过记录；保持唤醒需要桌面端能力才展示。20 条可作为首期产品上限建议，需按实际用户量和服务成本确认。 |

对齐来源：Z Code 官方《自动化》文档（https://zcode.z.ai/cn/docs/automations）。

## 1. 定位与模块边界

侧边栏“自动化”改为“定时任务”。核心入口回答：做什么、什么时候做、在哪里做、结果在哪里看。

- 创作画布：定义图片/视频流程、模型、输入和节点依赖。
- 智能体：执行自然语言任务及工具调用。
- 定时任务：决定何时启动哪个执行对象，管理运行次数、状态和结果。
- 原通用工作流：保留定义、编辑器和历史；从定时任务的高级执行对象或“管理工作流”入口访问，不删除旧数据或直接改写旧路由语义。

新入口建议 `/schedules`，详情 `/schedules/:id`；保留 `/workflows` 及 `/workflows/:workflowKey` 的兼容访问。

## 3. 用户流程与界面

### 3.1 列表页

顶部：标题“定时任务”、一句说明“安排 AI 在指定时间完成任务”、主按钮“新建任务”。不用占据首屏的大型说明区或监控大屏。

默认展示紧凑任务列表；一行包含名称/任务摘要、执行对象、时间规则、下次执行、已自动运行次数、最近一次结果、启用开关、更多操作。时间规则显示“每个工作日 09:00”，不直接显示 Cron。

筛选：全部、已启用、已暂停、需处理。任务定义状态与最近运行状态分开显示：例如“已启用 · 上次失败”。

行内主操作：立即执行、暂停/恢复、查看结果；更多菜单：编辑、复制、归档。暂停不等于取消正在执行的任务，取消当前执行是单独动作。

空状态只展示少量只读模板，如工作日晨会动态、每日风险扫描、周五发布简报、文档同步检查；点击仅预填指令和调度，用户仍需审阅。模板明确是示例，不伪装成已运行的数据。

### 3.2 新建/编辑

采用居中表单或宽侧栏，按四个部分纵向排列，高级参数默认收起。

1. 任务内容：名称、任务说明；用户写“每天整理项目最新进展，列出完成项、阻塞项和下一步”。时间表达识别只能用于预填，保存前显示可校验的时间规则。
2. 执行对象：首期“智能体任务”；后续增加“创作画布”和“已有工作流”。智能体任务可选择已授权项目/工作区、权限、模型、已有技能和工具；不要求先画流程。推理强度待调用链支持后开放。
3. 执行时间：一次性、每天、工作日、每周、自定义间隔。明确时区、起止日期，并展示接下来 5 次执行时间。Cron 放高级选项，首期可不开放。
4. 执行与结果：默认独立会话、站内结果通知；高级项配置执行时限、调用次数上限、重试、重叠和错过执行策略。

底部：“保存并启用”为主操作，“保存为暂停”为次操作。“立即试运行”另行触发，明确它会真实调用模型，不是免费的校验按钮。

### 3.3 任务详情与运行详情

任务详情两个主页签：“配置”“运行记录”。每次运行独立记录计划时间、实际开始/结束、触发方式、所用配置版本、结果摘要、产物和关联执行 ID。

点击运行记录可进入已有智能体会话或创作画布查看全过程；定时任务页保留摘要与状态，不复制一套聊天或画布界面。首期站内显示未读结果和“待处理”数量；邮件、Webhook、系统通知后续再接。

## 4. 默认行为与边界

| 情形 | 建议默认行为 |
| --- | --- |
| 一次性任务 | 到期只产生一次调度实例；结束后定义标为已完成；失败的人工重试仍关联原实例 |
| 周期任务 | 独立生成每次执行记录；默认不继承无限增长的对话历史 |
| 上次还在运行/排队/等用户/等外部结果 | 跳过这次触发并记录原因；后续可配置“合并等待一次”，首期不堆积队列 |
| 错过计划时间 | 默认跳过，记录 missed；可选恢复后补最近一次，不补跑全部历史 |
| 编辑规则/提示词/模型 | 新版本用于之后的触发；已进入队列的运行保持快照，界面显示其版本 |
| 暂停 | 阻止新的自动触发；已经认领但尚未派发的实例再次检查定义版本/暂停状态；正在执行的实例不隐式取消 |
| 立即执行 | 走同一队列和授权链，记录 MANUAL；不改变周期的 next_run_at 和自动运行次数，也不绕过重叠策略 |
| 暂停中的立即执行 | 允许用户明确试运行一次，不恢复周期 |
| 连续失败 | 累计展示；建议达到 3 次后自动暂停并提示，可配置 |
| 等待权限确认/补充输入/选片 | 状态进入需处理；不当作失败自动重试，也不自动提升权限或代选素材 |
| 关闭页面 | 后台服务存活时继续执行 |
| 本机休眠/关机或后台服务停机 | 不能按点执行；恢复后按错过策略处理。服务器调度也不能直接访问离线本机目录 |

日期语义：采用 IANA 时区，UTC 存储实际时刻；“每周一 09:00”按当地日历计算，“每 2 小时”按固定间隔计算，不能混用。夏令时不存在的时刻建议跳过，重复时刻只触发一次；用预览和自动化测试固定行为。

## 5. 后台实现建议

### 5.1 架构

建议链路：任务定义 → 到期扫描 → 原子认领与实例落库 → 持久化派发队列 → 执行适配器 → 既有执行引擎 → 状态归并 → 运行记录/站内结果。

先复用 Spring + PostgreSQL，不因首期需求引入额外消息中间件。扫描器只发现到期并入队，不能在事务内调用模型，也不能依赖浏览器计时器。后续任务规模需要时，再评估独立队列。

建议新增 `platform/schedule` 包，包含定义服务、时间计算器、扫描器、派发器、状态归并器及执行适配器；名称在实施时按现有包规范定稿。

### 5.2 新增数据结构（建议）

- `scheduled_task`：tenant_id、user_id、name、status、target_type、target_config、schedule_type、schedule_config、timezone、next_run_at、revision、overlap_policy、misfire_policy、retry_policy、consecutive_failures。模型配置只引用安全配置 ID，不保存密钥。
- `scheduled_task_run`：task_id、definition_revision、scheduled_for、trigger_type、trigger_key、config_snapshot、status、target_run_id、conversation_id、started_at、finished_at、result_summary、error。自动触发键包含任务、版本和计划时刻；人工触发用客户端幂等键。
- `scheduled_task_attempt`：每次派发/恢复尝试、owner、lease_until、fencing_token、attempt、错误分类及外部任务身份。实例与尝试分开，失败重试不会伪造新的计划触发。

`scheduled_task_run` 的 QUEUED 行可作为首期持久化队列。唯一触发键防止重复入队，租约和 fencing 防止失效执行者覆盖状态；同一任务用原子活动实例认领落实重叠策略。

### 5.3 事务与恢复

扫描器锁定到期定义，事务内写入执行快照、唯一实例并计算 next_run_at，提交后由 worker 认领。worker 开始前检查取消标记、授权、执行环境和重叠约束。

派发到已有执行引擎也需要幂等键和可查询的 target_run_id。不能只给外层调度表去重：如果引擎已经启动、调度关联尚未写回就崩溃，重试可能再次调用模型。需要启动接口按 scheduled_task_run.id 查找/创建同一目标执行，或在同一事务建立关联并提交后启动。

重启时：QUEUED 继续认领；已有关联执行 ID 的实例恢复观察；租约过期但外部提交结果不明的实例先查询/对账，不盲目再次生成。现有 AgentRunRecoveryJob 将孤儿任务标为中断，需明确哪些检查点可安全恢复；非幂等工具的未知结果进入需人工处理。

不承诺外部供应商端到端 exactly-once；通过持久化触发去重、派发幂等和结果对账降低重复执行风险。

### 5.4 独立后台智能体入口是前置任务

将 ManusAgentController 中组装模型/工具/上下文/工作区/权限的逻辑抽为共享应用服务，由交互入口和定时派发器调用。后台模式不能靠伪造 SSE 客户端保活；事件应能持久化，页面只是观察者。

工具必须注册既有 run 权限作用域和用户规则；无人值守不等于 YOLO。遇到已有 ASK/需要用户补充时挂起并保留恢复上下文。显示已有 PLAN/BUILD/EDIT/GUARDED 等选项时，沿用其真实语义，不新增同名但不同效果的模式。

运行时限和模型调用上限应实际强制执行。精确金额预算需可靠的供应商计价数据支持，未接通前只显示可核实的 token/调用次数，费用标为估算或未知。

## 6. 接口建议（不是现有接口）

| 方法与路径 | 作用 |
| --- | --- |
| GET /api/scheduled-tasks | 分页列表、状态筛选、下次执行和最近结果 |
| POST /api/scheduled-tasks | 创建定义，显式选择启用或暂停 |
| GET/PATCH /api/scheduled-tasks/{id} | 读取/乐观锁更新配置 |
| POST /api/scheduled-tasks/preview | 无模型调用，校验规则并返回下 5 次执行时间 |
| POST /api/scheduled-tasks/{id}/pause 或 /resume | 调整后续触发状态 |
| POST /api/scheduled-tasks/{id}/run | 幂等手动入队 |
| POST /api/scheduled-tasks/{id}/archive | 停止后续触发，保留运行历史 |
| GET /api/scheduled-tasks/{id}/runs | 运行历史 |
| GET /api/scheduled-task-runs/{runId} | 结果及下游执行深链 |
| POST /api/scheduled-task-runs/{runId}/cancel 或 /retry | 取消或显式重试，仍检查权限和副作用 |

所有接口按用户与租户隔离；项目、工作流、模型引用在创建和派发时都检查有效性。初期详情轮询即可，后续再补事件推送。

## 7. 创作画布接入规则

第二阶段开放“执行创作画布”。选择项目和确认过的画布版本，冻结图、模型、提示词及素材绑定；编辑画布不会悄悄改变既有计划，提示用户显式更新绑定版本。

沿用唯一开始节点、全部上级成功才执行的约束，调度器只负责启动流程，不改变节点依赖。多候选等待用户选片时，定时实例进入 WAITING_INPUT 并阻止同任务重复堆积。

旧通用工作流绑定明确的 definition version；不创建空工作流来承载每一个自然语言任务。首期媒体任务只自动生成并保存结果，不顺带加入发布到外部平台的行为。

## 8. 分阶段交付及验收

### 第一阶段：可独立使用的定时智能体任务

先完成后台独立执行入口，再交付列表、表单、一次性/每日/每周/工作日、时间预览、暂停恢复、手动运行、持久化调度、结果记录、站内待处理入口、基本重试与重叠控制。

验收：关闭页面仍执行；到期只出现一个实例；重启后定义和队列不丢；上次没结束不会重叠；暂停/编辑与认领并发时行为确定；结果可回到对应会话；无人应答的权限请求不会误报成功。

### 第二阶段：创作画布与既有工作流

增加两种执行适配器、绑定版本预览、候选待处理、取消与异步完成映射。验证重复派发不会重复创建供应商任务；画布节点依赖保持不变。

### 第三阶段：体验增强

再增加自然语言生成时间规则、任务模板、自定义间隔/Cron、变化才通知、外部通知渠道。自然语言解析需确认后的结构化规则才生效。

测试必须覆盖固定时钟、时区/DST、错过执行、并发扫描、租约失效、派发崩溃、用户隔离、权限撤销、手动幂等，以及浏览器页面关闭后的后台执行。供应商调用先用模拟实现；真实计费验收单独安排。

## 9. 待用户补充但不阻断规划

- 已确认参考智谱 Z Code；参考其当前公开《自动化》文档。是否还需对齐某个特定版本的视觉设计或交互截图，可在实施前补充。
- 默认执行环境：当前本机后台，还是长期在线服务器；可先明确本机能力边界，避免误以为关机后也会执行。
- 首批实际任务：建议提供 2～3 个真实用途，以便确定默认模板、工作区范围和通知粒度。
