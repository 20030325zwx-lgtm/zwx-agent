## 一、概念与架构

### Q1.1 什么是 Agent？它和大模型直接调用的本质区别是什么？

**口述答案（30–45s）**：Agent 是「模型在循环里做决策」的系统：模型能观察环境、选择下一步动作、调用工具拿到真实结果，再据此继续决策，直到满足完成条件或被外部终止。大模型直接调用是一次性的输入输出映射，没有观察—决策—执行的闭环，也没有副作用。本质区别不在「有没有工具」，而在**控制权是否交给了模型**——一旦交给模型，你就必须为它的错误决策准备预算、超时、权限和验收，这才是 Agent 开发的真正工作量。

**追问预案**：那你怎么判断一个系统「够格」叫 Agent？（看是否有循环、是否有基于环境反馈的自主分支、是否有真实副作用。）

**工程兜底要点**：控制权外移带来四类必防问题——无界循环、无界成本、越权副作用、错误的自我验收。缺任何一类保护，生产上都会出事。

**Aster 挂钩**：普通业务 Agent（单轮模型 + 按需 RAG/工具）与超级 Agent（`agent/graph/ManusGraphOrchestrator.java` 的 Planner→Workers→Verifier→Aggregator）正好是「不交控制权 / 有限交控制权」两档，用它说明「不是所有场景都该上 Agent」。

### Q1.2 Agent 的基本架构由哪些核心组件构成？

**口述答案**：五个必选 + 三个进阶。必选：意图识别、运行核心（ReAct 或图编排这类循环）、上下文管理、检索/RAG、评估与反馈。进阶：规划器、记忆系统、工具执行沙箱。另外有三个横切件容易被候选人漏掉，但面试官很爱听：**身份与租户贯穿**（异步执行时不能丢）、**生命周期钩子**（运行前/步骤前/工具前后/结束/错误/中断）、**可观测**（trace + token + 工具成功率）。

**追问预案**：为什么身份传递要在架构里单独提？（子任务一旦异步，鉴权、数据隔离和审计就会断链。）

**工程兜底要点**：把「组件清单」讲成「数据与控制流」：谁产生上下文、谁消费、谁能在失败时终止它。

**Aster 挂钩**：横切件对应 `agent/hook/AgentHookPipeline.java`（记忆注入/压缩/提取、工具预检、结果截断、执行 trace 都是独立 hook）；身份对应 `platform/security/CurrentActor.java` + `web/controller/AiController.java`。

### Q1.3 Workflow、Agent、Tools 三个概念的区别？

**口述答案**：Workflow 是**开发者预先写死的控制流**，分支由代码或规则决定，可预测、可测试、成本低；Agent 是**模型决定的控制流**，走几步、调哪个工具由运行时判断，灵活但不确定；Tools 是两种范式共用的**能力出口**，本身没有决策权。选型问题我会反问一句：这条流程能不能提前枚举？能枚举就用 Workflow，只在枚举不了的地方（意图理解、参数补全、非结构化抽取）嵌一次模型调用。

**追问预案**：那你怎么混合？（Workflow 做骨架，节点内部允许 Agent 化；Agent 的自由度按节点风险逐级放开。）

**工程兜底要点**：Workflow 的失败是「某个节点挂了」，Agent 的失败是「走错路还自信」。后者的排查手段完全不同，需要 trace 而不是日志。

**Aster 挂钩**：旅游/情感这类流程稳定的业务用固定编排；跨领域多步骤任务才进 `ManusGraphOrchestrator`。这个取舍本身就是答案的一部分。

### Q1.4 Agent 和 Chatbot、Pipeline、CLI 的边界在哪？打标签算不算 Agent？

**口述答案**：判断标准是三个问题：模型能不能决定下一步、动作会不会改变外部世界、失败时有没有回路。Chatbot 只有对话状态，Pipeline 只有固定顺序，CLI 是人驱动工具——它们都不满足「模型决策 + 副作用 + 反馈回路」。给数据打标签如果是一次调用，那是 LLM 应用不是 Agent；如果它会自己决定查哪些字段、发现置信度低就回头补充检索，那它就是 Agent。所以「算不算」取决于有没有循环和自主分支，不取决于名字叫 agent。

**追问预案**：这么抠定义有什么实际意义？（有：决定了你要不要为它建评测集、限流和审计，非 Agent 的轻量链路不需要那套成本。）

**工程兜底要点**：不要在简历里把一次模型调用写成 Agent，面试官一定会追问循环在哪。

**Aster 挂钩**：`capability/skills/SkillPromptBuilder.java` 里的技能是「给模型的能力描述」，不是决策体；能明确区分 Skill / Tool / Agent 三层，这题就稳了。

### Q1.5 描述一次完整的 Agent loop 迭代，中间发生了些什么？

**口述答案**：一轮大致七步：① 组装上下文（system + 工具 schema + 记忆 + 历史 + 上一步结果）；② 调用模型；③ 解析输出（文本 or tool_calls）；④ 若为工具调用则做授权与参数校验；⑤ 执行并施加超时/大小限制；⑥ 结果截断或结构化后回填上下文；⑦ 判断终止条件（完成/超步数/超预算/被用户中断/需人工审批）。关键点是每一步都要有**退出路径**，尤其是第 4、5 步失败时必须能回到第 1 步而不是抛出后卡死。

**追问预案**：同一轮模型返回多个 tool_calls 怎么处理？（见 Q2.7：先判依赖，无依赖并行，有副作用的串行，并做幂等。）

**工程兜底要点**：步数上限、单步超时、总 deadline、token 预算四个限制必须同时存在；只有步数上限的实现在长上下文场景照样能烧穿成本。

**Aster 挂钩**：`agent/execution/AgentToolCallLedgerService.java` 记录每次工具调用，是「第 5、6 步可追溯」的落点；结果截断在 `agent/hook/ToolResultTruncationHook.java`。

### Q1.6 项目里为什么用（或不用）Agent？这题怎么答不被反问倒？

**口述答案**：用「三判据」答：任务能不能预先枚举、错误的代价有多大、有没有可验收的客观信号。流程固定且错误代价高（比如转账、发信）→ Workflow + 人工确认；流程开放且错误可回滚（调研、总结、草稿）→ Agent；有客观验收信号（能跑通测试、能核对字段）→ 可以放心让模型多试几步。千万不要答「因为 Agent 是热点」，那正好给面试官递刀。

**追问预案**：那你为什么还上了多 Agent？（因为要并行且需要统一验收，同时要承认代价：延迟、成本、故障面都变大了。）

**工程兜底要点**：主动说清代价——多次模型调用带来的延迟与费用、规划错误传播、并发取消和结果冲突。承认代价是加分项。

**Aster 挂钩**：`../agent-interview-notes.md` §「普通 Agent 与超级 Agent 的区别」那张对比表就是这题的标准答案来源，直接背「额外成本」那一行。

### Q1.7 LangChain 和 LangGraph 有什么区别？分别适合什么场景？为什么有时选择手搓？

**口述答案**：LangChain 抽象的是「链式组件」——模型、Prompt 模板、Retriever、Memory、Tool 的标准化封装，适合快速搭单流程和做集成。LangGraph 抽象的是「状态图」——显式的节点、边、状态和 checkpoint，适合有循环、分支、返工、中断恢复的编排。手搓的理由通常是三个：框架的上下文拼装不透明，出 bad case 时定位不了；依赖升级会静默改变行为；生产要的是可控的超时、取消、审计，而这些恰恰是框架最不关心的部分。我的选择原则是**集成用框架，控制流用显式图或自己的代码**。

**追问预案**：那你项目用的什么？（Java 生态：Spring AI 做模型与工具调用的映射，编排用 Spring AI Alibaba Graph 自建图节点。）

**工程兜底要点**：框架选型要连带说明「出问题时代码里能不能找到那一行」。找不到就是生产风险，不是效率问题。

**Aster 挂钩**：`agent/graph/PlannerNode.java`、`WorkersNode.java`、`VerifierNode.java`、`AggregatorNode.java` 是自己显式命名的节点，好处是每段都能单独测、单独限流。

### Q1.8 自研 Agent 和 Coze/Dify 这类平台怎么选？你体验过它们什么优缺点？

**口述答案**：平台的优点是快、可视化、天然带知识库和插件市场，适合业务验证和非工程角色参与；缺点有三：控制流黑盒（复杂分支和循环难以表达）、上下文不可控（拼装顺序你改不了）、深度定制会撞墙（工具权限、租户隔离、审计粒度）。我的分界线是：**给单一业务同学用的问答类应用放平台，进生产的核心链路必须自研**，因为前者错了可人工兜底，后者错了是资损和合规问题。

**追问预案**：如果面试官问「Manus/扣子这类产品的改进建议」——按「可控性 / 可观测性 / 成本」三条线给具体建议，别夸 UX。

**工程兜底要点**：平台做 POC、自研做落地是常见组合；说清迁移成本（提示词资产、评测集要重建）。

**Aster 挂钩**：本项目自研的核心理由可作为答案——需要租户级隔离、工具级授权（`capability/tools/ToolGuardPolicy.java`）和执行审计，这三项平台都不给细粒度控制。

## 二、推理范式

### Q1.9 什么是 ReAct？它怎么实现？和 CoT 的区别？

**口述答案**：ReAct 是让模型交替产生「Thought（推理）」和「Action（工具调用）」，再把工具返回的 Observation 写回上下文继续推理，直到给出最终答案。实现上就是循环：把 Thought/Action/Action Input 组织进 Prompt 或用原生 tool calling，解析出工具名与参数执行，结果作为 Observation 追加。和 CoT 的区别：CoT 只在模型内部推理，不接触外部世界，结论无法被事实校正；ReAct 把推理锚定在真实观测上，能自我纠偏，代价是延迟、成本和需要死循环保护。

**追问预案**：ReAct 常见失败模式？（工具选错、Thought 里空转不调工具、拿到 Observation 后无视、反复同一调用。）

**工程兜底要点**：Thought 与 Action 分离解析；解析失败要有降级（重试一次带纠错提示，再失败则回落到直接回答）；必须有步数上限与重复调用检测。

**Aster 挂钩**：`agent/core/ReActAgent.java` 是文本式循环的实现，`agent/core/ToolCallAgent.java` 是原生 tool calling 版——两者并存正好能说明「工程上我更愿意用模型的原生函数调用而不是正则解析 Thought」。

### Q1.10 ReAct、Plan-and-Execute、Reflection 三种范式的核心区别？项目怎么选型？

**口述答案**：ReAct 是边想边走，每一步都由模型决定，适合步骤不可预知、需要根据中间结果频繁改道的任务。Plan-and-Execute 是先产出完整计划再逐步执行，全局结构清楚、可审计、便于并行，适合能提前分解的任务；弱点是计划一旦错了后续全错，所以要保留重规划入口。Reflection 不是执行范式而是质量范式——产出后来一轮自我批评再改，适合有明确验收标准的场景（代码、报告），不适合事实性问答（模型会把自己的正确答案改错）。我的默认组合是**全局规划 + 局部 ReAct + 一次有上限的返工**，并把反思固定在「验收器」角色而不是让执行者自评。

**追问预案**：为什么反思不该由执行者自己做？（同一模型同一上下文，偏差是共享的，自评容易过度自信。）

**工程兜底要点**：返工轮数必须硬上限；反思要产出结构化 verdict（pass/revise/unverified），不能是自由文本。

**Aster 挂钩**：`VerifierNode` 输出 pass/revise，模型调用或解析失败记为 `unverified`（早期版本这里是 fail-open 直接放行，属于我修过的真实缺陷——这个细节值得讲）。

### Q1.11 Plan-and-Execute 里的 DAG 怎么工作？某个子任务失败了怎么办？

**口述答案**：计划表示成有向无环图，节点是子任务、边是数据依赖，无依赖的节点并行执行，有依赖的等前序产出。控制流用拓扑序推进，每个节点带自己的输入契约和超时。子任务失败要分四类处理：可重试的瞬时错误（指数退避重试）、参数或依赖不满足（回头重规划而不是硬执行）、工具本身不可用（降级或换工具）、模型产出质量不达标（有限次返工）。最忌讳的是「失败就整体重跑」，那会把成本变成乘法。

**追问预案**：怎么防止 DAG 里出现环或者两个节点互相等？（规划时校验拓扑可存在性，非法计划直接拒绝并回退成单任务。）

**工程兜底要点**：必须有全局 deadline 和「已花费预算」概念；节点结果要么入库要么显式标记缺失，不能让下游基于空结果继续编。

**Aster 挂钩**：`PlanJsonParser.java` 把计划硬约束在 `MAX_STEPS = 4`，解析或模型失败时回退为单个 general 任务——即「宁可少并行，不可整链失效」。

### Q1.12 如何赋予 LLM 规划能力？CoT、ToT、GoT 这些方法你怎么看？

**口述答案**：从轻到重四档：① Prompt 内约束输出为结构化步骤（最常用、最可控）；② CoT/自洽性（多路采样投票，提升单次推理质量）；③ ToT/GoT——把中间状态组织成树或图做搜索回溯，效果好但调用量成倍上升，只有「错了能廉价验证」的题才划算；④ 后训练（用规划数据 SFT 或偏好优化）让模型天生会拆任务。工程上我优先用 ① + 验收器，因为规划失败的主要表现是「拆得不合理」而不是「不会拆」，用结构化约束 + 一次人工或规则校验比上搜索树性价比高得多。

**追问预案**：怎么判断一个计划质量好不好？（看覆盖原始需求、步间依赖是否成立、每步是否可验收——这三个维度能做成自动检查。）

**工程兜底要点**：计划必须是**执行建议而非权限令牌**——不能让计划文本决定工具能不能被调用，权限由代码在运行时授予。

**Aster 挂钩**：这条正是 `../agent-interview-notes.md` §3 里「规划结果是执行建议，不是权限令牌」的原话，Worker 启动时仍由代码按角色过滤工具。

### Q1.13 复杂任务怎么做任务拆分？为什么要拆？效果怎么提升？

**口述答案**：三个动机：单上下文放不下（拆小才能塞满有效信息）、错误半径（小步骤失败只重试小块）、可并行。拆分维度我按顺序试：按**产出物**拆（每步有独立可验收产物）→ 按**角色**拆（调研/写作/校验）→ 按**数据边界**拆（不同文档、不同表）。提升效果的关键不是拆得更细，而是给每个子任务写清**输入契约和完成标准**，否则拆完只是把一次幻觉变成四次。拆过细的代价也要讲：聚合时上下文丢失、跨步一致性变差、成本上升。

**追问预案**：怎么知道拆得不合理？（看返工率和聚合阶段的冲突数；如果 Verifier 总在挑跨步矛盾，说明拆得太碎或依赖没建对。）

**工程兜底要点**：子任务数量硬上限；每步结果结构化为固定字段而不是自由文本，方便聚合与差异定位。

**Aster 挂钩**：Planner 限 4 个子任务并指派 researcher/author/analyst/general 角色；`WorkerRole.java` 是角色到工具集合的映射入口。

### Q1.14 Agent 的反思（Reflection）机制怎么实现？为什么要用？有什么坑？

**口述答案**：实现是「生成 → 按标准批评 → 带批评重做」的闭环，关键是批评要有**可判定的标准**（schema 校验、测试是否通过、引用是否存在、需求点是否覆盖），而不是让模型泛泛地问自己「对不对」。为什么要用：模型单次输出的错误率在高难任务上很高，而多轮自我修正对格式类、逻辑类任务收益明显。坑有三个：一是自我强化偏见（同一个模型看不到自己的盲区）；二是无界返工（越改越差还停不下来）；三是把反思成本说成质量保证。所以我会给反思配**外部信号**——规则、测试、检索证据——并把轮数锁死。

**追问预案**：反思和 Code Review 的关系？（同构：需要独立视角、明确 checklist、可阻塞合并；区别是 Review 有确定语义，反思只能给概率性结论。）

**工程兜底要点**：反思结论必须落成枚举值；达到上限仍不通过的，要明确标注「未验收」而不是悄悄放行。

**Aster 挂钩**：`VerifierNode.java` 的 `unverified` 状态 + `AggregatorNode.java` 的 `[未验收]` 标注，是这题最有力的答案细节。

### Q1.15 Agent 为什么会死循环、路径震荡、重复调用？怎么检测和治理？

**口述答案**：成因主要是四类：工具返回内容无法推进判断（返回空、报错或语义模糊），模型退而求其次重复上一次动作；上下文过长导致目标被稀释，模型忘了已经做过；工具描述重叠，两个工具都能「看起来对」；终止条件写得不可判定，模型永远觉得还差一步。治理分层做：硬限（步数、总 deadline、token 预算）先兜住成本；再用**重复检测**——把 (工具名, 规范化参数) 做哈希，N 次内重复就拒绝执行并回灌提示；再加震荡检测（最近 K 步在两个状态间来回切换则强制收敛）；最后加一次显式「是否已完成」判定，把模糊终止条件变成结构化判断。

**追问预案**：重复调用一定错吗？（不是，轮询类任务合法。所以要用白名单和进度判据区分「有效重试」和「空转」。）

**工程兜底要点**：死循环要能被外部中断（用户断开 SSE、run 取消），并在审计里留下「为什么被终止」的枚举原因。

**Aster 挂钩**：`../agent-interview-notes.md` §11 讲了取消传播的现实限制——`Future.cancel(true)` 只是发起中断，底层 HTTP/JDBC 不一定立即停；这题主动说出这个边界，比只讲算法更有说服力。

### Q1.16 什么是 Agent 的「任务幻觉」？模型没执行工具却说做完了，怎么办？

**口述答案**：任务幻觉是模型声明了未发生的事实——说「已发送邮件」但根本没调用工具，或者把计划当成结果汇报。成因是对话式训练偏好「给出确定的完成答复」，而 Agent 的副作用必须由代码确认。治理靠三点：① **完成状态由系统判定不由模型判定**——只有 ledger 里存在成功的工具记录，才允许走「完成」分支；② 最终答案要求携带**证据字段**（来源、引用 ID、执行记录 ID），后端校验这些 ID 真实存在；③ 高危副作用走审批态，模型只能声明「已准备好草稿」。

**追问预案**：怎么量化这类幻觉？（做「声明—实际执行」对齐率：回答声称的动作集合与 ledger 中成功动作集合的差集比例。）

**工程兜底要点**：不要指望用 Prompt 写「禁止谎报」来根治，那是概率约束不是硬约束。

**Aster 挂钩**：`agent/execution/AgentToolCallLedgerService.java` 提供「真实发生过哪些工具调用」的事实来源，是这个答案的落点。

## 三、多智能体

### Q1.17 什么是 Multi-Agent？相比单 Agent 有什么优势，又引入哪些新问题？

**口述答案**：Multi-Agent 是把一个任务拆给多个各有 Prompt、工具和上下文的执行体协作完成。真正的收益只有三个：上下文隔离（每个角色只装自己需要的信息，绕开长上下文退化）、职责与权限分离（工具面收窄，误用概率下降）、并行（吞吐与时延）。引入的新问题更多：通信成本（跨 Agent 传的是自然语言，信息有损）、状态一致性（并发改同一资源会冲突）、错误放大（上游错一步下游全错）、故障面扩大（超时、失联、部分成功）、成本与调试难度翻倍。所以判断标准很硬：**能用单 Agent + 好上下文工程解决的，不要上多 Agent**。

**追问预案**：哪些场景值得上？（需要不同权限域、可并行、且有统一验收环节的任务——写代码 + 跑测试 + 出报告。）

**工程兜底要点**：上多 Agent 前必须先具备 trace、run 级取消、成本上限和结果落库，否则线上不可运维。

**Aster 挂钩**：超级 Agent 四个节点就是这套取舍的落地，`../agent-interview-notes.md` 对比表里「额外成本」一行要背下来。

### Q1.18 Single-Agent 与 Multi-Agent 的设计方案怎么选？子 Agent 的任务边界怎么定？

**口述答案**：我会按「是否需要不同的权限域」而不是「是否需要不同的能力」来切。子 Agent 的任务定义要满足四条：输入能一句话说清、产出可独立验收、失败可单独重试、与其他子任务无共享可变状态。反过来，如果发现两个子 Agent 必须来回对话才能推进，那说明它们本来是一个任务，硬拆开只会引入通信损耗。实践上我倾向**协调者—工作者的浅层结构**，不做对等协商式多 Agent——后者不确定性太高，工程上不可运维。

**追问预案**：子 Agent 之间要不要共享记忆？（可以共享只读的长期记忆，但工作记忆必须隔离；共享可变记忆等于把并发问题引进来。）

**工程兜底要点**：每个子任务显式声明依赖边；没有依赖才允许并行；聚合阶段要能识别并标注冲突来源。

**Aster 挂钩**：`WorkerRole.java` 的角色划分就是「按权限域切」的实现——researcher 和 author 拿到的工具面不同。

### Q1.19 多 Agent 的协作与动态切换机制怎么设计？调度策略如何实现？

**口述答案**：协作机制三层：**状态层**是共享的运行状态（计划、各步产出、活动事件），只允许通过明确的写入口变更；**通信层**是「结构化消息 + 结果摘要」，不传完整上下文，避免 token 爆炸；**调度层**决定谁在什么时候跑——按拓扑序调度无依赖节点、给每类角色配独立线程池、设置总 deadline 和单节点超时。动态切换（比如中途从简单路径升级到重路径）我建议只在**验收失败**这一个触发点上发生，并且只升一级，否则会变成无界升级。调度上还要防饥饿：长任务不能占满 worker 池，要有队列上限和显式拒绝策略。

**追问预案**：队列满了怎么办？（分场景：可降级的降级为提示词直答，不可降级的明确报告「未启动」，绝不能静默丢弃。）

**工程兜底要点**：调度器必须持有子任务句柄和取消状态，run 结束时统一取消未完成任务。

**Aster 挂钩**：`WorkersNode.java` 用 `FutureTask` + 专用 executor 并行、按 conversation 取消；RAG 队列满时降级、Worker 队列满时报告未启动。

### Q1.20 各角色的 system prompt 有什么不同？角色化怎么提升正确率？

**口述答案**：差异体现在四件事上：目标（调研角色只负责找证据不下结论）、可用品（工具清单不同，越权工具不出现）、输出契约（各自的 JSON schema 不同）、边界（明确「遇到超出你职责的问题就返回缺口而不是自己干」）。角色化的真正收益是**收窄选择空间**：给一个 Agent 30 个工具，它选错的概率远高于给 5 个。同时角色 Prompt 里要写明「不要做什么」，否则会出现每个角色都尝试收尾的重复劳动。多 Agent 提升正确率的机制不是「人多力量大」，而是每次调用的上下文更干净、工具面更窄。

**追问预案**：角色多了会不会失控？（会，所以角色数要和验收能力匹配——没有聚合与验收能力的第 5 个角色不该存在。）

**工程兜底要点**：角色 Prompt 要版本化管理，能单独评测；改一个角色就重跑全链路评测，否则无法归因。

**Aster 挂钩**：`agent/graph/` 四个节点各有一份职责边界，`PlanJsonParser.java` 限定角色枚举，超出即解析失败回退单任务。

### Q1.21 子 Agent 超时、失联、并发修改冲突怎么处理？

**口述答案**：超时用**分层 deadline 预算**：run 级总期限往下派发剩余预算，每层调用按剩余时间设 connect/read 超时，到点不再启动新子任务并取消在跑的。失联要区分「慢」和「死」：心跳或活动事件超时无更新即标记 failed，并把已完成部分保留成部分结果，让聚合阶段能降级交付而不是整单作废。并发修改冲突有三招：分片隔离（每个 Worker 写自己的工作区文件，最后由单线程聚合）、乐观并发（版本号/条件更新，冲突方重试）、或把写操作串行化到唯一协调者。绝对不允许两个 Worker 直接写同一个外部资源。

**追问预案**：`Future.cancel(true)` 就够了吗？（不够——它只是中断请求，底层阻塞 I/O 要靠 connect/read 超时或可取消客户端才真停；这是很多人答错的地方。）

**工程兜底要点**：取消要传播到工具层与外部连接池，并有测试覆盖断连场景。

**Aster 挂钩**：SSE 超时/错误设置停止标记 + `WorkersNode.stopAll()`、Worker 在 finally 中从活动集合移除；但统一取消上下文仍是我列出的待补缺口（notes §12）。

### Q1.22 某个 Agent 误判导致策略冲突怎么办？两个 Agent 结论不一致听谁的？

**口述答案**：先定义**仲裁优先级**，不能让模型临场协商。我的优先级是：确定性证据（数据库/工具返回值/测试是否通过）> 检索到的原文 > 模型判断；同级冲突时由 Verifier/聚合角色按显式规则裁决，并把冲突本身作为信息写入结果（「A 说涨价、B 说降价，来源分别是…」），而不是强行选一个。误判导致策略冲突的常见根因是**上游结论被当成事实下游直接消费**，修法是在数据流里区分「事实」和「推断」两类字段并各自带来源。

**追问预案**：能不能靠投票（多 Agent 取多数）？（能提升正确率但成本高，且不解决共同偏差；对可验证的事实用证据仲裁，对主观项才用投票。）

**工程兜底要点**：冲突率本身要做成指标，异常升高说明 Prompt 或工具描述漂移了。

**Aster 挂钩**：`knowledge/retrieval/AgentKnowledgeRagResult.java` 带检索状态与引用，正是「结论附来源」的落地形式。

### Q1.23 了解 A2A 吗？它和 MCP 最关键的区别是什么？

**口述答案**：MCP 解决的是**Agent ↔ 工具/数据源**的标准化接入：统一的能力发现、调用和结果格式，把「N 个 Agent × M 个工具」的适配成本降成一次性接入。A2A 解决的是**Agent ↔ Agent**的互操作：身份发现、任务生命周期、流式进度、跨系统长任务的状态同步与产物传递。最关键的区别我讲一句：**MCP 的对端是无状态的能力提供方，A2A 的对端是同样有决策权、有上下文、会失败的智能体**，所以后者必须处理信任、委托权限和任务归属问题。

**追问预案**：现在落地了吗？（协议还在早期，多数团队仍是内部自定义编排；能说出「我把它当设计参考而非生产依赖」比装作很熟强。）

**工程兜底要点**：跨 Agent 调用要处理身份透传与权限收敛——被委托方不能拿到委托方的全部权限。

**Aster 挂钩**：MCP 侧有 `capability/mcp/McpToolRegistry.java` 和 `McpToolDescriptor.java`；对外部 Agent 的协作目前项目没有，如实说「未落地，只是关注」即可。

### Q1.24 Workflow / Graph / Loop 的关系？怎么防止图跑飞、State 更新冲突、中断恢复？

**口述答案**：Loop 是最小单位（一次「决策—执行—观察」），Graph 是把多个可循环/分支的节点用显式边连起来，Workflow 是图的某种受约束形态（分支预先确定）。防跑飞靠三件套：全局步数/时间/成本上限，环检测，和「只有节点声明 DONE 才终止」。State 更新要避免原地修改共享对象，用不可变快照 + 单写入口，冲突时以「谁持有该字段的所有权」决定；并行节点各写各的字段，聚合节点再合并。中断恢复要求状态**可序列化**：把恢复所需的数据落库，而不是把运行时对象（连接、回调、SSE）留在状态里。

**追问预案**：内存 checkpoint 和持久化 checkpoint 的差别？（前者进程重启即失效，只能支撑同进程内的续跑；跨重启恢复必须落库并含版本信息。）

**工程兜底要点**：说清自己实现到了哪一档，别把内存态说成可恢复。

**Aster 挂钩**：`agent/graph/GraphCheckpoint.java` 是刻意只保留可恢复数据（计划、结果、验收状态）的 record，经 `agent/execution/AgentRunService.java` 落库；而图内执行用的是 `MemorySaver`（按 threadId=conversationId 隔离）——这个「两个层次」的区分讲清楚就是满分答案。

## 四、Harness 与工程化

### Q1.25 Agent Harness 是什么？为什么现在常被单独拿出来问？

**口述答案**：Harness 是模型之外、包围模型的那层执行框架——上下文组装、工具接入与授权、循环控制、中断与恢复、验证与评测、观测与成本核算。它的定位是「让同一个模型在不同 harness 下表现差异可控」。单独被问是因为现在模型能力趋同，产品差距主要来自 harness：同样的 Claude/GPT，Codex/Claude Code 和普通聊天框的完成率差好几倍。所以做 Agent 的工程岗，考察重点其实是 harness 设计而不是会不会调 API。

**追问预案**：Harness 和框架（LangChain）是一回事吗？（框架提供积木，harness 是你的那套装配 + 护栏 + 评测；框架可换，harness 是团队资产。）

**工程兜底要点**：harness 必须自带评测——没有评测集的 harness 只是胶水代码。

**Aster 挂钩**：把 `agent/hook/` 管线 + `agent/graph/` 编排 + `capability/tools/` 策略 + `evaluation/eval-sets/` 合起来描述，就是一套自研 harness 的骨架。

### Q1.26 如果让你设计一个完整的 Agent Harness，你会分几层？

**口述答案**：六层。① 接入层：请求解析、鉴权、限流、会话归属；② 编排层：循环/图、步数与预算、并行与取消；③ 上下文层：system、工具 schema、记忆、检索、历史与压缩策略；④ 能力层：工具注册、描述、授权、沙箱、幂等；⑤ 验收层：结构化 verdict、返工策略、人工审批态；⑥ 观测层：trace、token 与成本、工具成功率、评测集与回归门禁。每层要单独说清「失败时行为是什么」，这比画框图重要。

**追问预案**：哪层最难？（我答上下文层——它决定效果上限，且最难归因；其次是验收层，因为「什么算完成」本身就是业务定义。）

**工程兜底要点**：层间只通过明确契约交互；工具结果进入上下文前必须经过截断和脱敏，否则观测层与安全层都失效。

**Aster 挂钩**：六层能逐一对上本项目：`AiController` / `ManusGraphOrchestrator` / `AgentHookPipeline` / `ToolFactory`+`ToolGuardPolicy` / `VerifierNode` / `AgentToolCallLedgerService`+`TokenUsageService`。

### Q1.27 上下文污染怎么治理？为什么 Agent 多轮后效果变差？

**口述答案**：变差有四个可定位的原因：① 稀释——无关历史把目标指令挤出注意力焦点；② 陈旧——早期的错误结论被后续当成事实反复引用；③ 膨胀——压缩时先砍掉最有用的中间结论，留下工具原始输出这种低价值大块头；④ 角色漂移——历史里的助手输出把模型带向不该有的口吻。治理手段：分层压缩（保留任务目标和已确认结论，丢弃原始检索/网页正文，用引用 ID 代替全文）、给上下文打来源与时效标签、每 N 步强制「重述当前目标与已知事实」、把长期事实从对话历史里剥离进结构化记忆。

**追问预案**：压缩阈值怎么定？（按模型窗口和单轮预期输出留余量倒推，并且要看**内容**而不是只看 token——工具大块头优先压。）

**工程兜底要点**：压缩本身要用便宜的模型或规则做，不能每次全量重算；被压缩的内容要留指针以便回查。

**Aster 挂钩**：`agent/hook/MemoryCompressionHook.java` + `ToolResultTruncationHook.java` 分别管历史与工具结果两条膨胀源；`TokenUsageService.java` 的采样里带 `systemChars`，就是用来定位膨胀的。

### Q1.28 Agent 的自进化机制怎么实现？

**口述答案**：可落地的自进化有四档，成本递增：① bad case 回流——线上失败样本进入评测集，Prompt/工具描述改动必须过回归；② 经验沉淀——把成功轨迹里的可复用片段（工具序列、参数模板）写成技能或 few-shot 示例供后续检索；③ 参数化——把纠错反馈变成偏好数据做 DPO/SFT，这是真正的模型层进化；④ 自动改写 Prompt（如用另一个模型优化指令），风险最高，因为优化目标容易过拟合到评测集。工程上我做到 ①② 就很实在，③④ 必须有离线评测门禁否则是自欺。

**追问预案**：自动改写 Prompt 怎么防止「只优化了评测集」？（留出从未参与优化的盲测集，且指标要看任务成功率而不是打分均值。）

**工程兜底要点**：自进化的前提是**质量有客观信号**；没有验收信号的场景，先建信号再谈进化。

**Aster 挂钩**：`evaluation/eval-sets/`（含 baseline 快照与 `run_baseline.py`）是 ① 的地基；技能侧有 `capability/skills/BuiltInSkillRegistry.java` 可承载 ②。

### Q1.29 相同输入为什么会得到不同的 Agent 执行结果？怎么提升可复现性？

**口述答案**：原因分三类：**模型侧**——采样随机性（temperature/top-p）、MoE 路由与批形状导致的浮点差异、上游模型版本或灰度变更；**系统侧**——并行 Worker 完成顺序影响聚合、检索结果随知识库更新变化、工具本身返回外部状态、缓存命中与否；**上下文侧**——记忆和 trace 写回顺序不稳定。提升复现性的做法：评测固定 temperature=0 或低温度并记录模型快照版本；并行结果按子任务序号稳定排序再聚合；检索加时间戳/版本入 trace；给每次 run 记录可回放的输入快照。要老实说明：生产完全复现不现实，目标是**可解释差异**——出问题时能说清差异来自哪一层。

**追问预案**：那怎么还做 A/B？（固定评测集 + 多次采样取分布指标，比较区间而不是单次结果。）

**工程兜底要点**：trace 里存模型名与版本、温度、工具清单哈希；缺这些时线上问题只能靠猜。

**Aster 挂钩**：`agent/hook/ExecutionTraceHook.java` + `DashScopeRerankService.java`（检索结果带排序版本）是回答落点；并行顺序稳定性是我承认的待补强项。

### Q1.30 面试收尾题：如果让你从零设计一个 Agent 架构，你怎么讲？

**口述答案**：按「先约束、后能力」的顺序讲，避免一上来堆组件。第一步定边界：解决什么问题、错误代价多大、有没有客观验收信号——这决定要不要 Agent。第二步定骨架：固定流程用 Workflow，开放式任务用一个循环加显式终止条件，明确最大步数/时间/成本。第三步接能力：工具先做注册与授权（模型只能看见当前身份允许的），工具结果统一截断和脱敏。第四步做上下文工程：分层记忆 + 压缩 + 引用而非全文。第五步做验收与观测：结构化 verdict、ledger、trace、评测集和回归门禁。最后主动补一句风险：我的第一版不打算做多 Agent，先让单 Agent 的完成率和成本可观测，再决定要不要拆。

**追问预案**：第一版砍掉了什么？（多 Agent、自进化、自动重规划——理由是运维与评测能力还没建立。）

**工程兜底要点**：这道题区分候选人的是「有没有讲失败路径」，而不是「有没有讲高级组件」。

**Aster 挂钩**：把自己项目当成答案实例——「我先做了单 Agent 业务链，验证上下文和工具授权没问题后，才加了图编排做并行」。演进顺序本身是加分点。
