## 一、工具调用与 MCP

### Q2.1 Function Calling 的执行流程是什么？模型是怎么判断需要调用工具、并生成参数的？

**口述答案**：请求时把工具的 name/description/JSON Schema 一并给模型；模型在解码时如果判断需要外部能力，就不产出普通文本，而是产出一个 `tool_calls` 结构（函数名 + JSON 参数）。这个能力是**训练出来的**——模型在带工具标注的数据上做过 SFT/偏好训练，学会「什么时候该调、参数从哪填」。执行由运行时完成：解析函数名、按 schema 校验参数、真正调用、把结果作为 tool 消息回灌，再让模型继续生成。关键认知是：模型只是**生成了一个调用意图**，它并没有执行任何东西，所以执行前的授权和校验全在工程侧。

**追问预案**：模型会不会「想调但不输出调用」？（会，表现为直接编造答案。治理靠提示里禁止无据回答 + 检查该动作是否在 ledger 里真实发生。）

**工程兜底要点**：函数名和参数一律视为不可信输入；schema 校验失败要给结构化报错回灌，而不是直接抛异常终止会话。

**Aster 挂钩**：Spring AI 把模型的工具调用映射到 Java `ToolCallback`，注册与暴露由 `capability/tools/ToolFactory.java` 收口。

### Q2.2 Function Call 和 Agent 的工具调用是什么关系？

**口述答案**：Function Calling 是**模型层的输出格式**，一次调用一次返回；Agent 的工具调用是**循环里的一个环节**——它要额外处理「这一步做完后下一步做什么」，包括结果回填、失败重试、终止判定和副作用管理。所以 FC 只解决「模型会不会表达调用意图」，Agent 要解决「调用编不编得对、失败了怎么办、会不会停不下来」。另外 Agent 场景下还有工具可见性问题：不是所有已注册工具都该暴露给当前这次调用。

**追问预案**：只做一次 FC 算不算 Agent？（不算，见 Q1.4。）

**工程兜底要点**：把 FC 的返回当作「模型意图」，把工具执行结果当作「事实」，二者在 trace 里必须分开存，否则无法归因。

**Aster 挂钩**：`agent/core/ToolCallAgent.java` 是循环侧实现，`agent/hook/PlannedToolCall.java` 保存「模型计划要调什么」，与实际执行记录区分开。

### Q2.3 MCP 和 Function Calling 的本质区别是什么？

**口述答案**：不是竞争关系，是**分层**。Function Calling 是模型能力：决定调哪个函数、参数怎么填；MCP 是接入协议：规定工具怎么被发现、描述、调用、返回，以及宿主和提供方之间怎么握手。有了 MCP，一个工具服务写一次就能被任何支持 MCP 的客户端复用，把「N 个应用 × M 个工具」的适配成本变成一次性接入。反过来 MCP 不解决模型选错工具的问题，工具选择质量还是取决于描述写得好不好和模型本身的 FC 能力。

**追问预案**：那 MCP 有什么代价？（工具列表会进上下文，工具一多 token 成本和选择噪声都上升；还有第三方 server 的供应链与权限风险。）

**工程兜底要点**：接入外部 MCP server 要做能力登记与策略校验，不能因为它「标准化」了就默认信任。

**Aster 挂钩**：`capability/mcp/McpToolRegistry.java` + `McpToolDescriptor.java` 做工具登记，`capability/mcp/McpServerConfigurationService.java` 管 server 配置；本地还自建了 `services/browser-mcp`、`document-mcp`、`image-search-mcp` 三个 server。

### Q2.4 MCP 的 Host / Client / Server 三层各自职责是什么？

**口述答案**：Host 是宿主应用（我的 Agent 后端），负责持有用户身份与权限、决定暴露哪些工具、执行安全策略与用户授权。Client 是 Host 内部与某个 Server 一一对应的连接器，负责协议握手、能力协商、生命周期和请求转发，是「一个 server 一个 client」的隔离单位。Server 是能力提供方，对外声明 tools、resources、prompts 三类原语并执行调用。这么分的原因是把信任边界放在 Host：Server 只看到自己被授权的最小上下文，拿不到用户全量身份。

**追问预案**：为什么一个 Client 只对一个 Server？（避免能力串味和越权聚合，也让某个 server 故障不影响其他连接。）

**工程兜底要点**：Server 返回的内容属于**不可信数据**，会进上下文，因此是 Prompt Injection 的传播路径之一，必须标注来源并做敏感内容处理。

**Aster 挂钩**：`McpConnectionTestResult.java` 体现「接入前先连通性校验」；策略侧仍依赖工具层自身校验，未对 MCP server 做 schema 级细粒度授权——这是我要如实说明的边界。

### Q2.5 Agent Skill 与 MCP 最根本的差异？Skill 和 Prompt 又有什么区别？

**口述答案**：MCP 给的是**能力**（可调用的外部动作/数据），Skill 给的是**方法与知识**（怎么做某类任务的步骤、约束和参考资料）。Skill 通常是磁盘上的说明文档加可选脚本，按需加载；MCP 是运行时的远程调用。Skill 与 Prompt 的区别：Prompt 是每次请求都要带的指令，Skill 是**可延迟加载的能力目录**——先在上下文里只放名字和一句话描述，命中任务时才读入正文，这就是它省 token 的关键。代价是引入一个路由判断：模型要能正确决定「现在该加载哪个 skill」，加载错了等于没写。

**追问预案**：为什么 Claude Code 的 skill 写在 system 而不是 user query 里？（system 位置更稳定、优先级更高、不受用户输入污染，也便于按会话缓存。）

**工程兜底要点**：Skill 内容里如果有可执行脚本，它的安全等级等同于工具，不能因为「是文档」就免审。

**Aster 挂钩**：`capability/skills/BuiltInSkillRegistry.java` + `SkillPromptBuilder.java` 是「目录 + 按需拼装」的实现；仓库根 `skills/web-research.md` 就是一份技能正文。

### Q2.6 工具很多时怎么做 tool routing？多个工具都能完成子任务时怎么选？

**口述答案**：分三层收窄可见面：**按身份/租户**过滤（数据权限），**按 Agent 或角色**过滤（能力域），**按当前意图**过滤（动态检索）。最后一层是关键工程——把工具描述向量化，按用户请求检索出 top-N 注入上下文，而不是全量塞进去。当多个工具都能做时，我不让模型裸选，而是给**排序信号**：领域内专用工具优先于通用工具、只读优先于写、历史成功率高的优先。这套逻辑本质就是一个小型召回—排序问题，可以直接复用检索那套评估指标（工具选择准确率、top-1 命中率）。

**追问预案**：工具选择错了怎么定位是描述问题还是模型问题？（做「人工标注正确工具 vs 模型选择」的混淆矩阵；集中在某一对工具说明描述歧义，普遍错说明能力或上下文问题。）

**工程兜底要点**：工具数量上升时同时监控 token 成本和选择准确率，两条曲线一般一条涨一条跌，要显式选拐点。

**Aster 挂钩**：角色化过滤在 `agent/graph/WorkerRole.java`（researcher/author/analyst/general 各拿不同工具面）；通用角色当前可见全部已注册工具，这点我会说是扩散风险而不是优点。

### Q2.7 同一轮模型返回多个 tool_calls 怎么处理？并行有多大收益？会有冲突吗？

**口述答案**：先判断依赖关系再决定执行方式：读类、无共享资源的调用可以并行，收益基本等于「最慢一次调用」取代「多次调用之和」，在检索、抓网页这类 I/O 密集场景里提升非常明显（我实际遇到的是从数秒降到单次调用耗时）。但有副作用或访问同一资源的必须串行——同一文件的写入、同一外部记录的修改、有前后依赖的查询。工程上还要处理三个细节：任一调用失败时其他调用是否继续、结果回填顺序要与调用顺序一致（否则模型混淆）、以及每个调用要单独记录 id 以便对账。

**追问预案**：并行会不会踩线程安全问题？（会——每个调用要带自己的身份上下文，不能用共享可变状态传租户信息。）

**工程兜底要点**：写类工具要带幂等键，重试不能重复扣款/重复发信。

**Aster 挂钩**：`capability/tools/IdempotentToolCallback.java` 就是给工具调用套幂等语义的位置；`agent/graph/WorkersNode.java` 用专用 executor 做子任务级并行。

### Q2.8 工具接入多了导致 Prompt 膨胀怎么办？工具 description 为什么这么关键？

**口述答案**：膨胀有三条出路：**检索式注入**（只放本次可能用到的 top-N 工具）、**分层描述**（一行摘要进常驻上下文，完整说明按需拉取，就是 Skill/MCP 的延迟加载思路）、**分组命名**（把同一领域的工具聚成一个入口，内部再分发）。description 关键是因为它是模型唯一的选型依据：模型看不到你的代码实现，只能靠这段文字判断「什么时候该用它、参数什么含义、什么时候不该用」。我写 description 的规矩是三段式——做什么、前置条件与输入约束、不适用场景，最后那段最能减少误用。

**追问预案**：description 写长了不是更膨胀？（是权衡：宁可对少数高频工具写详细，也别给全部工具写平庸描述；改动要过工具选择评测。）

**工程兜底要点**：工具名和参数名要语义明确，`query`/`do_it` 这类命名会显著提高选错率。

**Aster 挂钩**：`McpToolDescriptor.java` 是描述登记处；`TokenUsageService.java` 采样里带 `systemChars`，就是用来盯常驻上下文膨胀的。

### Q2.9 模型返回了不存在的工具名，或参数格式不对，怎么办？

**口述答案**：分层处理：**先硬校验**（JSON Schema：类型、必填、枚举、长度），失败不执行；**再纠错重试**——把结构化错误信息作为 tool 消息回灌，让模型改一次，这比直接报错的自愈率高；**再降级**——二次仍失败就回退到「无工具直答 + 明确告知无法完成」，或走预置兜底路径。不存在的工具名要区分是幻觉还是近似匹配：如果只有一个语义相近的合法工具，可以做受控纠正（并记录，因为这是描述歧义的信号），否则一律拒绝。

**追问预案**：有没有办法从模型层面减少？（约束解码/结构化输出、schema 更强的模型、或把高频参数改成枚举；后训练是最贵的一档，应用岗一般不到那步。）

**工程兜底要点**：所有拒绝与纠错都要落 trace 并统计「参数错误率」，它是工具设计质量的核心指标之一。

**Aster 挂钩**：集中预检在 `agent/hook/ToolGuardHook.java` + `capability/tools/ToolGuardPolicy.java`；`agent/hook/PlannedToolCall.java` 保存模型计划，便于比对「计划 vs 实际」。

### Q2.10 工具调用失败（API 超时、返回空）怎么处理？重试、降级、澄清怎么设计？

**口述答案**：先分类再决定：**瞬时错误**（超时、限流、5xx）走指数退避 + 抖动重试，重试次数和总预算受限；**确定性错误**（参数非法、资源不存在、无权限）不重试，直接改参数或告知用户；**语义空返回**（调用成功但没内容）最容易被误当失败，要作为 Observation 明确告诉模型「查询成功但无结果」，让它换策略而不是原样重试。降级是最后一层：换成更粗但可靠的数据源、或返回部分结果并标注缺失。如果任务本身依赖缺失信息，就**反问用户澄清**而不是硬编。

**追问预案**：失败后的 feedback 怎么设计才对模型最有用？（给可行动的语义——「这个城市没有地铁数据，可改用公交查询」比「HTTP 500」有用得多，但要避免把内部错误细节原样吐给用户。）

**工程兜底要点**：重试必须幂等；超时要有分层预算（单工具 < 单步 < 整个 run），只有单工具超时的系统会出现整体无限延长。

**Aster 挂钩**：检索侧的降级枚举是现成例子——`knowledge/retrieval/KnowledgeRetrievalStatus.java` 用 `SUCCESS/NO_HIT/TIMEOUT/OVERLOADED/FAILED` 区分五种情况，让上层分别处理而不是统一当失败。

### Q2.11 调用链条上如何保障故障容错和超时？高并发下的稳定性怎么设计？

**口述答案**：四个机制：**预算向下传递**（run 的剩余时间作为每次调用的超时上限，到点不再启动新调用）；**隔离**（每个外部依赖独立连接池与线程池，避免一个慢服务拖垮全部）；**背压**（有界队列 + 显式拒绝策略，队列满时报「未启动」而不是静默排队）；**熔断与降级**（连续失败短路该依赖，切到备用路径）。多 Agent 场景还要处理异步一致性：结果按子任务序号稳定排序再聚合，部分失败要能降级交付，父取消必须级联到子调用。

**追问预案**：为什么不能用默认线程池跑模型调用？（`common pool` 会被长时间阻塞 I/O 占满，且队列不可控；模型/网络调用必须用自己的有界 executor。）

**工程兜底要点**：`Future.cancel(true)` 只是请求中断，底层 HTTP/JDBC 得靠 connect/read 超时才真停——这是最常见的误判点。

**Aster 挂钩**：`WorkersNode.java` 用有界池 + 显式拒绝，Worker 用 `FutureTask` 支持按 conversation 取消；贯穿所有底层调用的统一取消上下文仍是缺口（notes §12）。

### Q2.12 如何保证 Agent 稳定输出结构化数据？

**口述答案**：按可靠性从低到高排：Prompt 里给 schema 和示例 → few-shot 加边界例子 → 原生 JSON/工具调用模式（模型侧已针对结构输出训练） → 后置解析与 schema 校验 + 一次纠错重试 → 把自由文本改造成**枚举选择**（能收敛成分类就别让模型自由生成）。最后一个技巧最有效：缩小输出空间。此外要明确处理「部分成功」——用固定字段承载缺失值而不是让模型省略字段，否则下游解析会分支爆炸。

**追问预案**：JSON 里出现多余字段或注释怎么处理？（宽容解析 + 归一化，并把该事件计入「格式违规率」指标，超阈值就换更强模型或改枚举。）

**工程兜底要点**：结构化输出不等于内容正确；schema 校验只保证形状，值仍要有范围校验和来源核验。

**Aster 挂钩**：`agent/graph/PlanJsonParser.java` 是典型实现——解析失败不抛死，而是回退为单个 general 任务，保证主链路不断。

## 二、Memory 与上下文工程

### Q2.13 Agent 的短期记忆和长期记忆分别解决什么问题？怎么存、粒度多少、怎么用？

**口述答案**：短期记忆解决「这一件事做得下去」——当前 run 的消息、工具结果、中间结论，存进程内或会话表，粒度是消息或步骤，随 run 结束清理。会话记忆解决「隔一会儿还能接着聊」——最近 N 轮原文加摘要，按 conversationId 存，粒度是一个 turn 或一段摘要。长期记忆解决「跨会话别重复问我知道的东西」——只存**原子事实**（偏好、约束、身份、既定决定），粒度是一条事实，不存对话片段；写入时带来源、时间和置信度。用的时候是**检索注入**而不是全量塞入：按当前意图检索相关事实，标注为「来自记忆，可能过期」。

**追问预案**：为什么不把历史全部塞长上下文？（成本、稀释、以及会把过时结论当事实——见 Q2.17。）有的面试官会按「感知记忆 / 短期记忆 / 长期记忆 / 实体记忆」四分法问，本质是同一套：感知对应原始输入与多模态嵌入，短期对应工作记忆，长期对应事实库，实体记忆是「人/物画像」这种结构化槽位——能把两套术语对齐就是加分项。

**工程兜底要点**：三种状态要物理隔离，混在一张表里迟早出现「A 用户的偏好注入到 B 用户」的越权事故。

**Aster 挂钩**：三层分别落在 `agent/graph/RunContext.java`（工作记忆）、`chat/memory/FileBasedChatMemory.java`（会话）、`chat/memory/MemoryService.java` + `agent/hook/MemoryInjectionHook.java` / `MemoryExtractionHook.java`（长期事实，异步提取注入）。

### Q2.14 记忆为什么常用向量库？embedding 和检索策略怎么设计？检索要不要分层？

**口述答案**：用向量库是因为记忆的触发是**语义的**而非键值的——用户不会提关键词，但意思相关就该召回。设计要点：每条事实单独 embed（短文本语义更干净），metadata 带租户/用户/类型/时间/来源会话，检索必须**先按权限过滤再算相似度**，顺序反了就是数据泄露。召回可以放宽 top-K 再加时效与类型加权（近期偏好权重更高），最后过一层 rerank 或规则筛选。检索要分层：先查「硬约束」（用户明确说的、合规相关的）全量注入，再查「软偏好」按需 top-N，两类混在一起会导致硬约束被挤出。

**追问预案**：向量检索会不会召回错记忆？（会，这是主要风险之一；所以注入时要带来源与置信度，且敏感事实走规则匹配而不是语义匹配。）

**工程兜底要点**：记忆的写入率要比读取率更保守——宁可少记，错记的清理成本远高于漏记。

**Aster 挂钩**：长期事实按租户/Agent/用户范围查询并带来源会话；提取开关默认关闭，这本身就是「写入要保守」的体现。

### Q2.15 Memory 和 RAG 的区别是什么？能不能用 RAG 去检索 Memory？

**口述答案**：机制上两者都是「检索后注入」，所以确实可以用同一套向量检索实现——工程上我常复用 RAG 基础设施。区别在**数据来源和生命周期**：RAG 检索的是相对稳定的共享知识库（文档、条目），多人复用、由内容方维护；Memory 检索的是**由交互产生、随时间失效、且强绑主体身份**的私有事实。因此三个差异必须处理：写入方不同（模型自动抽取 vs 人工维护）、权限不同（个人隔离 vs 租户共享）、时效不同（会过期冲突 vs 版本化更新）。把记忆当知识库做，最常见的事故是越权和过期事实长期生效。

**追问预案**：那哪个先做？（看产品：知识密集型问答先 RAG，个性化助手先 Memory。）

**工程兜底要点**：两者共用检索管道，但必须分开命名空间与过滤条件，不能共表混查。

**Aster 挂钩**：本项目知识库是租户级共享（`knowledge/retrieval/AgentKnowledgeRagService.java`），记忆是用户级私有（`chat/memory/MemoryService.java`），两套过滤条件独立。

### Q2.16 Agent 的记忆压缩通常有哪些方法？压缩阈值怎么确定？

**口述答案**：四类方法：**滚动摘要**（把旧对话压成一段事实性摘要，最常用）、**结构化抽取**（转成槽位/字段，如「目的地=大阪、预算=5000」，压缩率最高且可校验）、**分层保留**（目标与约束常驻，中间过程近期保留、远期只留指针，全文用引用 ID 回查）、**遗忘/淘汰**（按时间、访问频次、重要性打分丢弃）。阈值确定不能只看 token：我会按「模型窗口 − 本轮预期输出 − 工具结果预留 − 安全余量」倒推触发点，并且**按内容类型设不同优先级**——工具原始输出一律先压，用户明确约束永不压。压缩本身用便宜模型或规则做，别每次全量重算，否则压缩比省下的还贵。

**追问预案**：压缩把关键信息压丢了怎么发现？（做「压缩前后能否回答原问题」的对照评测，或保留原文引用便于回查。）

**工程兜底要点**：压缩要有幂等和版本，同一会话反复压缩会累积漂移，越压越离谱。

**Aster 挂钩**：`agent/hook/MemoryCompressionHook.java` 负责历史压缩，`ToolResultTruncationHook.java` 负责工具结果截断——两条膨胀源分别处理，这个分工值得强调。

### Q2.17 记忆过期、衰退、冲突怎么处理？如何避免记忆污染上下文？

**口述答案**：治理靠元数据而不是靠模型自觉：每条事实带**时间戳、来源、置信度、类型（偏好/约束/事实）**。过期用 TTL 或「同类新值覆盖旧值」；衰退用访问频次与时间衰减给检索打分，让近期高频记忆优先召回；冲突要显式检测——同类别出现互斥值时不静默选择，而是触发一次澄清或标注「存在冲突、以最新为准」。防污染的三条硬规矩：记忆内容进上下文必须加**来源标记**且明确它是数据不是指令（否则成为 Prompt Injection 的持久化通道）；用户纠正过的旧事实要立刻失效；被抽错的事实要能被删除。

**追问预案**：怎么实现「记忆衰退」才不丢关键信息？（衰退只作用于检索排序，不作用于删除——召回不到但没删，随时能找回。）

**工程兜底要点**：长期记忆最大的风险不是召回不准，而是**错误事实的持续放大**——一次抽错，后续每次都带着它。

**Aster 挂钩**：抽取注入已有，但用户查看/编辑/删除与时效治理尚未形成完整产品路径，这我在 notes §12 明确列为缺口，面试时如实说。

### Q2.18 长期记忆怎么避免抽错事实？用户治理闭环该怎么做？

**口述答案**：抽取只认**明确表达**：「我不吃香菜」「我叫小王」这类第一人称直述才写；从行为推断的偏好（连续三次查机票就判定「常出差」）默认不写或标低置信度。写入前做四类过滤：敏感信息（证件号、健康、住址）不落长期记忆；无来源不写；同值去重；与已有事实互斥时不覆盖而先标记冲突。治理闭环是产品能力不是算法能力：用户要能查看、修改、删除记忆条目；账号注销或数据导出时必须级联删除并记录审计；每条记忆要能回答「这条从哪来、什么时候」。

**追问预案**：没有治理闭环会有什么后果？（合规风险 + 用户信任崩塌；一条错误记忆会让助手长期「发疯」且无法解释。）

**工程兜底要点**：默认关闭抽取、按租户可开，是把风险前移到产品决策的正确做法。

**Aster 挂钩**：`MemoryExtractionHook.java` 只做异步提取、开关默认关闭，正是「保守写入」的实现选择。

### Q2.19 上下文工程是什么？核心问题有哪些？最关键的工作是什么？

**口述答案**：上下文工程是**在有限窗口内决定放什么、以什么顺序放、放多少**的系统工程。核心问题四个：稀缺（token 预算）、相关性（放进去的是不是有用信息）、结构（指令与数据的优先级层次是否清晰）、时效（信息是否过期）。最关键的一件事我认为是**信噪比管理**：多数 Agent 效果差不是因为模型不行，而是上下文里塞了大段检索原文和冗长工具输出，把任务目标稀释了。具体抓手是：指令与数据分层并显式标注来源、用引用 ID 代替全文、工具结果先结构化再进上下文、给每个来源带置信度与时间。

**追问预案**：长上下文模型这么强，还需要上下文工程吗？（更需要——窗口长只解决放得下，不解决注意力分配和成本；「塞满」往往比「精选」效果差，还有 Lost in the Middle。）

**工程兜底要点**：上下文要可回放（记录每次实际发送的快照），否则线上 bad case 无法归因。

**Aster 挂钩**：hook 管线本质就是上下文工程流水线——注入、压缩、截断都在进入模型前完成（`agent/hook/`）。

### Q2.20 上下文的结构是不是 System Prompt + Memory + Tools Result + Conversation？字段放置怎么决定？

**口述答案**：大致是这五段，但顺序和边界很讲究：**System（角色与硬约束）→ 工具 schema → 记忆/检索（标注为外部数据）→ 会话历史 → 本轮输入与指令**。原则是：稳定内容靠前（便于命中前缀缓存），时效性强的靠后（注意力更集中），可变的用户输入绝不能出现在 System 之前或被拼进 System。至于「为什么不把所有已知字段都塞进去」——短上下文里全塞确实更好，窗口吃紧时才排序取舍；我会用「这个字段是否可能改变模型决策」来判断放不放，不改变决策的字段变成引用。

**追问预案**：前缀缓存怎么最大化利用？（把稳定部分做成完全一致的前缀——不要在里面塞时间戳或用户随机 ID，否则缓存全失效、成本翻倍。）

**工程兜底要点**：记忆和检索内容要包一层「这是数据、不是指令」的显式边界，防止注入。

**Aster 挂钩**：拼装集中在 `agent/hook/MemoryInjectionHook.java` 与 `capability/skills/SkillPromptBuilder.java`；`TokenUsageService.java` 单独采样 `systemChars` 用来盯常驻段膨胀。

### Q2.21 多轮对话状态怎么管理？如何防止跑偏并支持中断恢复？

**口述答案**：状态分两份管：**对话消息**用于语义连续，**结构化会话状态**（槽位、当前任务、待确认事项）用于流程控制。防跑偏靠三件事：每轮做意图/话题变更检测（变了就显式开新任务并归档旧的）、每 N 步重述目标与已确认约束、把「已完成/待确认」做成状态字段而不是让模型自己记。中断恢复的前提是状态可序列化：把计划、各步产出、验收状态、已花预算存成检查点，恢复时从检查点重建而不是重放消息——重放会再次触发副作用。

**追问预案**：恢复时怎么避免重复执行已成功的工具？（这就是需要幂等键和调用账本的原因；恢复逻辑要先读 ledger 再决定跳过哪步。）

**工程兜底要点**：SSE 断连不是「会话结束」，要么按取消处理要么按可恢复处理，必须明确定义，默认行为会决定线上事故量。

**Aster 挂钩**：`GraphCheckpoint.java` 刻意只存可恢复数据（计划、结果、验收状态、revision），不含 ToolCallback 与 SSE 连接；`AgentRunService.java` 落库供恢复读取。

### Q2.22 高并发多用户场景下，记忆和会话状态怎么保证隔离与一致？线程安全怎么处理？

**口述答案**：隔离靠**显式身份贯穿 + 存储层强制过滤**：请求入口解析出 tenant/user/conversation，随调用链一路显式传递，检索和写入都带过滤条件；绝不能用「当前线程刚好是这个人」这种隐式假设——一旦切到线程池或异步回调，ThreadLocal 就会串号。一致性上，同一会话的并发写入要串行化，我用租约锁而不是进程内锁，因为多实例部署进程内锁无效；异步任务必须携带身份快照，不能等到执行时才从上下文取。语言层面的坑要主动说：Java 里模型调用是阻塞 I/O，不能用 `common pool`，也不能指望 `InheritableThreadLocal` 跨 executor 生效。

**追问预案**：锁用 Redis 还是数据库？（我这边用 PostgreSQL 租约：锁键含租户/用户/Agent/会话，token 条件释放并定时续期；好处是和业务数据同库、不需要额外组件，代价是库长时间不可用时续租会失败、租约到期仍有并发窗口，需要监控续租失败并做多实例演练。）

**工程兜底要点**：把「LangChain 默认 memory 在多用户下会串」这类框架陷阱讲出来，说明你真做过并发。

**Aster 挂钩**：身份在 `platform/security/CurrentActor.java`；会话锁已改为 PG 租约（`chat/conversation/ConversationLockManager.java`），实例侧有心跳与租约接管（`chat/conversation/ApplicationInstanceRegistry.java`），见 notes §12 第 4 条；进程内 `MemorySaver` 只用于图内状态，不承担跨实例一致性。

### Q2.23 上下文超预算被截断，怎么决定截断长度？哪些内容永远不能丢？

**口述答案**：截断不按「保留最近 N 条」一刀切，而是**按内容重要性分级**：任务目标、用户明确约束、已确认的关键结论、外部系统的 ID 永不丢弃；工具原始输出、网页正文、已被后续结论取代的中间推理优先丢或替换为引用。长度选择要留安全余量（预期输出 + 下轮工具结果），并按模型窗口和成本一起算。另外「为什么不干脆把这些字段都塞进去」——能塞就塞是对的，只是塞的边际收益会递减，我用一次对照实验决定，而不是靠感觉。

**追问预案**：截断导致模型重复调用同一工具怎么办？（保留「已调用清单」这种结构化摘要，比保留原文更有效也便宜。）

**工程兜底要点**：截断要有可观测事件——记录本次丢了什么、为什么，出 bad case 才能归因到「上下文被砍了」。

**Aster 挂钩**：截断集中在 `ToolResultTruncationHook.java`（大小）与 `MemoryCompressionHook.java`（历史），二者可独立开关和调参。

## 三、RAG

### Q2.24 讲一下 RAG 的完整链路，离线和在线分别包含哪些步骤？

**口述答案**：离线（索引）：数据接入 → 解析与清洗（版面、表格、图片 OCR、噪声）→ 结构化分块 → 元数据补齐（来源、版本、权限、时间）→ embedding → 入库建索引。在线（检索生成）：query 理解与改写 → 多路召回（向量 + 词法）→ 过滤（权限、版本、时效）→ 去重 → 重排 → 上下文组装 → 生成 → 引用校验与溯源 → 兜底判定。两个阶段的责任要分清：索引阶段决定「能不能被召回」，检索阶段决定「召回得准不准」——大多数效果问题的根因在索引侧，但大家第一反应都是去调检索参数。

**追问预案**：整条链路你改哪一段收益最大？（我的答案是解析与分块：垃圾进垃圾出，且比换 embedding 便宜。）

**工程兜底要点**：过滤必须在 rerank **之前**执行——先精排再按权限筛，会出现「有权重的文档被排除后凑不满结果」的隐性错误。

**Aster 挂钩**：`knowledge/retrieval/AgentKnowledgeRagService.java` 的注释就是这个原则——「版本有效性过滤（必须先于 rerank）→ 向量召回 → 逻辑文档去重 → 重排序精排」。

### Q2.25 RAG 和微调怎么选？为什么不用 GraphRAG / 为什么不用现成方案？

**口述答案**：RAG 解决「模型不知道」，微调解决「模型不擅长这么答」。选 RAG 的理由：知识可日更、答案可溯源、权限可控、成本低、上线快。选微调的场景：稳定输出格式或风格、领域术语与语气、要压缩推理成本、以及需要提升的是**能力而非知识**。实践中常见组合是「RAG 供事实 + 轻量微调定风格/工具调用格式」。至于「为什么不用 GraphRAG/为什么不用框架」——我按问题规模决策：图谱构建与维护成本高，只有当问题真的是多跳关系（实体关联、跨文档推理）时才值得；召回量小、文档结构清晰时朴素向量 RAG 更便宜可控。

**追问预案**：怎么证明你的选择更优？（做消融：同一评测集上比朴素 RAG / 加 rerank / 加图谱三档的 Recall 与成本曲线。）

**工程兜底要点**：别把「不用框架」说成嫌框架不好，要说「框架的上下文拼装我改不动，而这段正是效果瓶颈」。

**Aster 挂钩**：本项目是租户级知识库 + 向量（pgvector）+ rerank，没有上图谱；解析侧自建 `DoclingServeChunkingService.java`，属于「重索引」投入。

### Q2.26 文档分块怎么切？长度、overlap、语义切分怎么定？中文要注意什么？

**口述答案**：我会先按**文档结构切**（标题、段落、表格、代码块、列表），再在超长节点内做定长兜底，而不是无脑按字数滑窗。长度取「能独立表意、且检索时语义不混杂」的粒度，实践中中文 300–800 字是常见区间，但真正决定的是：一块里如果同时讲两件事，召回时必然被稀释。overlap 的作用是保住跨块句子的完整性，通常给到块长的 10–20%，或者更好的做法是**保留标题路径作为前缀**（比盲目重叠有效）。中文的坑：分句要按中文标点而不是空格；定长切分容易切在词中间，词法检索（BM25）效果会变差，所以中文场景要配分词器或 jieba 类预处理；全角/半角与中英混排要在清洗阶段归一。

**追问预案**：`RecursiveCharacterTextSplitter` 的实现逻辑？（按分隔符优先级递归切分——先段落、再句子、再字符，切不动才硬切；它不理解语义，所以结构信息要靠元数据补。）

**工程兜底要点**：入库时要保存 chunk 序号、父文档 ID、标题路径、版本、权限，否则无法做去重、溯源和增量更新。

**Aster 挂钩**：分块交给外部 Docling 服务（`DoclingServeClient.java`），并保留 `chunkIndex`（`AgentKnowledgeChunk.java`）做逻辑文档去重与预览。

### Q2.27 非 Markdown 的文档（PDF、表格、图片）怎么处理？解析质量为什么重要？

**口述答案**：流程是：版面还原（标题层级、段落边界、表格、页眉页脚剔除）→ 图片走 OCR 或视觉模型转文本 → 清洗噪声（重复水印、断行、乱码）→ 补元数据（页码、章节、来源）→ 再切块。表格是最难的一类：转成纯文本会丢结构，我会保留为 Markdown 表格或「行转句」两种形态之一并做对照实验。PDF 的坑集中在公式、脚注和跨页表格——LaTeX 解析不完整时，做法是保留原始图片并让视觉模型生成描述，同时把原文以引用形式存下来，而不是硬凑一段错误文本。解析质量决定上限：后面所有检索优化都建立在「块本身是完整可表意的」这个前提上。

**追问预案**：为什么 MinerU/Docling 这类解析质量好？（它们做版面分析 + 阅读顺序重建 + 表格结构识别，是「文档理解」而不是「抽文本」；代价是慢、需要独立服务、解析失败要有回退路径。）

**工程兜底要点**：解析要有可观测的失败状态（文档级 `errorMessage`、chunkCount），并且支持重新解析而不污染已有索引。

**Aster 挂钩**：解析链路就是自建例子——`DoclingDocumentPreprocessor.java`、`HtmlTableParser.java`、`DocumentParsingModule.java`；索引恢复有 `AgentKnowledgeIndexRecoveryJob.java`；细节见仓库 `docs/pdf-parsing.md`。

### Q2.28 Embedding 模型怎么选？评价好坏用什么指标？相似度距离有哪些？

**口述答案**：选型看四点：**语种匹配**（中文必须看 C-MTEB 而不是 MTEB 英文版）、**领域适配**（法律/代码/医疗通用模型明显偏弱）、**维度与成本**（维度影响存储和检索延迟）、**是否支持长文本**（截断会让长块语义漂移）。评估不能只看公开榜单：我会用自己业务抽的 200–500 条「query—正确文档」对，测 Recall@K / MRR，再上生产前做 A/B。距离度量：余弦最常用（对归一化向量与点积等价），内积适合未归一化模型，欧氏距离对模长敏感。要注意**阈值必须随模型标定**——换 embedding 模型后原来的相似度阈值全部失效，这是最常见的静默劣化。

**追问预案**：要不要微调 embedding？（领域术语差异大、且已有标注数据时才值得；一般先用 rerank 补足精度，成本更低。）

**工程兜底要点**：向量模型更新要重建索引并双跑对比，不能热替换——不同模型的向量空间不可比。

**Aster 挂钩**：向量库配置在 `knowledge/document/AgentKnowledgeVectorStoreConfig.java`（pgvector），检索参数 `topK` / `similarityThreshold` 是可配置项，便于按模型重新标定。

### Q2.29 稠密检索、稀疏检索、混合检索分别是什么？BM25 的原理和局限？

**口述答案**：稠密（向量）检索把语义压成向量算相似度，能处理同义改写和概念相关，弱点是对**精确匹配**很差——型号、法条号、人名、代码符号容易被召回近义项；稀疏（BM25/倒排）基于词频、逆文档频率和长度归一化打分，精确匹配强、可解释、便宜，但完全不懂同义词。所以生产上我做混合召回再统一重排：两路各出候选，先按文档去重，再用 rerank 模型统一打分。BM25 要能说出公式的三个部件（TF 饱和、IDF、长度归一化参数 k1/b），并说明它相比 TF-IDF 的改进在于词频饱和——一个词出现 20 次不该是出现 2 次的 10 倍相关。

**追问预案**：中文怎么用好 BM25？（必须分词；或改用字符 n-gram 索引绕开分词依赖。）

**工程兜底要点**：两路召回的分数不可直接比较，一定要过统一 rerank；简单加权求和会随阈值漂移。

**Aster 挂钩**：双路是现成实现——`AgentKnowledgeRagService.java` 里 `vectorPool` 与 `lexicalPool` 合并后交给 `DashScopeRerankService.java`，trace 分别记录向量与词法候选数与耗时。

### Q2.30 重排序（Rerank）怎么做？为什么有效？成本和延迟怎么权衡？

**口述答案**：召回阶段用双塔式向量检索追求**快而全**（query 和文档各自编码，可预计算），rerank 阶段用 cross-encoder 把 query 和候选拼在一起做一次完整注意力计算，因而能捕捉词级交互，精度高但不能预计算。典型配置是召回 20–50 条、精排到 3–5 条。它最能解决的是「语义相近但答非所问」的问题。成本上 rerank 是一次外部调用，几十条候选增加几百毫秒到一秒，所以我按场景开关：问答类开、高频短查询类可关或改用更小的模型。另一个要点是 rerank 分数要落到 trace 里，因为它给了「相关性」的连续信号，做阈值和兜底判定比向量分数可靠。

**追问预案**：除了 rerank 还怎么提精度？（查询改写、子问题分解、多路召回、按元数据过滤、上下文组装时排掉低分块。）

**工程兜底要点**：精排服务必须有超时降级——rerank 挂了要能回退到召回顺序，而不是整条链路 500。

**Aster 挂钩**：`DashScopeRerankService.java` 返回可选结果（`Optional<List<RerankHit>>`），失败时 `RetrievalOutcome.reranked=false` 保留原始顺序，降级路径是显式设计出来的。

### Q2.31 Query 改写有哪些方式？意图识别要不要单独做？

**口述答案**：常用五类：**纠错与归一**（口语转规范表述）、**指代消解**（把「它/上面那个」用会话状态补全，多轮场景收益最大）、**扩展与同义改写**（提升召回，但会引入噪声）、**压缩**（去客套留信息核）、**分解**（复杂问题拆成多个子查询分别召回再聚合）。意图识别我建议单独做一层，不要用大模型裸判：FAQ/知识问答/工具调用/人工转接这四类分流，用规则 + 小分类模型足够且延迟低、可控可解释，大模型只兜长尾和歧义。做分类时 Zero-shot 适合冷启动，标注少就用 few-shot + 严格输出枚举 + 置信度阈值，低于阈值转澄清或人工。

**追问预案**：改写会不会反而变差？（会，改写必须可评测——固定 query 集对照「原样检索 vs 改写检索」的 Recall；线上按意图分桶看，不是整体一个均值。）

**工程兜底要点**：改写后的 query 和原 query 都要留痕，否则 bad case 无法判断是谁的锅。

**Aster 挂钩**：意图分类评测集已建：`evaluation/eval-sets/knowledge-intent-eval-v1.json` + `run_baseline.py`，这是「分类层可回归」的具体证据。

### Q2.32 什么是 Lost in the Middle？怎么缓解？RAG 有噪声怎么办？

**口述答案**：指模型对长上下文**首尾注意力强、中间信息利用率显著下降**，表现为把强相关的块放在中间等于没放。缓解手段：控制注入块数（3–5 块比 10 块好）、把最相关内容放开头或结尾、每块带清晰标注（来源、序号）帮助定位、长文档改成先摘要再追问的两段式。噪声治理要分层：检索侧收紧阈值和 rerank 过滤、组装侧做去重与截断、生成侧要求**逐条引用**并允许回答「依据不足」。最有效的单一手段其实是降低注入量——多数 RAG 幻觉来自给了 8 块其中 5 块无关。

**追问预案**：怎么验证「塞更多上下文确实更差」？（同一评测集跑 3/5/8 块的对照，看忠实度和答案正确率而非流畅度。）

**工程兜底要点**：忠实度（答案是否被引用支持）要作为独立指标自动检查，而不是等用户投诉。

**Aster 挂钩**：本项目注入前做了逻辑文档去重 + 阈值过滤（`AgentKnowledgeRagService.java`），指标侧有 `RagEvaluationMetrics.java` 承载。

### Q2.33 RAG 召回效果差怎么定位？你的排查顺序是什么？

**口述答案**：我按数据流从后往前二分：**先看是不是索引里根本没有**——拿标准答案的原文去库里精确查，查不到就是数据/解析问题，不用再看检索。有原文的话看 trace：正确块有没有进向量召回？没有说明 embedding 或分块问题（语义漂移、块太长）。进了召回但没进精排？说明 rerank 或候选截断问题。进了精排但答案还是错？那就是组装或生成问题（阈值太松塞了无关块、Prompt 没有约束必须引用）。整条链路必须有分阶段候选快照才排得动，只看最终答案的 RAG 系统基本等于黑盒调试。

**追问预案**：优先检查 Embedding、Chunk、Query Rewrite、Hybrid 还是 Rerank？（按上面顺序：Chunk/解析 → 召回 → 精排 → Prompt。多数团队先动 Rerank，其实是错的方向。）

**工程兜底要点**：评测集要按「失败类型」打标（无命中/命中错块/有块但答错），修一类指标才看得出一类问题。

**Aster 挂钩**：`RagRetrievalTrace.java` + `RagTraceCandidate.java` 记录了双路候选数、各阶段耗时与最终是否 rerank——这题我可以直接讲一次真实定位过程。

### Q2.34 知识库怎么动态增量更新？新旧文档分布不一致、时间衰减怎么处理？

**口述答案**：更新以**文档为版本单位**：新版本写入并标记生效，旧版本立即从检索过滤中下线但保留一段时间便于回滚，避免「同一问题召回到新旧两版」。避免分布不一致的关键是**别混用不同 embedding 模型的向量**：模型升级就全量重建索引并双跑对比。时间衰减要区分场景——新闻、公告类需要按时间加权；法规、手册类不能因为「旧」就降权，过期与否应由显式生效日期决定而不是发布时间。所以我会把「时效」做成元数据规则（生效期、失效期）而不是全局相似度惩罚项。检索不到时的兜底要有分层：换策略检索一次 → 外部搜索（标注为外部来源）→ 明确拒答并说明知识边界，绝不混着答。

**追问预案**：更新延迟能接受多少？（取决于 SLA：公告类分钟级可用增量写入，全量重建只在换模型时做，并配恢复任务。）

**工程兜底要点**：必须有「索引落后」的监控指标（未索引文档数、最近索引时间），否则知识库悄悄过期是发现不了的。

**Aster 挂钩**：索引恢复有 `AgentKnowledgeIndexRecoveryJob.java`；检索侧的「版本有效性过滤先于 rerank」就是这套规则的落地。

### Q2.35 什么时候该用 GraphRAG / 知识图谱？图谱怎么保证更新实时性？

**口述答案**：值得上图谱的信号很具体：问题**多跳**（A 投资了 B，B 的子公司做什么）、需要**关系聚合**（某实体的一度关系全貌）、或者需要**跨文档消歧同名实体**。单跳事实问答用图谱是负收益——构建慢、抽取错一个三元组就错一片、更新成本高。工程上我会用混合方案：向量负责文档级召回，图谱负责关系扩展。实时性上，图谱不能全量重建，要做**增量三元组 + 版本戳**，抽取管道异步跑并留审核；最大风险是抽取错误传播，所以三元组必须带来源引用，允许按来源一键失效。

**追问预案**：图谱抽取质量怎么评？（抽样人工标注三元组的准确率与召回率，并统计多跳问题上的答案正确率提升幅度——不提升就别维持。）

**工程兜底要点**：图数据库的运维成本和查询不可控是常被低估的坑，说清「我为多跳收益付出的代价」。

**Aster 挂钩**：本项目没有上图谱，是明确取舍（知识库规模和多跳需求都不足以支撑），如实回答比硬凹好。

### Q2.36 什么是 Agentic RAG？它和普通问答里的 RAG 有什么区别？

**口述答案**：普通 RAG 是「检索一次然后生成」的固定管道；Agentic RAG 让模型参与检索决策——要不要查、查什么、查完够不够、要不要换关键词再查、要不要调用精确查询工具替代模糊检索。区别有三：检索次数动态、query 由模型生成、结果质量由模型自评。收益明显的是复杂问题（需要多次不同侧面的检索）和知识库覆盖不全的场景（先搜内网再搜外网）。代价也要讲：延迟从一次检索变成 N 次、失败模式变成「模型反复查不到就乱猜」，所以要设**最大检索次数**和「检索无果则拒答」的硬规则。

**追问预案**：什么时候不该用 Agentic RAG？（意图单一、库小而干净的场景，固定管道更快更稳也更便宜——这句话最能体现工程判断。）

**工程兜底要点**：每次检索都要进 trace 与成本核算，多轮检索的成本很容易被低估到 3–5 倍。

**Aster 挂钩**：超级 Agent 里 Worker 可反复调用检索与搜索工具，就是 Agentic RAG 形态；普通业务 Agent 走固定一次检索，正好说明两档差异。

### Q2.37 怎么评估一个 RAG 系统？指标怎么设计？评估集怎么建？

**口述答案**：分两段打分。**检索侧**：Recall@K（正确块进没进前 K）、MRR/NDCG（排位是否靠前）、命中率与空召回率。**生成侧**：忠实度/接地性（答案是否被引用支持）、答案相关性、引用正确率、拒答合理率（该拒的时候有没有硬编）。另外两个工程指标常被漏：**端到端延迟**（分位数，不是均值）和**单问成本**。评估集建设最有性价比：从真实 query 抽样 + 人工标注正确块和标准答案，100–300 条就能显著指导迭代；按意图分桶看指标，整体均值会掩盖某一类崩塌。LLM-as-judge 可以打忠实度，但必须定期与人工标注对齐（算一致性），否则只是把幻觉换了个地方。

**追问预案**：上线后怎么持续评？（线上采样回流成 bad case 集，每次改动过回归门禁；同时看转人工率和用户纠错率这两个真实信号。）

**工程兜底要点**：评测集要版本化、要有从未参与调参的盲测集，防止把阈值调到过拟合。

**Aster 挂钩**：`RagEvaluationMetrics.java` + `evaluation/eval-sets/`（含 `baseline-2026-10-26-r2.json` 这类基线快照和 `run_baseline.py`）是「评测集驱动迭代」的落地证据。

### Q2.38 搜索引擎和 RAG 是什么关系？调用外部搜索时如何避免无关结果污染回答？

**口述答案**：RAG 是「取回内容 → 注入 → 生成」，搜索系统追求召回率、排序和相关性，所以 RAG 的检索环节本质上就是一个搜索问题，可以直接复用倒排、向量、rerank 那套。和外部搜索的结合要注意三点：一是**来源可信度分级**（官方站点、垂直站、UGC 内容要区别对待并带权），二是**时效与去噪**（搜索结果里的 SEO 垃圾文要过滤，抓取失败和正文为空要区分），三是**归因**（必须给外部来源链接，且和内部知识库来源分开标注）。我会把「外部搜索结果」显式标记为低信任上下文，要求模型说明它来自外部。

**追问预案**：什么时候只搜一次、什么时候多次？（意图单一一次即可；比较类/多实体类需要按子问题分别搜，用最大次数限制成本。）

**工程兜底要点**：搜索结果的抓取要走受控出口（SSRF、大小、超时、重定向逐跳校验），别把「抓网页」当成无害操作。

**Aster 挂钩**：`capability/tools/WebSearchTool.java` + `WebScrapingTool.java` 是能力面，`UrlAccessPolicy.java` 是出网校验，两者分离正好说明「能力」与「策略」分层。

## 四、存储与性能

### Q2.39 PGVector、Elasticsearch、MySQL 在 Agent 系统里怎么分工？倒排索引解决了什么问题？

**口述答案**：MySQL/PostgreSQL 存**业务主数据**——会话、消息、文档元数据、审计、租户权限，它要的是事务和一致性。向量检索选 PGVector 的场景是数据量在千万级以下、且希望和元数据同库做过滤（权限条件 + 相似度一次查完，运维只维护一个存储），需要更大规模和更强混合检索时再上专业向量库或 ES。ES 的强项是全文检索、分布式、聚合分析，混合召回方案里常承担词法那一路。倒排索引解决的问题是「在亿级文档里找含某词的文档」这件事不能靠顺序扫描——它把词映射到文档列表，把匹配复杂度从数据量降为词 posting 长度。

**追问预案**：PGVector 用 IVFFlat 还是 HNSW？（HNSW 查询快、召回高但建索引慢、内存占用大；IVFFlat 建库快、需要预热聚类。数据量小或写多读少时甚至可以先用暴力扫描。）

**工程兜底要点**：向量与业务数据同库的最大收益是**权限过滤和向量检索原子化**——避免「先粗召回再回业务库鉴权」导致的结果数不足。

**Aster 挂钩**：本项目就是 PG + pgvector 单库路线（`AgentKnowledgeVectorStoreConfig.java`），检索带 `tenantId/agentKey` 过滤表达式，是这个取舍的直接例子。

### Q2.40 高并发的检索问答系统，召回和生成阶段的延迟怎么优化？

**口述答案**：召回侧：**两级缓存**（本地 L1 + Redis L2，键含 query 归一化和版本，命中直接返回）、语义缓存（相近 query 复用已验证答案，但要设相似度阈值并防串题）、热数据常驻、索引调优与候选数控制。生成侧：流式输出把首字延迟做小（SSE）、批量合并小请求、模型分级（简单意图走小模型或缓存）、限制输出长度、把 rerank/校验做成可降级旁路。**架构层**：连接池隔离、超时预算、熔断降级和队列有界，避免一个慢依赖把所有线程占住。成本侧我还会加 token 记账，因为它才能暴露「哪些意图在烧钱」。

**追问预案**：缓存穿透和击穿怎么防？（穿透用空值短 TTL + 布隆过滤；击穿用单飞/互斥重建 + 过期错峰；雪崩用 TTL 加抖动。）

**工程兜底要点**：语义缓存在 Agent 场景要格外小心——带上下文的请求不能跨会话复用，否则 A 的答案出现在 B 的对话里。

**Aster 挂钩**：SSE 流式在 `web/controller/AiController.java`，检索侧耗时在 `RagRetrievalTrace` 里分段可观测，token 成本在 `agent/observability/TokenUsageService.java`。

### Q2.41 大模型或 Agent 连数据库时，如何防越权、敏感数据泄漏和查询幻觉？

**口述答案**：**权限**：数据库账号按角色最小授权（只读账号、限定 schema 与表），连接串由服务端保管，模型只能提供查询意图不能提供凭据；SQL 生成后必须过策略校验——只允许 SELECT、禁止多语句与系统表、必须能解析出访问表并在 allowlist 内、强制 LIMIT 和超时。**泄漏**：结果进入上下文前做字段级脱敏，敏感列（身份证、手机号、金额）默认不出库；返回行数与大小限制，审计记录只存脱敏摘要。**查询幻觉**：模型会编不存在的表名和字段，所以要给它**受控 schema 视图**（只暴露它被允许看的表和列注释），并把「表不存在/无权限」的错误回灌成可行动提示；答案要求附最终执行的 SQL 供核对。

**追问预案**：只读账号是不是就够了？（不够——只读也能全表拖数据，必须有行数上限、超时和出网控制。）

**工程兜底要点**：SQL 注入防护要放在解析层而不是字符串匹配；用 AST 解析判断语句类型和涉及表，才谈得上可信。

**Aster 挂钩**：`capability/tools/DatabaseQueryTool.java` 与 `ExternalDatabaseQueryTool.java` 分别处理内外部库，外部库在连接前做公网地址校验；但「资源级细粒度授权」我仍列为缺口（notes §12 第 8 条）。

### Q2.42 RAG 的知识库是静态的还是动态的？结束语、招呼语这类场景要不要检索？

**口述答案**：真实系统基本都是动态的，所以必须有「未索引/索引中」状态和可观测指标，否则用户会以为知识库是权威的其实是旧的。至于要不要检索：**先做意图门控**。寒暄、感谢、确认这类不检索（省一次延迟和成本，还能避免把无关文档塞进上下文造成污染）；FAQ 走模板；知识类和需要精确数据的走检索或工具。门控用小模型或规则就够，不要每次都用大模型判断。这个「按意图分流」的设计其实是所有问答系统的第一层架构。

**追问预案**：门控判错怎么办？（宁可多检索一次也别漏——漏检索会让用户看到幻觉，多检索的代价只是延迟，两个错的代价不对称。）

**工程兜底要点**：门控本身要能评测（用意图标注集算准召），不然它是整条链路最隐蔽的失效点。

**Aster 挂钩**：`KnowledgeRetrievalStatus.NO_HIT/OVERLOADED` 等状态让上层可以区分「检索不到」和「服务过载」，配合意图门控做不同降级。

### Q2.43 RAG 上线后 bad case 怎么收集、怎么迭代？有没有在线学习？

**口述答案**：收集渠道四个：用户显式反馈（点踩、追问「不对」）、转人工/放弃信号（同一问题反复问或换措辞重试）、抽样人工审核（每天固定条数按意图分层抽）、以及自动检查（低 rerank 分数、无引用、拒答率突增）。迭代闭环是：bad case → 归因分类（无数据/未召回/召回错块/生成错）→ 对应修复（补文档、改分块、调阈值、改 Prompt）→ 进评测集回归。在线学习我谨慎——把反馈直接用于更新模型或自动改 Prompt 风险太大（用户可能教坏它，还会被注入），更稳的是**离线批量**：攒够一批再评再发版，并保持每次改动可回滚。

**追问预案**：怎么衡量迭代是否真的有效？（基线快照对比：同一评测集上版本间的 Recall@K、忠实度和端到端成功率，而不是「看起来改好了」。）

**工程兜底要点**：bad case 集比评测集更宝贵——它代表真实分布，要版本化保存并防止泄漏进训练/Prompt。

**Aster 挂钩**：`evaluation/eval-sets/` 里带日期的 baseline JSON 就是这个回归机制，`AgentKnowledgeReviewLogService.java` 承担知识侧的人工审核记录。

### Q2.44 智能客服这类场景的完整链路怎么设计？

**口述答案**：第一层是**问题分类分流**：FAQ 走模板直答，知识类走 RAG，查订单/物流/账户走工具调用（带鉴权），高风险或低置信度走人工转接。第二层是**上下文与身份**：会话归属、租户隔离、历史与工单信息注入。第三层是**回答质量控制**：引用必须存在、敏感承诺（赔付、时效）走规则校验而不是模型生成。第四层是**兜底与观测**：拒答与转人工阈值、满意度与转人工率指标、bad case 回流。这套设计的核心思路是**按风险分层用模型**——能用规则和小模型解决的绝不交给大模型自由发挥。

**追问预案**：怎么定「低置信度就转人工」这个阈值？（在标注集上画「答对率 vs 转人工率」的权衡曲线，按业务成本选点，而不是拍一个 0.7。）

**工程兜底要点**：客服 Agent 一定要审计「说了什么承诺」，因为模型最容易在安抚用户时超额承诺。

**Aster 挂钩**：情感/旅游/测试这几类业务按 agentKey 共用同一套分流与租户隔离骨架（`agent/core/AgentDefinition.java`、`agent/core/AgentRunIdentity.java`），可直接类比；`platform/security/ReviewAccessGuard.java` 是审核权限的例子。
