## 一、评估与可观测

### Q3.1 如何评估一个 Agent 的效果？评测集和指标怎么设计？

**口述答案**：我会同时看**结果**和**过程**。结果层：任务成功率（端到端做对了）、答案质量（忠实度、相关性）、拒答与转人工的合理性。过程层：平均步数、工具选择准确率、参数错误率、返工率、超时与中断比例。评测集从真实请求分层抽样，按意图分桶（问答/操作/多步任务），每条标注「完成判据」——这一步最关键，因为 Agent 的评测难点不是打分而是**定义什么算完成**。规模上 100–300 条就能指导迭代，比上千条低质样本有用。

**追问预案**：过程指标好但结果差说明什么？（执行正确但目标定义错了，常见于 Prompt 让模型「努力完成」而任务本身不可完成。）

**工程兜底要点**：必须留一个从不参与调参的盲测集，否则阈值和 Prompt 会过拟合到评测集。

**Aster 挂钩**：`evaluation/eval-sets/`（意图评测 + 带日期的 baseline 快照 + `run_baseline.py`）就是这个机制；这是我主动想补强的一层，因为单测通过不代表线上质量。

### Q3.2 你如何量化一个 Agent 的性能？（面试官想听的三个数字）

**口述答案**：我会给三个可对比的数字而不是形容词：**完成率**（同一评测集上，任务成功比例，附置信区间）、**成本**（单任务 token 与调用次数；多 Agent 场景要算到子任务粒度）、**时延**（首字延迟和端到端 P95，用分位数不用均值）。再补一个质量维度：工具调用错误率与返工率——它们能解释「为什么慢和为什么贵」。最关键的一句话是：**任何 Agent 的效果改进必须同时报成本和延迟的变化**，只报质量提升的多半是在拿钱换分数。

**追问预案**：怎么让「完成率」可信？（判据必须机械可判定——通过测试、字段匹配、引用 ID 存在；纯靠模型打分要定期与人工标注对齐。）

**工程兜底要点**：成本核算要落到每次 run 与每个角色，否则永远不知道是哪一步在烧钱。

**Aster 挂钩**：`agent/observability/TokenUsageService.java` + `agent/advisor/TokenUsageAdvisor.java` 采集每次调用的 `promptTokens/completionTokens` 和 `systemChars`，`agent/execution/AgentToolCallLedgerService.java` 提供调用事实。

### Q3.3 Agent 的评估体系通常包括哪些维度？只看准确率够吗？

**口述答案**：不够。六个维度：**能力**（任务成功率、质量分）、**过程**（步数、工具正确率、无效循环率）、**鲁棒**（输入扰动、依赖故障、边界与拒绝表现）、**效率**（时延分位、token 与费用、并发吞吐）、**安全**（越权率、注入成功率、敏感信息泄漏、危险动作被拦截率）、**满意度信号**（转人工率、重复提问率、纠错率）。工程上我最看重「安全」和「鲁棒」两类，因为它们决定能不能上线；很多团队只报能力分，结果上线后被一个空返回的工具打穿。

**追问预案**：这些维度怎么落地成日常机制？（每个维度配 1–2 个自动指标 + 一条回归门禁 + 一个线上告警，不能只停在文档里。）

**工程兜底要点**：安全评测要包含「失败时必须拒绝」的用例集——fail-open 的验收器是真实事故来源。

**Aster 挂钩**：我修过的一个真实问题可以当答案：Verifier 模型调用/解析失败早期被记为 pass（fail-open），现在改为 `unverified` 并在最终结果标注 `[未验收]`。

### Q3.4 LLM-as-a-Judge 怎么用？有哪些坑？

**口述答案**：适合做**相对判断**（A/B 哪个更好、答案是否被引用支持、是否违反风格约束），不适合做绝对事实核验。三个必须防的坑：**位置偏好**（先出现的答案更容易被选中，要双向各评一次）、**长度偏好**（长答案得分高，要显式要求忽略篇幅）、**同源偏差**（评委和被评模型同源，会共享盲区，重要场景换模型或加规则校验）。落地规矩：judge 输出必须是结构化 verdict + 理由，Prompt 里给出评分锚点例子，并定期抽样与人工标注算一致性（Cohen's kappa 级别），一致性掉下去就说明 judge 漂了。

**追问预案**：能不能用 judge 做线上实时质检？（可以但要便宜模型 + 抽样，实时全量评会让成本翻倍；更稳的是离线批量评 + 线上小比例抽检。）

**工程兜底要点**：judge 的评分不进业务决策链路，只做观测；让 judge 决定放行就等于把幻觉换了一层包装。

**Aster 挂钩**：本项目验收用的是规则 + Verifier 组合而非纯 judge，`VerifierNode.java` 的 verdict 是枚举不是分数，这是有意的选择。

### Q3.5 「任务成功率」在 Agent 里怎么定义和自动判定？

**口述答案**：判据分三类，可靠性递减：**客观可验证型**（代码能编译/测试通过、数据库状态确实变了、目标文件确实生成）——这类最该优先设计进去，可以完全自动；**结构可检查型**（必填字段齐全、引用 ID 真实存在、枚举值合法）——用代码判，不要问模型；**语义判断型**（回答是否解决了问题）——只能用 judge 加人工抽审。设计上我会把每个任务类型的判据写成清单，作为评测集的元数据；判据本身要能评审，因为「判据写歪 → 优化方向歪」是最隐蔽的失败。

**追问预案**：怎么防止模型学会「讨好判据」？（判据多样化 + 保留盲测集 + 抽样人工复核，并对「刚好卡在判据边界」的答案做专项审查。）

**工程兜底要点**：完成判定要基于系统事实（ledger、DB 状态、产物），不能基于模型自述——这是 Q1.16 的评测版延伸。

**Aster 挂钩**：`agent/graph/GraphCheckpoint.java` 里的 `verificationStatus` / `revision` 让「是否验收、返工了几轮」成为可统计字段。

### Q3.6 Agent 的成本怎么核算和优化？有哪些立竿见影的手段？

**口述答案**：核算要做到 **run → 步骤 → 角色 → 调用**四级归因：每次模型调用记录 prompt/completion token 和单价，每个工具调用记录耗时，聚合成「每任务成本分布」而不是总量。优化顺序按性价比排：① **稳定前缀命中缓存**（system 与工具 schema 完全一致，别塞时间戳）；② **上下文瘦身**（工具结果截断、检索用引用代替全文——这两项通常能砍掉一半输入 token）；③ **模型分级路由**（意图分类和小任务走便宜模型，规划与验收才走强模型）；④ **减少返工与循环**（步数与返工上限、重复调用检测）；⑤ 输出长度约束。

**追问预案**：多 Agent 的成本膨胀主要在哪？（同一上下文被复制进 N 个角色，以及规划/验收各一次额外调用——所以并行不等于多倍成本，串行链才会。）

**工程兜底要点**：没有归因就没有优化，「整体看像很贵」这种结论推动不了任何改动。

**Aster 挂钩**：这是我在推的方向——已有 token 采集（`TokenUsageService.java`），还缺按角色/意图的成本分布看板与预算熔断，我会说清「已做到哪、没做到哪」。

### Q3.7 改动 Prompt 或模型版本后，怎么保证没有回归？

**口述答案**：把评测当 CI 用：固定评测集 + 基线快照，改动后跑对照，按意图分桶看指标差值，超过阈值就阻断发布。要同时看三类信号：能力（成功率）、成本（token/步数）、稳定性（同一输入多次运行的方差）。灰度发布时用**分桶流量 + 线上代理指标**（转人工率、纠错率、拒答率）而不是主观感受。模型版本变更最危险，因为它会静默改变工具调用的表现，所以模型名和参数要写进配置并可追溯，不能靠 SDK 默认。

**追问预案**：评测集不够用时怎么办？（从线上采样补，并给评测集打「覆盖意图」标签，找出没有样本的意图桶。）

**工程兜底要点**：Prompt 要版本化管理并与评测结果绑定，改 Prompt 不留记录等于不可回溯。

**Aster 挂钩**：`evaluation/eval-sets/baseline-2026-10-26-r2.json` 这类带日期版本号的快照就是这个用途。

### Q3.8 怎么评估 Agent 的鲁棒性？除了准确率还测哪些对抗与边缘 case？

**口述答案**：我会专门做一组「必须不出事」的用例：**输入扰动**（错别字、口语化、超长输入、多语言混杂、重复粘贴）、**边界**（空输入、只有一句话的任务、要求做两件矛盾的事、需要超权限的动作）、**依赖故障**（工具超时/返回空/返回脏数据、rerank 挂掉、知识库为 0 条）、**对抗**（Prompt 注入样本、诱导泄露系统提示或他人数据、诱导越权写操作）、**资源**（并发上限、队列饱和、请求中途断连）。判据不是「答得好」而是「行为可接受」：该拒的拒了、该降级降级了、该转人工转了、没有副作用发生。

**追问预案**：断连怎么测？（在 SSE 中途主动关闭连接，验证线程与队列能回落、无残留副作用、状态标记为 interrupted。）

**工程兜底要点**：这类测试集往往比能力评测集更早暴露生产事故，且用例成本低。

**Aster 挂钩**：检索侧的 `NO_HIT/TIMEOUT/OVERLOADED` 就是可测的故障注入点；`AgentKnowledgeIndexRecoveryJob.java` 对应「索引坏了能自愈」这一类用例。

## 二、线上排查

### Q3.9 线上 Agent 延迟明显升高，怎么通过 Trace 定位并优化？

**口述答案**：先看是**全局变慢还是某类请求变慢**——按意图、Agent、模型分维度切分位数，别被均值骗。然后拆一次慢 run 的时间线：模型调用次数与每次耗时、工具调用耗时（网络/外部服务）、检索耗时（向量/词法/rerank 分段）、排队等待（executor 队列）、序列化与流式推送。定位后典型结论有四类：**上下文膨胀**（prompt token 上涨 → 单次调用变慢，看 token 趋势）、**队列饱和**（等待时间占比高 → 池子或降级策略问题）、**外部依赖抖动**（某工具 P99 拉高 → 加超时与熔断）、**步数增加**（返工或死循环，看平均步数变化）。优化要对症，「换更快的模型」常常不是根因。

**追问预案**：Trace 里必须有哪些字段才能排得动？（runId、父子步关系、模型名与参数、prompt/completion token、每次工具调用的目标与耗时、状态码、失败原因枚举、检索各阶段候选数。）

**工程兜底要点**：步数与 token 要设阈值告警，它们比延迟更早预示失控。

**Aster 挂钩**：`agent/hook/ExecutionTraceHook.java` 采集步骤事件、`RagRetrievalTrace` 分段记录 `vectorMillis/lexicalMillis/rerankMillis/totalMillis`——检索延迟能直接拆开看，这是我最常拿来定位的一段。

### Q3.10 用户反馈「回答效果不好」，你的排查流程是什么？

**口述答案**：四步固定流程：**复现**（拿同一 query 同一身份重跑，确认是不是随机性；相同输入不同结果见 Q1.29）→ **分段判定**（先看事实源：该信息在不在库里/工具能不能取到；再看是否召回；再看是否进了上下文；最后看生成）→ **归因分类**（数据缺失/检索未命中/命中错块/上下文被截断/Prompt 约束不足/模型能力不足）→ **修复并固化**（改动进评测集防回归）。最忌讳的是先改 Prompt 试一把——那会让问题暂时消失但原因未知，下次还会来。

**追问预案**：怎么判断是被截断还是没召回？（看实际发送的上下文快照；所以我强调上下文要可回放。）

**工程兜底要点**：bad case 要有归因标签并统计分布，修的是「一类」而不是「一条」。

**Aster 挂钩**：本项目的答案快照 + trace 让「进入模型的到底是什么」可查，`RagTraceCandidate.java` 保留候选明细。

### Q3.11 一个可运维的 Agent 服务需要哪些线上指标和告警？

**口述答案**：我会分四组：**质量代理**（任务成功率抽样、返工率、`unverified` 比例、拒答与转人工率）、**稳定**（错误率、工具失败率按工具维度、检索降级次数、未启动/被拒绝任务数）、**效率**（端到端 P50/P95、首字延迟、平均步数、单任务 token 与费用）、**资源**（executor 活跃数与队列长度、连接池使用率、租约锁续租失败、MCP/外部服务健康）。告警挂在**变化率**上而不是绝对值：成功率跌 X%、步数突增、某工具失败率翻倍。最后一条常被忽略：知识库「索引落后」和「未索引文档数」必须有指标，否则用户拿到的是旧答案而你不知道。

**追问预案**：这些指标怎么和 SLO 绑定？（按意图分桶定 SLO，问答类和执行类不能共用一个成功率目标。）

**工程兜底要点**：指标要能定位到 run，否则只是仪表盘不是排障工具。

**Aster 挂钩**：目前项目有 trace 与 token 采集、评测基线，但缺统一的线上 SLO 与告警体系——这是我在 notes §12 里列的「质量与运维缺门禁」，面试时如实说是待办而不是已建好。

### Q3.12 多实例、异步执行下的可观测和身份传播怎么保证不断链？

**口述答案**：三件事：① **显式传递身份快照**（tenant/user/agent/run/conversation 随任务对象走，不依赖 ThreadLocal——切线程池就会串号）；② **一个全局关联 ID**（runId 贯穿日志、trace、DB 记录与外部调用，异步分支也要挂得上）；③ **状态外置**（会话锁用数据库租约而不是进程内锁，检查点落库才能跨实例恢复）。另外要监控「断链」本身：出现没有 runId 的日志、或者异步任务找不到父上下文，就是设计漏洞的信号。

**追问预案**：为什么 Java 里这块比 Go 容易出事？（Go 的 `context.Context` 是显式一等公民；Java 没有等价物，需要自建 run 级上下文携带 deadline、取消令牌与子任务句柄，否则取消与超时传不下去。）

**工程兜底要点**：审计和隔离都建立在身份正确上——身份断链意味着数据隔离同时失效，这是安全事故不是观测问题。

**Aster 挂钩**：`platform/security/CurrentActor.java` 做入口身份；PG 租约锁把键扩到 tenant/user/agent/conversation，并且每个 JVM 有实例心跳（`chat/conversation/ApplicationInstanceRegistry.java`），租约与 `agent_run` 记录 owner_instance，崩溃实例留下的租约可被其他实例识别并接管——「多实例下租约怎么回收」这个细节讲出来很有说服力。统一取消上下文仍未贯穿（notes §12 第 11 条）。

## 三、安全与权限

### Q3.13 为什么 Prompt Injection 在 Agent 场景比普通大模型更严重？怎么防？

**口述答案**：普通聊天里注入的坏结果是一句错话；Agent 里模型手握工具，注入可以直接诱导真实读取、联网、查询、写库或发信，而且是**多步传播**——恶意内容进了工具结果或长期记忆，后续每一步都会带着它。防护必须是分层的：把网页、文件、邮件、数据库结果**标记为数据**而不是指令（结构化包裹 + 来源标注）；权限在服务端执行时校验，不靠 Prompt 声明；敏感读取与外发要审批；工具结果与最终答案脱敏后再入审计。要明说一句：**没有单点方案能防注入**，只有「即使被注入也做不成坏事」的纵深。

**追问预案**：检索/记忆内容也能成为注入载体？（能，这是最容易被忽略的一条——被污染的文档或抽取到的恶意记忆会长期生效。）

**工程兜底要点**：Agent 的注入防护评测要常态化跑，包含「注入后是否发生副作用」这种可判定用例。

**Aster 挂钩**：详见 [`../agent-interview-notes.md`](../agent-interview-notes.md) §6；本项目现状是工具层校验 + 角色过滤，未做全链路注入评测。

### Q3.14 Agent 应该在什么情况下请求人工确认（human-in-the-loop）？怎么设计？

**口述答案**：满足任一条件就该要审批：**不可逆**（删除、转账、发信、下单）、**影响外部人**（对外沟通、发布）、**超权限**（跨租户或超出角色资源范围）、**低置信**（模型自己不确定但动作代价高）、**批量**（一次影响 N 条以上）。设计上有四个要点：调用先持久化成「待审批」状态而不是直接执行；审批 UI 要展示**将要发生什么**（目标、参数摘要、影响范围）而不是模型推理文本；批准后**服务端重新授权**再执行（不能信前端按钮）；拒绝或超时要把拒绝原因回灌给模型，让它换路径。恢复时要保证幂等，避免重复执行。

**追问预案**：审批会不会让 Agent 失去价值？（用「风险分级」控制频率——低风险自动执行 + 事后审计，只有高风险才阻塞。把审批当成本而不是安全性唯一指标。）

**工程兜底要点**：审批态需要状态机和恢复语义，属于「不实现就别说支持」的能力。

**Aster 挂钩**：本项目**尚未实现**完整的审批后恢复状态机（notes §12），我能讲清设计但必须说是待补——这个诚实回答本身是加分项。

### Q3.15 如果 Agent 能执行 Shell 命令，怎么防止它执行恶意命令？

**口述答案**：第一认知是**把 Shell 当远程代码执行能力**，而不是普通查询工具。应用层能做的：默认关闭、命令 allowlist、拒绝 shell 元字符与管道拼接、拒绝绝对路径和穿越、限制解释器选项、限时限量输出。但必须说清局限：**allowlist 不能证明命令安全**（合法命令带恶意参数照样能读敏感文件），符号链接、环境变量、系统差异都可能绕过。真正的边界在操作系统层：非 root 容器或独立执行服务、只挂任务工作区、无网络或受控出口、只读根文件系统、CPU/内存/进程数配额，并做逃逸测试。

**追问预案**：那你项目做到了哪一层？（我做到应用层双重复核——`ToolGuardPolicy` 预检 + 工具内二次校验，没有容器级隔离；把「应用护栏 ≠ OS 沙箱」这条边界说清楚比夸功能强得多。）

**工程兜底要点**：对无法可靠约束的解释器（能读文件、能起子进程、能联网）直接从工具集移除，比写十层校验有效。

**Aster 挂钩**：详见 notes §5；代码在 `capability/tools/TerminalOperationTool.java` + `ToolSandbox.java`。

### Q3.16 「权限不是 Prompt」具体指什么？服务端授权模型应该怎么设计？

**口述答案**：指模型 Prompt 里写「你不允许做 X」只是**概率性约束**，遇到注入或幻觉就会失效；真正的授权必须在代码执行点判定。设计上我分四段收敛：**注册期**（工具是否对该 Agent 可用、有无风险分级）、**暴露期**（当前身份能看见哪些工具，schema 决定参数范围）、**执行期**（对具体动作 + 目标资源重新授权，带租户/用户/资源三要素）、**事后**（审计与告警）。最关键的是执行期这次校验：它必须是「即使模型被骗也会拒」的，而且不能依赖上一次调用的结论。

**追问预案**：细粒度和性能怎么平衡？（授权结果可按 run 缓存，但缓存 key 必须含动作与资源，别只按工具名缓存。）

**工程兜底要点**：资源级授权 + 高风险写操作的审批与幂等键，是「工具名级授权」和「生产可用」之间的主要差距。

**Aster 挂钩**：现状是工具名/角色级（`WorkerRole.java` + `ToolGuardPolicy.java`），资源级授权仍是缺口（notes §12 第 8 条）——这个坦率区分是这题的高分答法。

### Q3.17 Agent 的审计日志应该记什么？怎么做脱敏？

**口述答案**：每次工具调用记：runId、tenant/user、Agent 或角色、会话、工具名、目标资源摘要、策略决定（放行/拒绝及原因）、耗时、结果状态与大小、错误类别。每次模型调用记：模型名与参数、token 用量、上下文版本哈希。原则是**能重建决策链但不复制业务内容**：参数与结果只存摘要、长度和哈希，密码/Token/身份证/手机号/完整文档内容绝不原样入库；完整内容如有留存需求，单独放受控存储并配保留策略与访问审计。还要能回答「谁在什么时候批准了这个动作」。

**追问预案**：日志里最常见的泄漏点在哪？（异常栈——里面常带 SQL 与连接信息；以及 debug 级别打印完整 prompt。我专门把 Advisor 和 Agent 的日志改成事件与长度就是为这个。）

**工程兜底要点**：审计要防篡改并规定保留期；否则「有日志」不等于「有审计」。

**Aster 挂钩**：`agent/hook/ExecutionTraceHook.java` + `AgentToolCallLedgerService.java` 是执行事实源，`docs/agent-interview-notes.md` §12 提到本轮已把敏感正文日志收敛为事件与长度。

### Q3.18 Agent 读邮件/文档/数据库再自动回复，怎么防数据泄露？

**口述答案**：读取侧管「能看什么」：按用户与资源 ACL 最小授权、数据库限只读 + 表范围 + 行数 + 超时、检索强制带租户过滤、上下文里只放完成任务所需的字段并做脱敏。外发侧管「能说出去什么」：收件人与域名校验、附件类型与大小限制、敏感数据规则匹配（身份证、密钥、内部字段）、批量发送限制，并且**默认生成草稿由用户确认**。最容易被忽略的是通道混合：被读取的内容里的指令可能诱导 Agent 把别的数据发出去，所以「读到的东西」和「能发的范围」之间必须有服务端策略边界，而不是交给模型判断。

**追问预案**：能不能用 DLP 规则代替审批？（规则能拦已知模式，但拦不住「把 A 项目结论透露给 B 项目同事」这种语义泄露，语义层要额外判定且默认拒绝。）

**工程兜底要点**：租户隔离要在存储层强制，不能只在业务代码里加 if——一旦漏加就是跨租户事故。

**Aster 挂钩**：已有 JWT 身份、知识库租户隔离、私有对象存储与只读 SQL 工具；邮件发送与通用 DLP **未实现**，不能说成现状（notes §8）。

### Q3.19 怎么对 Agent 做红队/对抗测试？

**口述答案**：三条路径：**用例库驱动**（把已知注入模板、越权诱导、泄露诱导、伪完成声明做成可回归的攻击集，每次改动跑一遍）；**角色模拟**（让一个模型扮演攻击者，对被测 Agent 发起多轮诱导，把成功突破的样本固化进用例库）；**线上灰度自检**（在预发环境用真实工具配置跑高危场景，验证「即使被骗也没有副作用」）。判定要看**行为**：有没有发生未授权读写、有没有泄漏系统提示或他人数据、有没有谎报完成。这套机制的价值在于它会随能力增长稳定暴露新风险，而不是一次性审计。

**追问预案**：自动红队的成本高怎么控？（攻击集分层——每次改动跑核心 50 条，每周跑全量；新样本先进观察集不阻塞发布。）

**工程兜底要点**：测试结果要可复现（记录输入快照与模型版本），否则无法证明修复有效。

**Aster 挂钩**：这是本项目明确缺的一块（notes §12 第 12 条：需要 RAG/工具选择/成功率/安全攻击的离线数据集），我会把它作为下一步优先级讲，而不是回避。

### Q3.20 接入第三方 MCP server 或插件，有哪些额外风险？

**口述答案**：四类：**供应链**（server 实现随时可变，能力描述与实际行为不一致，工具描述本身就能成为注入载体）、**权限扩散**（一个 server 可能带来几十个工具，模型选择面和被攻击面同时放大）、**数据外流**（参数会发到第三方，凭据与个人数据可能出域）、**稳定性**（外部服务不可控，必须有独立超时、熔断与降级）。治理做法：接入时登记能力清单并**默认拒绝未登记工具**（fail-closed），参数走白名单校验，出网走受控出口，并按 server 维度做独立配额。要主动承认一句：应用层校验不等于隔离，第三方 server 的错误实现我控制不了。

**追问预案**：默认拒绝会不会误伤新工具？（会，所以我留了一个显式配置的放行开关，但它只放名称、不放 schema 级参数授权——这是兼容性与安全性的真实取舍。）

**工程兜底要点**：把工具描述当作不可信输入看待，纳入版本管理与评测。

**Aster 挂钩**：`McpToolRegistry.java` 做登记、`ToolGuardHook.java` 的 `allowed-unregistered-tools` 配置是显式放行开关（`app.agent.hook.allowed-unregistered-tools`）。

## 四、系统设计压轴题

> 通用答题骨架（六层）：**接入（鉴权/限流/会话）→ 编排（循环或图/预算/取消）→ 上下文（记忆/检索/压缩）→ 能力（工具/授权/沙箱/幂等）→ 验收（判据/返工/审批）→ 观测（trace/成本/成功率/评测门禁）**。
> 每题都按这个骨架展开，再补该题特有的风险点——这比每题重新组织答案省力得多。

### Q3.21 设计一个通用 Agent 框架，你会怎么设计？

**口述答案**：按上面六层展开，重点讲三处设计取舍：① **控制流可显式配置**——同一套框架要能表达「固定 Workflow」「单循环 ReAct」「图式多 Agent」三档，用声明式的节点与边而不是把逻辑埋在 Prompt 里；② **一切受限**——每档都有最大步数、总 deadline、token 预算、工具白名单，缺省值保守；③ **扩展点标准化**——工具注册、上下文 hook、验收器、观测器是四个稳定接口，业务只在这四处扩展。运行时状态必须可序列化并落库（不含连接与回调），否则谈不上中断恢复。最后强调：框架交付时**必须自带评测 harness**，不然团队会各写各的临时验证，效果无法比较。

**追问预案**：面试官一定会问「哪层最难」→ 答上下文层与验收层（见 Q1.26），并说明理由。

**必答风险点**：异步身份断链、并行写冲突、模型版本漂移导致既有 Prompt 失效。

**Aster 挂钩**：这就是本项目结构——`agent/graph/` 编排 + `agent/hook/` 扩展点 + `capability/` 能力面 + `evaluation/` 评测，直接照着讲。

### Q3.22 设计一个 AI 客服 Agent：模糊需求、指标和权限怎么处理？

**口述答案**：第一层做**意图与置信分流**：FAQ 模板、知识类走 RAG、订单/物流/账户走工具调用、低置信或高风险转人工——判据来自小模型或规则而不是大模型裸判。模糊需求处理原则是**宁可反问不可猜测**：缺关键槽位（订单号、时间范围）就走澄清，最多两轮，超轮次转人工。承诺类回答（赔付、时效、退款）必须来自结构化规则表，不允许模型自由生成，这是客服场景最重要的一条硬约束。指标：一次解决率、转人工率、答后重复提问率、承诺违规率、端到端 P95、单会话成本。权限：会话归属校验、只返回当前身份可见的数据、写操作（改地址、退款）走审批。

**追问预案**：怎么定「低置信转人工」阈值？（在标注集上画答对率与转人工率的权衡曲线，按业务代价选点。）

**必答风险点**：超额承诺、跨用户数据泄漏、注入来自用户上传文件（工单附件是典型载体）。

**Aster 挂钩**：业务 Agent 按 agentKey 区分（情感/旅游/测试）共用同一套租户与检索骨架（`agent/core/AgentDefinition.java`）；`KnowledgeRetrievalStatus.NO_HIT` 支撑「检索不到就不硬答」这条规则。

### Q3.23 设计一个多 Agent 自动 PR / 代码 Review Agent

**口述答案**：拆分是**读代码的、判定问题的、写建议的、验证的**四类角色，但关键设计不在拆分而在沙箱与验证：每次 run 一个独立工作区或容器（只读源码 + 可写工作副本、无外网或受控出口、资源配额），工具集限定在「读文件、跑测试、跑静态分析、查 diff」。产出必须是**结构化 findings**（文件、行号、类别、证据、置信度），证据来自真实工具输出而非模型推断。验证环节用确定信号：能否复现、测试是否通过、静态分析是否同意——只有通过的才进入评论，其余降级为草稿。写操作（提交评论、合并）默认草稿 + 人工确认后执行。

**追问预案**：怎么控制误报？（每条 finding 带证据与置信度，设阈值 + 按类别统计误报率并持续调规则，必要时只对高危类别自动评论。）

**必答风险点**：沙箱逃逸（依赖安装、脚本执行都是攻击面）、并发写同一分支冲突、diff 上下文过长导致注意力稀释。

**Aster 挂钩**：可类比 `capability/tools/ToolSandbox.java` 的工作区隔离思路，但要如实说明项目里还没有代码执行类沙箱。

### Q3.24 设计企业知识库 Agent 链路，并支持知识变更主动推送

**口述答案**：索引链路走「接入 → 解析（版面/表格/OCR）→ 结构化分块 → 元数据（权限、生效期、版本、负责人）→ 向量 + 词法双写」。检索链路强调三点：**权限过滤必须在精排之前**、版本有效性用元数据而非时间惩罚、命中结果带引用可溯源。主动推送是最容易设计错的部分：变更事件先做**影响面计算**（这份文档变更会影响哪些已订阅话题/哪些历史问答的正确答案），再按订阅关系与频控合并生成摘要，推给谁取决于谁有权限看，并且推送内容要带「变更前后差异 + 来源链接」。要有防抖与去重，否则一次批量重建会造成刷屏。

**追问预案**：怎么保证「索引落后」不伤用户信任？（指标暴露未索引文档数与最近索引时间，答案里标注知识快照时间。）

**必答风险点**：权限变更未随推送重新校验导致越权推送、旧版本残留导致新旧答案同时被召回、推送频控缺失。

**Aster 挂钩**：本项目检索侧完全对应——向量与词法双路、`AgentKnowledgeIndexRecoveryJob.java` 管索引恢复；主动推送尚未实现，可按设计口述。

### Q3.25 设计一个运维故障排查 Agent，高危操作怎么管控？

**口述答案**：能力分两档：**只读诊断**（查监控、查日志、查配置、看拓扑）默认自动执行，**变更动作**（重启、扩容、回滚、改配置、删数据）全部要求审批与人工确认。排查流程编排成「假设—验证」循环：模型提出候选原因，用只读工具去证伪，每步输出结构化结论（假设、证据、剩余候选），这样人能中途接得住。管控要点：命令 allowlist 且参数强校验、按环境（预发/生产）分级授权、每个动作绑定幂等键与回滚方案、并发保护（同时只允许一个 run 对同一资源写）、全过程审计。最关键的判断是**模型只做诊断建议，不直接持有生产写权限**。

**追问预案**：如果告警风暴时 Agent 想批量重启怎么办？（批量动作超阈值自动升级为人工审批，并加时间窗内的动作次数上限。）

**必答风险点**：误判导致雪崩式操作、日志里含敏感数据被带进上下文、与既有自动化系统（HPA/熔断）互相打架。

**Aster 挂钩**：可引 notes §5 的 Shell 防护边界与 `ToolGuardPolicy.java` 的集中预检，并明确生产级审批尚未实现。

### Q3.26 设计一个旅行规划 Agent，任务怎么拆解？各子 Agent 职责怎么划？

**口述答案**：拆解按**产出物**而不是按步骤：需求收集 → 目的地与行程框架 → 交通方案 → 住宿方案 → 每日玩法 → 预算与冲突校验 → 成稿。前段是槽位填充（缺预算、缺时间就澄清），中段是可并行的信息收集（交通/住宿/玩法互不依赖，适合多 Worker），末段必须串行（预算与冲突校验依赖全部结果）。职责划分的依据是**权限域不同**：信息收集只读搜索、校验角色要能访问结构化价格数据、成稿角色不需要任何外部工具。这里有个经典错误值得主动说：行程的可行性是**约束满足问题**，模型的时空推理并不可靠，所以「同一天两个城市」这种错误必须由代码规则校验兜住，不能指望反思。

**追问预案**：怎么让结果可信？（每个价格/班次带来源与时间戳，并在最终输出前做一次规则校验清单，校验失败就回炉而不是标注「已优化」。）

**必答风险点**：幻觉价格与班次、时间/地理冲突、工具结果过期（价格时效）、并行结果的跨步一致性。

**Aster 挂钩**：旅游现在是 **agentKey 驱动的配置形态**而不是独立类——工具集在 `capability/tools/TravelToolConfig.java`（联网搜索），身份与路由靠 `agent/core/AgentRunIdentity.java`（tenantId + agentKey + conversationId）+ `agent/core/AgentDefinition.java`。我可以讲清单 Agent 版做到了哪、多 Worker 拆解属于设计推演。

### Q3.27 设计一个 Deep Research / 文献调研 Agent，多 Agent 方式有什么风险？

**口述答案**：流程是「问题澄清 → 检索面规划（生成子问题）→ 并行搜索与抓取 → 证据结构化（每条结论带来源与原文引用）→ 交叉验证（同一结论要求多来源，冲突要并列展示）→ 综述生成 → 事实性抽查」。多 Agent 的风险我重点讲三个：**共同偏差**——同一模型系列做检索和验证，错会错在一起，验证要引入不同信号（原文匹配、规则、不同模型）；**引用膨胀**——Agent 很擅长生成看起来权威的引用，必须把引用 ID 与真实抓取记录做后端比对，不能凭模型写出；**成本失控**——一次深度调研可能几十次搜索加十几次抓取，要有预算与检索次数上限，超限就降级为「部分结论 + 明确缺口」。

**追问预案**：怎么评一个 Deep Research 产品？（结论可核查率、来源多样性、缺口是否如实声明、成本与时延，而不是文章流畅度。）

**必答风险点**：伪引用、把预印本/营销页当权威、抓取内容里的注入。

**Aster 挂钩**：`skills/web-research.md` 是技能化调研流程的例子，`capability/tools/WebScrapingTool.java` + `UrlAccessPolicy.java` 覆盖抓取与出网校验。

### Q3.28 设计一个内容标注 Agent 的流程，怎么保证标注质量？

**口述答案**：标注任务的特殊性在于**有客观金标**，所以流程是：标签体系与判定说明（写成可执行规则而不是模糊描述）→ 单条标注（强制枚举输出 + 理由 + 置信度）→ 低置信与规则冲突项进复核 → 定期用金标集测一致率（与人工标注算 Kappa），并监控标签分布漂移。批处理要控制成本：小模型或便宜模型跑第一批、难例升级模型。质量保障的关键设计是**标签体系先于模型**——绝大多数标注质量问题的根因是标签定义有歧义，而不是模型不行；所以我会要求每个标签都配 2–3 个正反例。

**追问预案**：能不能让模型自己迭代标注 Prompt？（能，但只在金标集上验证提升后采纳，且保留原始规则版本，否则会出现「为刷分改定义」的自欺。）

**必答风险点**：类别不平衡下的假高准确率、标注泄漏（金标进过 Prompt）、漂移无人监控。

**Aster 挂钩**：这套「枚举输出 + 评测集」思路与本项目 `PlanJsonParser.java`（枚举角色、硬约束）和 `evaluation/eval-sets/` 一脉相承。

### Q3.29 设计一个视频/股票分析这类多模态或数据密集型 Agent 全链路

**口述答案**：共同结构是「**结构化取数 → 分段理解 → 规则校验 → 归因输出**」。视频类：抽关键帧 + ASR + OCR 三路并行产出带时间戳的中间表示，再由模型在这些表示上做归纳；难点是长视频超出单轮上下文，要按镜头分段并维护「已看摘要」，输出必须能给出时间点引用以便人工核对。股票/数据类：数据必须来自接口而非模型记忆，字段口径先固定（时间戳、复权方式、币种），计算交给代码（指标、同比、阈值告警），模型只做解释与归因串联；输出要求每个数字可回溯到一次工具调用。两者的共同风险都是**把模型推断当事实**，所以数值与时间位置必须由系统提供。

**追问预案**：多模态里图文顺序有影响吗？（实践中有影响，视觉 token 与文本的相对位置会改变注意力分配，需要在自己评测集上对比而不是照搬结论。）

**必答风险点**：幻觉数值、跨模态错配（图中没有的东西被说出来）、长视频分段间的记忆丢失、数据源延迟。

**Aster 挂钩**：图像理解侧有 `knowledge/image/` 模块与 `services/image-search-mcp`，文档解析有 `document-mcp`；「数值由工具提供」这条正好用 `DatabaseQueryTool.java` 举证。

### Q3.30 讲讲你做一个 Agent 项目的完整流程？（项目全流程 / 一分钟介绍）

**口述答案**：按「问题定义 → 判据设计 → 最小可用链路 → 评测集 → 加能力 → 生产化」六步讲。第一步不写代码：确认错误代价和有没有客观验收信号，决定要不要 Agent。第二步定义「算完成」，因为它决定后面所有优化方向。第三步做最小链路（单 Agent + 少量工具 + 固定检索），先拿到基线完成率和成本。第四步建评测集，把 bad case 分类固化。第五步才加规划、并行、记忆、审批这些复杂能力——每一项都必须在评测集上证明收益，收益不明显就撤。第六步生产化：预算与步数上限、取消与超时、授权与审计、监控告警。

**追问预案**：面试官接着会问「哪一步最难」→ 答判据设计（因为业务方常给不出可机械判定的完成标准）。

**必答风险点**：跳过评测直接加能力（最常见的失败路径）、把「Demo 能跑」当「能上线」。

**Aster 挂钩**：一分钟版本在 notes §「先讲整体架构」，收尾用 §「当前项目的安全边界速记」那段——先说跑通了什么，再说哪些是生产化待补，这个顺序最可信。

## 五、手撕与编码

> 应用/开发岗的手撕重点在**能跑、边界清楚**，不是最优复杂度。写完主动说清时间和空间复杂度和一个已知缺陷。

### Q3.31 手撕：ReAct 循环 / Tool Registry

**口述答案**：ReAct 骨架就是「组装上下文 → 调模型 → 解析 Thought/Action → 执行 → 回填 Observation → 判定终止」，考的是边界处理：解析失败要能重试并回灌纠错提示，工具不存在要拒绝，步数上限和重复调用检测不能忘。Tool Registry 考的是接口设计：注册（名称、描述、schema、风险等级）、按身份/角色求可见集合、按名查找并执行、执行结果统一封装。我会主动加一个 `Idempotent` 语义和参数校验钩子，因为这正是面试官想看的工程意识。

**关键点**：终止条件用显式枚举（DONE/预算耗尽/被取消/需审批），不要靠「模型说完了」；工具执行必须在权限层之后。

**常见坑**：忘记处理「一轮多个 tool_calls」；把工具原始大输出直接拼进上下文；异常吞掉导致循环不退出。

**Aster 挂钩**：现成对照是 `agent/core/ToolCallAgent.java`（循环）与 `capability/tools/ToolFactory.java`、`capability/mcp/McpToolRegistry.java`（注册与求集合）。

### Q3.32 手撕：Memory 系统与上下文压缩

**口述答案**：我会写三层结构：工作记忆（本次 run 的消息列表，带来源标签）、会话记忆（按 conversationId 存取，带最大轮数与摘要替换）、长期记忆（事实条目：内容 + 类型 + 租户/用户 + 时间 + 来源 + 置信度，检索时先按权限过滤再做相似度）。压缩函数是这题的重点：保留目标与用户明确约束，丢弃工具原文（替换为引用 ID），历史按重要度打分而不是按位置截断——这一点写出来就能区分候选。

**关键点**：查询顺序必须是「filter 再 similarity」；写入口要有去重与冲突检测。

**常见坑**：全局可变单例导致多用户串号；异步提取时没带身份快照；把记忆当可信指令拼进 system。

**Aster 挂钩**：`chat/memory/MemoryService.java`、`FileBasedChatMemory.java`、`agent/hook/MemoryInjectionHook.java` / `MemoryCompressionHook.java` 逐层对应。

### Q3.33 手撕：混合检索 / Rerank / 语义缓存 / Chunking

**口述答案**：四个小题都常考，各自的评分点是——**Chunking**：按结构优先、定长兜底，保留标题路径与 chunk 序号，中文按标点切；**BM25 + 向量混合**：两路各出候选、按文档去重、分数不可直接相加所以要统一精排，并说清 BM25 的 TF 饱和与长度归一化；**Rerank**：cross-encoder 的输入构造（query+doc 拼一起）、候选数控制、超时降级回原序；**语义缓存**：相似度阈值 + TTL + **命名空间隔离**（跨会话/跨租户绝不能复用，这是最关键的正确答案）。

**关键点**：每道题都要说清「失败时行为」——解析失败、召回为空、精排服务超时。

**常见坑**：语义缓存不带权限维度（数据泄漏级错误）；混合检索直接加权求和；chunk 定长切在词中间还不做重叠。

**Aster 挂钩**：`AgentKnowledgeRagService.java`（双路 + 去重 + rerank + 降级）、`DashScopeRerankService.java`、`AgentKnowledgeChunk.java` 都有现成实现可参照着讲。

### Q3.34 手撕清单：还有哪些会被考？

**口述答案**：应用/开发岗的另外三类：**评估与运维类**（LLM-as-a-judge 的双向去偏骨架、任务成功率统计、带分位数的延迟聚合）、**并发类**（带 deadline 传播的并行工具调用、有界线程池 + 拒绝策略 + 取消级联）、**传统算法类**（真实面经里出现的是中等难度题，例如合并重叠区间 LeetCode 56，重点是复杂度分析与边界处理）。底层类（Self-Attention、多头、RoPE、LayerNorm、KV Cache、LoRA、采样）主要出现在算法岗，应用岗当进阶准备，见 `04-java-backend-appendix.md`。

**关键点**：手撕时先讲接口和错误处理，再写实现；写完主动补一个「我明知不足的地方」。

**常见坑**：只写 happy path；不写并发/超时；把伪代码当成品（面试官会要求能跑）。

**Aster 挂钩**：并发取消与超时的真实取舍见 notes §9–§11，那三段是 Java 工程手撕追问的最佳弹药。
