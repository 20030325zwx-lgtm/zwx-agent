## 一、缓存与存储

### Q4.1 Redis 有哪些数据结构？在 Agent 系统里分别用来干什么？

**口述答案**：基础五类 String/Hash/List/Set/ZSet，加上 HyperLogLog、Bitmap、Stream、GEO。**String** 存模型响应与嵌入缓存（键含 query 归一化 + 模型版本），配 TTL 加抖动防雪崩；**Hash** 存 run 状态与配额计数；**ZSet** 做限流滑动窗口和优先级队列；**Set** 做工具幂等键集合与去重；**Stream** 做轻量任务队列与事件流（消费者组支持多实例分摊）；**Bitmap/HyperLogLog** 做日活与去重统计。要主动补一句边界：Redis 不适合作为业务主数据源——它会丢，Agent 的会话、审计、知识版本必须落在有事务保证的库里，Redis 只做可重建的加速层。

**追问预案**：为什么不用 Redis 做会话锁？（可以用 `SET NX PX`，但续租与「误删他人锁」要正确处理——我用 Lua 做 token 条件释放；本项目最终选了 PG 租约，理由是锁与数据同库、少一个组件。）

**工程兜底要点**：缓存键必须含**版本维度**（模型版本、Prompt 版本、知识库版本），否则更新后仍在服务旧结果——这是 Agent 系统里最常见的缓存事故。

### Q4.2 缓存穿透、击穿、雪崩分别怎么防？两级缓存怎么设计？

**口述答案**：**穿透**（查不存在的数据反复打到 DB）用空值短 TTL + 布隆过滤器；**击穿**（热 key 过期瞬间并发打 DB）用单飞/互斥重建（同一 key 只放一个请求下去）+ 逻辑过期异步刷新；**雪崩**（大批 key 同时过期）用 TTL 加随机抖动 + 分片打散 + 降级路径。两级缓存是本地 Caffeine 做 L1（纳秒级、抗热点）+ Redis 做 L2（跨实例共享、容量大）：读走 L1→L2→DB 并回填，写要处理**跨实例失效**，常见做法是 L1 用短 TTL + 订阅失效广播，而不是追求强一致。在 Agent 场景里我会加上语义缓存这一层，但它必须带权限命名空间。

**追问预案**：语义缓存最大的风险？（跨会话/跨租户复用答案，等于数据泄漏；所以 key 必须含 tenant/user/权限摘要，且只缓存无上下文依赖的问答。）

**工程兜底要点**：收益与风险都要量化——命中率、P95 改善、以及「旧答案被命中」的比例；缓存要有可一键关闭的开关，出问题才能止损。

### Q4.3 Redis 的过期与淘汰策略是什么？

**口述答案**：过期删除是**惰性删除 + 定期抽样删除**组合，不是全局扫描（后者成本不可接受）。淘汰策略八种，常考的是：`noeviction`（写满报错，默认）、`allkeys-lru` / `allkeys-lfu`（全键空间按最近使用/频率淘汰，缓存场景首选）、`volatile-lru/lfu/ttl/random`（只在设了 TTL 的键里淘汰）。我会按用途选：模型响应缓存用 `allkeys-lfu`（热点问题 LFU 比 LRU 更稳），任务队列和锁这类不能丢的键放**独立实例**并用 `noeviction`——把可丢的和不可丢的混在一个实例里是设计错误。

**追问预案**：LRU 和 LFU 什么时候差别明显？（存在长期热 key 时 LRU 会被一次突发访问挤掉热数据，LFU 抗抖动更好。）

**工程兜底要点**：`maxmemory-policy` 要主动配，默认的 `noeviction` 在缓存实例上会造成写入报错，这是典型线上事故来源。

### Q4.4 Redis Stream 和 Kafka 怎么选？

**口述答案**：Stream 提供消费者组、ACK、pending list、XADD/XREADGROUP，够用且运维成本几乎为零（已有 Redis 就能用），适合**轻量异步任务、事件广播、中小吞吐**——比如 Agent 的工具任务派发、活动事件推送。Kafka 的优势是分区级并行、顺序保证、超长留存、吞吐量和完整的生态（流处理、精确一次语义、回放），适合**大规模日志、多下游消费、需要重放的数据管道**。判断标准我给三条：日均消息量与留存需求、是否需要多团队独立消费、是否已经有 Kafka 运维能力。多数 Agent 应用其实用不到 Kafka，为了「以后可能量大」引入分布式消息队列是不划算的复杂度。

**追问预案**：Stream 的坑？（pending 未 ACK 会堆积，需要 XPENDING/XCLAIM 做超时重派；消费者组没有分区级的严格顺序。）

**工程兜底要点**：选型说明里必须包含「消息丢了怎么办」和「重复消费怎么办」，两者都要求幂等消费。

### Q4.5 PGVector 和 Elasticsearch 怎么选？MySQL、ES、PG 在一个 Agent 系统里怎么分工？倒排索引解决什么问题？

**口述答案**：见 [`02-tools-memory-rag.md`](02-tools-memory-rag.md) Q2.39（那条更完整）。一句话版本：**PG/MySQL 管事务与主数据，ES 管全文检索与聚合分析，向量检索在中小规模下直接放 PG + pgvector 省掉一个组件**，规模或混合检索要求上来再拆。倒排索引解决的是「按词找文档」不能顺序扫描——词 → posting list，复杂度与数据总量无关、只与该词的出现次数相关。

**追问预案**：ES 做向量检索行不行？（可以，kNN 支持已成熟，但它同时带来 JVM 内存与分片运维成本；如果全文检索不是刚需，就没必要为向量引入 ES。）

**工程兜底要点**：混合检索架构里 ES/PG 分别承担词法与向量两路时，要处理「两路分数不可比」，统一交给 rerank。

### Q4.6 Spring 的 `@Component` / `@Service` / `@Repository` / `@Controller` / `@RestController` 有什么区别？

**口述答案**：都是被组件扫描纳管成 Bean，语义分层不同：`@Component` 是通用 stereotype；`@Service`、`@Repository`、`@Controller` 是它的特化标记，各自带附加语义——`@Repository` 会把持久层异常翻译成 Spring 的 `DataAccessException`，`@Controller` 参与 MVC 视图解析，`@RestController` 等于 `@Controller + @ResponseBody`（返回值直接序列化）。分层的核心价值不是注解本身，而是**依赖方向可控**：Web 层依赖 Service，Service 依赖能力层，能力层不反向依赖 Web。

**追问预案**：为什么 `@Service` 自注入或同类内方法调用时 AOP 不生效？（内部调用绕过了代理对象——事务/缓存/重试注解会静默失效，这是 Agent 服务里很容易踩的坑，比如给带 `@Transactional` 的方法写了工具调用重试。）

**工程兜底要点**：Agent 项目里最常见的 Spring 事故是**单例 Bean 持有会话状态**——所有 run 上下文必须显式作为参数传递，不能存字段。

## 二、并发、流式与 JVM

### Q4.7 SSE、WebSocket、轮询怎么选？流式输出怎么实现？断连怎么处理？

**口述答案**：**SSE** 单向、纯 HTTP、文本、自带重连语义，最契合 LLM 逐 token 输出——实现简单、代理友好、不需要协议协商；**WebSocket** 双向，适合需要持续交互的场景（实时协同、语音、前端要中途发指令停止）；**轮询**只在无法保持长连接或事件极稀疏时用。SSE 实现要点：Controller 返回流式载体并按事件类型推（`activity`/`delta`/`done`），中间层不要缓冲，超时与心跳要显式设置。**断连处理**是最能体现工程力的部分：连接关闭不等于任务结束，必须明确语义——要么取消（设置停止标记、取消子任务、释放工作区并记 `interrupted`），要么转为后台续跑并可重连续读。默认「不管它」会造成线程与 token 泄漏。

**追问预案**：怎么防止客户端断开后 Worker 还在跑？（监听连接关闭事件设置取消状态，同时给整个 run 配总 deadline 兜底，因为关闭事件不一定可靠送达。）

**工程兜底要点**：流式输出的错误要以事件形式下发而不是抛异常，否则前端只看到「卡住」。

**Aster 挂钩**：`web/controller/AiController.java` 走 REST + SSE 与 JWT，取消语义与局限在 [`../agent-interview-notes.md`](../agent-interview-notes.md) §11。

### Q4.8 线程池的核心参数与拒绝策略？为模型调用配池要注意什么？

**口述答案**：七个参数：核心线程数、最大线程数、保活时间、时间单位、工作队列、线程工厂、拒绝策略。执行顺序常被问错——**先入核心线程，再入队列，队列满才扩到最大线程，都满才触发拒绝**。拒绝策略四种：`Abort`（抛异常）、`CallerRuns`（调用方跑，会反压上游线程）、`Discard`、`DiscardOldest`。为模型调用配池的关键认知是：这是**阻塞 I/O 密集型**，线程数不受 CPU 核数约束而受下游容量与内存约束，所以必须用**独立池**（不同外部依赖隔离，避免一个慢服务拖垮全部）、有界队列、**显式拒绝策略**（不要用 `CallerRuns` 把请求线程占住），并且队列满时要有明确降级行为而不是静默排队。

**追问预案**：为什么不能用默认线程池？（`ForkJoinPool.commonPool` 并行度按 CPU 核数算，几个阻塞的模型调用就能占满，且全局共享会互相拖累。）

**工程兜底要点**：活跃数与队列长度必须进监控，饱和是成本失控和 P95 飙升的前兆。

**Aster 挂钩**：`WorkersNode.java` 用有界专用 executor + 显式拒绝，RAG 队列满降级、Worker 队列满报告「未启动」——这套区分处理正是这题的答案。

### Q4.9 线上 Java 服务 CPU 高、线程堆积、OOM 怎么排查？

**口述答案**：工具链是 `top -H` 定位线程 → `jstack`/Thread dump 看栈 → `jstat`/GC 日志看回收 → JFR 做长时段采样。CPU 高常见三类：死循环或正则回溯、GC 频繁（栈里大量 `GC task thread`）、序列化/大对象拷贝。线程堆积在 Agent 服务里最典型：**客户端断开后模型 HTTP 或 Worker 仍阻塞**，表现为线程数持续上涨、executor 队列积压，最终打满模型连接池或数据库连接池——排查时按线程名分组看阻塞点，区分网络等待、JDBC、锁竞争、`Future.join()` 和未关闭流。OOM 要看是堆内还是元空间/堆外，堆转储前先确认 GC 日志里的晋升失败模式。

**追问预案**：`Future.cancel(true)` 之后线程为什么还在？（中断是**协作式**的——阻塞在不可中断 I/O 上的线程不会因中断标志退出，必须配 connect/read 超时或可取消客户端；这是这题最硬核的正确答案。）

**工程兜底要点**：验证方式是断连压测，看线程数与队列能否回落到基线；「单元测试通过」证明不了这一点。

**Aster 挂钩**：真实场景与现状在 notes §9；本项目已做停止标记 + `stopAll()` + finally 清理，统一取消上下文仍未贯穿。

## 三、底层进阶（算法岗向，应用岗选看）

### Q4.10 Self-Attention 怎么算？为什么要多头？

**口述答案**：Q/K/V 由输入分别乘三个投影得到，注意力分数是 `softmax(QKᵀ/√d)V`；除以 `√d` 是为了防止维度大时点积方差过大把 softmax 推进饱和区。多头的作用是**让不同的子空间关注不同的关系模式**（句法、指代、位置邻近），单头只能表达一个加权分布，容易被高频模式主导；多头还带来并行计算效率。应用岗不需要手推到极致，但要能说清 KV Cache 为什么省算力（K/V 只依赖历史 token，可缓存复用）以及它对长上下文成本的直接影响。

**追问预案**：MHA/MQA/GQA 区别？（KV 头数递减：MHA 每头独立 KV，MQA 共享一组 KV（显存最省、质量略降），GQA 折中分组共享——推理服务里 GQA 最常见。）

### Q4.11 RoPE、MoE、量化各解决什么问题？

**口述答案**：**RoPE** 用旋转矩阵把相对位置注入 Q/K，使内积自然编码相对距离，外推性优于绝对位置编码，现在几乎是大模型默认方案。**MoE** 用门控把 token 路由到部分专家，参数总量大但每次只激活一小部分，从而在不成比例增加推理 FLOPs 的前提下扩容——代价是路由不均衡、专家负载不均和显存占用高。**量化**（INT8/INT4、权重量化 vs 激活量化）降低显存与带宽、提升吞吐，代价是精度损失与对某些任务（数值推理、长链）的退化。这三个是「为什么模型能跑得起、跑得快」这条线上的高频考点。

**追问预案**：怎么估算推理所需显存？（参数量 × 每参数字节 + KV Cache（层数 × 2 × 头数 × 头维 × 序列长 × batch × 字节）+ 激活；长上下文时 KV Cache 常常反超权重。）

### Q4.12 SFT、RLHF、DPO 的区别？应用岗需要会到哪一步？

**口述答案**：**SFT** 是监督微调，用「输入—期望输出」对让模型学会格式与领域行为，成本最低、最常做。**RLHF** 先训奖励模型再优化策略（PPO 类），能优化偏好但对训练稳定性、算力和奖励黑客都很敏感。**DPO** 跳过显式奖励模型，直接在偏好对上做优化，实现简单、稳定性好，是目前多数团队的默认选择；更新的 GRPO 之类则在推理类任务上省掉价值网络。应用岗的合理边界是：**会用 LoRA 做小样本领域适配、能准备合格数据集、知道什么时候该微调什么时候该用 RAG/Prompt**，不需要会调 PPO 的 KL 系数。要能一句话说清：能力问题才微调，知识问题用 RAG，格式问题优先约束解码。

**追问预案**：Agent 场景怎么用后训练？（工具调用格式错误率高、且有明确成功判据时最划算——用真实调用轨迹做 SFT，用「完成/失败」做偏好数据。）

### Q4.13 Transformer 训练里 Scaling Laws、涌现能力怎么理解？

**口述答案**：**Scaling Laws** 描述损失随参数量、数据量、算力呈幂律下降，实践意义在于「怎么把固定算力分给模型大小和数据量」（Chinchilla 结论是许多模型被训得「小而欠喂」）以及能否用小车次外推大车次。**涌现能力**指某些任务在规模跨过阈值前表现很差、跨过之后突然变好，争议点在于它部分是**评测指标不连续造成的假象**（用概率型指标衡量时曲线是平滑的）——能讲出这个争议就是加分答案。应用岗了解即可，主要用来证明「你知道自己用的模型是怎么来的」。

**追问预案**：为什么长上下文模型效果会衰减？（训练数据里长依赖监督信号稀疏 + 注意力在长序列上的分配问题，表现为「lost in the middle」，工程上仍要靠上下文精选。）

### Q4.14 推理部署要关心什么？（vLLM、连续批处理、显存）

**口述答案**：五个关注点：**吞吐 vs 时延**（continuous batching 把不同长度的请求动态组 batch，显著提升吞吐；TTFT 与 TPOT 要分开看）、**KV Cache 显存**（长上下文与大 batch 会迅速吃满显存，前缀缓存能省重复计算）、**并行策略**（张量并行/流水并行/专家并行对应不同瓶颈）、**量化与算子**（AWQ/GPTQ 降显存，FlashAttention 降注意力显存峰值）、**服务治理**（限流、超时、模型多版本灰度、失败降级）。自建还是调用 API 的判断也很实在：合规、成本、时延三者只要有一项卡住才值得自建，否则托管 API 的运维成本远低于自养推理集群。

**追问预案**：GPU 怎么选型？（先看是否需要训练，再看显存容量与带宽决定可服务的上下文长度和 batch，最后看互联与生态；只做推理时显存带宽往往比算力更决定成本。）

## 附：LeetCode 高频形态

真实面经里的算法题是**中等难度、重边界与复杂度分析**，出现过的有「合并重叠区间（LeetCode 56）」。常见形态按出现频率：双指针与滑动窗口、区间合并/覆盖、Top-K（堆或快选）、图的 BFS/DFS（依赖拓扑排序——和 Agent 任务编排直接呼应，很容易被抓来出「实现一个 DAG 调度器」）、LRU 缓存（手写，考 `LinkedHashMap` 或双向链表 + 哈希）。

准备策略：每题写完主动报**时间/空间复杂度**和**一个已知边界缺陷**，比多写一题更有效。
