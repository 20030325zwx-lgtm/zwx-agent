# Agent 岗位面经逐题回答与 Aster 项目审视

日期：2026-11-01。范围：当前工作区 yu-ai-agent 主项目，辅以 aster-infra 与 aster-mcp；静态源码审阅，没有运行计费模型、压测或故障注入。面经链接、公司、时间和题目按用户提供的材料组织，本次没有独立验证原帖真实性。以下“建议回答”是通用工程方案，不等于项目均已实现。

## 先给结论

Aster 已有 Agent Runtime 雏形和相当完整的工程模块：规划/并行 Worker/验收/汇总、工具权限、PostgreSQL 检查点与会话租约、幂等账本、混合检索与重排、MCP、独立容器沙箱和评测脚本。适合强调 Java 后端如何承接模型的不确定性。

不足主要集中在跨模块的一致性和证据：结果截断后如何再取、并发预算如何预占、恢复后如何隔离旧执行者、工具业务失败如何识别、宿主执行与沙箱如何统一，以及怎样用足够的样本证明稳定性和业务价值。不要继续堆功能来掩盖这些问题。

回答结构：先说业务目标，再说机制，接着说明失败场景和兜底，最后给验证指标；项目事实与未来方案明确分开。

## 一、字节：Coding Agent / Runtime / Harness

### 1. 为什么做 Coding Agent，与直接使用 ChatGPT 有何区别？

建议回答：Coding Agent 把代码理解、修改、执行测试和根据反馈修复组成闭环，收益是减少人工搬运上下文和执行命令的次数。核心差异不是模型名称，而是能否接入真实仓库、持久保存任务状态、执行受控工具并验证产物。ChatGPT 也可能具有工具和 Agent 能力，不能笼统说它只能聊天。简单解释代码不需要复杂 Agent；跨文件修改并验证才更适合。

项目举例：项目绑定、源码搜索、补丁、build/test、Git 工作区，加上 Planner → Workers → Verifier → Aggregator。应展示真实 diff 和测试结果，而不是只展示回答。

### 2. 模型负责什么，代码负责什么？

模型负责语义理解、候选计划、参数生成、结果解释和下一步建议；代码负责身份认证、授权、输入输出校验、状态流转、预算、超时、幂等和审计。模型可以提出执行请求，但不能自行授予权限；“模型说成功”不构成数据库提交或测试通过的证据。

### 3. Harness 包含哪些模块？

模型适配、提示词与上下文装配、工具注册与执行循环、规划调度、状态/检查点、工作区与产物存储、权限/沙箱、预算/限流、取消/恢复、日志/评测。Harness 是让模型可靠工作的外围执行环境，不是单独的提示词，也不一定需要多智能体。

### 4. Tool Calling 完整链路？

准备有权使用的工具及 JSON Schema → 发给模型 → 模型返回工具名/参数/tool_call_id → 程序校验参数与权限 → 记录调用状态 → 执行工具 → 校验业务结果并持久化 → 用对应调用 ID 回传工具结果 → 模型继续推理或结束。并行仅用于无依赖且不会产生冲突的操作。循环受步数、时间、费用和重复调用限制。

注意：流式参数未收齐前不执行；超时不必然代表远端没有执行。

### 5. 模型如何知道工具参数？

通过请求中的工具定义：名称、描述、input schema、required、类型、枚举和必要示例。Spring AI 可以从 @Tool/@ToolParam 与方法签名生成定义，MCP 客户端可以从服务端发现工具。Schema 能减少格式错误，但不能代替服务端权限、对象归属和业务校验。

### 6. 工具返回结果特别大怎么办？

完整结果写到受控产物存储，给模型返回短摘要、结果 ID、大小、格式、截断标记和可继续读取的位置。提供分页、范围读取、搜索/过滤工具，优先把筛选下推到数据源。按 token 预算控制回传内容，并限制最大结果大小及保留时间。结果 ID 必须绑定租户与运行权限，不能成为绕过鉴权的下载入口。

项目边界：目前有字符截断与账本持久化，尚不能把它描述成完整的大结果外置检索协议，详见不足 A。

### 7. 万行文件每次最多 2500 行，如何知道没读完？

使用显式分页契约，而不是让模型猜：返回 path、version/hash、start_line、end_line、has_more、next_cursor，可选 total_lines。读取 1–2500 行后 has_more=true，最后一页才为 false；不用为计算总行数每次扫描全文件。文件变化时旧游标失效或固定快照，避免前后页来自不同版本。若字符/token 上限先到，end_line 和 cursor 必须反映实际返回内容。

项目边界：readProjectFile 只有 fileName 参数和截断提示，不能按行继续读取，是明确缺口。

### 8. 多轮工具结果如何持久化？

区分三种数据：运行状态/调用状态进关系库；大结果进对象存储；模型当前需要的片段进入上下文。调用记录关联 runId、stepId、callId、工具版本、参数摘要、状态、产物引用和时间。工具结果不等于长期用户记忆。原始数据需脱敏、授权和 TTL，不能无限保存。

### 9. 上下文压缩、摘要还是丢弃？

组合使用：目标、约束、授权边界、未完成任务作为结构化状态保留；旧过程摘要；原始大结果外置按需取回；重复和可再生内容丢弃；最近关键交互原样保留。保留工具调用与响应配对，避免破坏协议。摘要必须能追溯来源；摘要失败不能直接丢掉唯一的授权或验收要求。

项目边界：已有自动摘要和配对保护，但按字符触发、摘要失败丢弃旧块，仍需防信息丢失。

### 10. 如何安全执行 Agent？

把外部网页、文件、工具输出当作不可信数据；模型不能因其中的指令提升权限。身份和权限在代码侧校验，高风险动作按精确参数确认，执行时再次校验。叠加路径隔离、出网控制、凭据最小化、资源限额、审计和取消。Prompt Injection 检测是辅助，真正边界是执行器的能力约束。

### 11. 如何设计沙箱与文件边界？

应用层做根目录、真实路径、符号链接和敏感文件校验；操作系统层用隔离容器或更强沙箱限制挂载、用户、网络、CPU、内存、进程数与时间。项目构建脚本本身可以执行任意代码，“只允许运行 npm test”不等于安全沙箱。容器共享宿主内核，有更强不可信多租户需求时考虑 gVisor/微虚拟机；不要把 Docker socket 暴露给任务容器。

项目边界：独立沙箱有真实资源限制，但本地代码构建链路仍直接启动宿主进程。

### 12. 本地迁移云端如何设计？

拆成 API/会话控制层、持久化调度层、执行 Worker、模型/工具网关、隔离工作区、PG 与对象存储。请求返回 runId，长任务异步推进；状态通过 SSE/事件订阅交付。调度使用租约、心跳、执行代次 fencing，状态转换 CAS；副作用工具使用业务幂等键和结果核对。工作区要有可恢复的存储策略，不能假设新 Worker 拥有旧主机的本地文件。

先根据负载选择 PG 任务表或消息队列，不为了“分布式”强加 Kafka/Redis。迁移验收要覆盖断线、杀进程、重复投递、租约失效、跨实例重连和取消传播。

## 二、网易/阿里/腾讯：Agent 与 Java 后端

### 网易 1. LangChain 与 LlamaIndex 分别适合什么？

LangChain 更偏模型、工具和应用组件集成，复杂状态流程可结合 LangGraph；LlamaIndex 更偏数据接入、索引和检索增强应用。两者功能存在重叠，应按生态、可观测性、维护成本和场景选型。Java 项目使用 Spring AI 是合理选择，不必为框架名字迁移技术栈。

### 网易 2. 多工具调用如何输出校验？

分传输、结构、业务三层：HTTP 成功只代表传输成功；结构按 schema 检查；业务校验状态、字段取值、对象归属与前置条件。统一返回 status/data/error/retryable/artifactRef，并验证跨工具的 ID 和版本一致性。不要让下游把“Error: …”字符串当正常数据。

### 网易 3. 如何防止无效结果？

无法保证工具永不失败，但能阻止无效结果进入下一步：类型化结果、空值/范围约束、来源和时间检查、失败分类、熔断与降级。只对明确可重试且安全的操作重试，指数退避加抖动；结果未知的写操作先查单，不盲目重放。

### 网易 4. 海量文档如何向量分片？

先确认向量规模、维度、QPS、过滤条件、内存与召回要求，再考虑分片。可按租户/知识域路由，大租户进一步散列；跨分片检索合并候选再重排。处理热点、元数据索引、文档版本、删除和重建。分片键不同于 ANN 索引参数；小数据用单实例 PGVector 更简单。

### 网易 5. 如何优化 RAG 召回速度？

逐段量化 query embedding、ANN、词法召回、融合、重排耗时及 P95；优化索引与过滤、适度并行双路召回、约束候选数和重排规模、缓存带权限及语料版本的结果。速度必须与 Recall@K/NDCG 一起评估，不能靠少检索掩盖漏召回。

### 网易手撕：最长无重复子串

滑动窗口 + 字符最后出现位置，左边界取 max(left, lastIndex + 1)，每个字符只处理一次；时间 O(n)，空间 O(字符集)。Java 需先问输入按 ASCII、UTF-16 char 还是 Unicode code point 处理。

### 阿里 1. Planning 如何实现？

模型输出结构化任务图：stepId、目标、依赖、工具能力和验收条件；程序校验 schema、DAG 无环、资源和权限。调度器按依赖推进，无依赖步骤并行；失败后局部修订，设置最大重规划次数和总预算。简单请求直接执行，避免规划成本超过任务本身。

项目已有 Planner/Workers/Verifier/Aggregator，可结合依赖执行与返工讲，但不能把 Verifier 的文本判断等同于独立事实验证。

### 阿里 2. 记忆分层？

工作记忆是当前计划、结果和上下文；情景记忆是历史任务事件与可复用案例；语义记忆是稳定事实、偏好和知识；程序性记忆是经验证的技能和流程。分别考虑租户/用户范围、来源、置信度、时效、冲突覆盖和删除。检索时只注入相关内容，避免错误事实反复固化。

### 阿里 3. CoT 有什么提升？

分步规划或中间校验有时能改善复杂任务分解和错误发现，但收益需要对照评测。工程上记录可验证的计划、动作、证据和简短决策依据，不依赖模型暴露完整内部思维链。工具真实返回与验收结果比长篇“思考过程”更可靠。

### 阿里 4. CoT 有哪些局限？

增加延迟和费用，可能合理化错误结论，早期错误会传递，长输出会污染上下文；更长推理不必然更好。用工具验证、结构化状态、简洁任务计划和预算上限约束，通过成功率/成本比较是否值得。

### 阿里 5. SFT 数据集如何构建？

围绕明确能力缺口收集脱敏且获得授权的真实任务轨迹，包含正确工具选择、参数、结果与最终交付；由规则和人工筛选纠错，覆盖失败恢复、拒绝与边界场景。去重并按用户/任务簇划分训练、验证和测试，避免同源泄漏。固定基线、离线评测再灰度。数据不够或瓶颈在工具协议时优先改工程，不为面试而训练模型。不要声称项目已做 SFT。

### 腾讯 1. 并发 Agent Session 怎么设计？

分清 session（对话）、run（一次任务）、step 和 tool call。不同会话可并行，同会话默认串行或显式分支；以 clientRequestId 去重，保存消息版本，状态进数据库。租约负责互斥，fencing 负责阻止失去租约的旧 Worker 写入；SSE 连接不能作为任务存活的唯一依据。取消、预算和权限要随 run 传播。

项目有 PG 会话租约与实例心跳，不是纯 JVM 锁；但检查点更新的旧执行者隔离仍需加强。

### 腾讯 2. MVCC 原理？

以 InnoDB 为例，隐藏事务字段、undo 版本链和 Read View 决定快照读能看到的版本。RC 通常每次一致性读新建快照，RR 通常首次一致性读建立事务快照；当前读如 SELECT FOR UPDATE/UPDATE 走锁语义。MVCC 减少读写冲突，不保证“所有读取不加锁”。项目使用 PG，面试时不要把 InnoDB 的具体实现直接套给 PG。

### 腾讯 3. 行锁与表锁？

行锁提高并发但增加锁管理与死锁复杂度，表锁简单但影响面大。InnoDB 主要通过索引记录加锁；隔离级别、索引与范围条件影响记录锁/间隙锁/next-key lock。无合适索引可能锁大量记录，不能一概说“自动升级表锁”。固定更新顺序、短事务、索引优化与可重试死锁处理是常用手段。

### 腾讯 4. 线程池参数如何设计？

先区分 CPU 与阻塞 I/O，再按任务耗时、到达率、下游并发上限和延迟目标压测。解释 core/max/队列/keepAlive/拒绝策略，采用有界队列与明确背压。模型调用通常受供应商限流约束，不能靠无限线程提高吞吐；虚拟线程也不消除连接池、Token 和内存限制。监控排队时间、活跃数与拒绝数。

### 腾讯 5. OOM 如何排查？

先看错误类型：堆、元空间、直接内存、线程数，还是容器被系统杀死。结合 GC 日志、容器 RSS/限制、jcmd、堆转储和 MAT 的 retained size/引用链定位。Agent 常见风险是无界历史、完整工具结果、事件缓存、积压任务和文件字节数组。修复生命周期或背压后再调堆大小；dump 可能暂停进程且含敏感数据。

### 腾讯 6. Linux CPU 高如何定位？

先区分应用计算、系统调用、I/O wait 与容器 CPU throttling；用 top/pidstat 找进程和线程，再将线程 ID 转十六进制匹配 jstack，重复采样确定热点。必要时用 JFR/async-profiler/perf。检查忙轮询、正则、大 JSON、GC 和过密调度。单次线程栈不足以证明根因。

### 阿里手撕：合并区间

按左端点排序，遍历与最后区间比较，重叠则扩展右端点，否则新增；O(n log n) 时间。确认闭区间下端点相等是否合并，处理空集、包含与负数；比较器避免减法溢出。

## 三、亚信安全：RAG、恢复、限流和预算

### 1. RAG 整体架构？

离线：解析/OCR → 清洗 → 带结构切片 → 元数据与权限 → embedding/索引 → 版本发布。在线：查询分析 → 权限过滤 → 向量/词法召回 → 融合去重 → 重排 → 有限证据上下文 → 带引用生成 → 引用及质量检查。无证据时明确拒答或转人工，不强行生成。

项目已有向量+词法召回、RRF、重排和检索轨迹，不能再用“只有向量检索”评价现状。

### 2. 如何构建 RAG 评测集？

从真实查询采样，按简单事实、多文档、时效、否定、无答案、权限隔离、噪声/OCR、提示注入分层；标注问题、相关证据片段、可接受答案和拒答条件。按文档/任务来源隔离开发与测试集，保留版本。合成数据补边界，但不能全靠模型同时出题、答题和打分。

### 3. 如何评价 Agent 回答质量？

分检索、回答和任务执行：Recall@K/MRR/NDCG；事实正确、引用支撑、完整性和拒答；真实任务成功、工具合法性、副作用正确、人工介入率。附带 P50/P95 延迟、每成功任务费用。规则/业务断言优先，模型裁判须经人工校准；同一模型自评不是充分证据。

### 4. 一个 Case 执行几次？

没有固定正确次数。确定性规则可单次回归；随机 Agent 的开发评测可先每例 3–5 次估计波动，再按目标置信区间与风险增加样本。模型版本、参数、工具环境和语料版本固定并记录。报告一次执行成功率和稳定成功情况，不能把“多次里至少成功一次”当上线成功率。增加同一题重复次数也不能替代场景覆盖。

### 5. 端到端延迟如何控制？

先分解排队、路由、检索、模型首 token、生成、工具、重试和验收，统计尾延迟。简单任务短路、无依赖操作并行、候选/工具数量约束、结果缓存和快速模型分工；设置端到端 deadline 并传播给子任务。流式改善感知，不代表总耗时下降；质量底线不应被超时优化破坏。

### 6. 长任务如何断点续传？

持久化任务图、当前状态、已完成步骤、调用账本、产物引用、模型/工具版本及审批状态。恢复时从已提交的安全边界继续，不能只重放 UI 事件。检查点粒度决定可重算范围；不确定副作用先核对，不能把“重跑节点”称为无重复恢复。

项目已有数据库 checkpoint 和恢复入口，可讲清保存了什么、哪些 Worker 会重新执行。

### 7. 第三方接口失败如何恢复？

区分：执行前明确拒绝、确定失败、可重试临时故障、请求已发但结果未知。只读请求可有限重试；写请求带业务幂等键，超时后按外部操作 ID 查询，无法查询则进入 UNKNOWN/RECONCILING 等人工或异步核对。只有需要且有业务定义时才补偿，不能把“反向操作”当通用回滚。

### 8. Redis 实现模型限流？

按供应商/模型/租户/用户建立 RPM、TPM 和并发限制。Lua 原子完成令牌桶补充与扣减，或用滑动窗口；配置 TTL，拒绝时返回 retryAfter。并发许可要有租约与请求唯一标识。Redis Cluster 中同脚本涉及的键需同槽，或者设计分层额度；跨槽多级限流并非天然原子。Redis 故障时明确拒绝还是保守降级策略。

### 9. Redis 控制 Token 额度？

调用前预占输入 token 估算 + 最大输出预算，设置模型输出上限；完成后按真实 usage 结算并退回余额。记录 reservationId、账户、请求状态、额度、过期和结算标识。Redis 可做快速原子预占，账务必须有可靠持久账本和对账。TPM 限流是速率问题，累计费用预算是账务问题，应分开。

### 10. 并发消耗如何防超额？

原子判断 available >= reservation 并扣减，不能先查余额再扣。结算必须幂等，重复响应不重复扣费；请求结果未知不能直接退全额，需保留预占并对账。重试同一逻辑调用复用 reservation，但实际新增供应商请求可能再次收费，应纳入账务。也可以用 PG 条件更新实现强一致预占，并非一定要 Redis。

### 11. 生成中预算耗尽，继续还是中断？

区分硬预算和软预算。硬预算应在调用前限制可用输出、必要时拒绝，避免靠输出中途计数兜底；运行中达到阈值则取消后续调用，并尝试取消当前请求。断开客户端流不保证供应商停止计算或计费，要保留未结算额度和误差缓冲。软预算可预留完成当前答复的余量，但不能自动开始下一步任务。

当前项目应诚实描述为“运行准入配额与用量统计”，尚不是强一致的并发模型预算系统。

## 四、九号公司：工具平台与业务闭环

### 1. LangGraph 每个节点的输入输出？

通常输入是共享 state 和运行配置，输出是部分状态更新或 Command；reducer 决定并行更新的合并方式。边决定下一节点，条件边依据状态路由，checkpoint 保存可恢复状态。节点边界要声明 schema、读写字段、副作用和重试策略。项目使用 Spring AI Alibaba 图编排与自己的工作流，不能自称用 Python LangGraph 实现。

### 2. Agent 自动建单怎么做？

理解诉求 → 查询已有信息 → 提取结构化草稿 → 校验必填字段/枚举/对象归属 → 缺失项追问 → 必要确认 → 带幂等键提交业务 API → 记录单号并查询状态 → 通知或交付。模型生成草稿，业务服务决定能否落单；不能让模型自由拼 SQL 直接入库。

### 3. 怎样保证 90% 以上准确率？

先定义分母和验收：字段准确率、整单正确率还是自动完成率，是否包含拒绝/转人工。建立代表性留出集，结合规则校验、检索约束、受控枚举、人工复核和置信度校准迭代。用样本量、置信区间和线上数据证明，不能承诺换模型或写提示词就保证 90%。自动完成率与自动建单正确率应同时报告，防止通过全部转人工刷准确率。

### 4. 剩余 10% 如何处理？

按原因分流：缺信息追问，低置信转人工，业务校验失败解释并补正，已创建但状态未知查单，明确错误走有审批的撤销/更正。保存原始输入、草稿、校验失败和最终人工修订作为回归案例。高损失错误可要求所有提交前确认，而非接受一个平均正确率。

### 5. 工具注册中心怎么设计？

保存工具唯一标识、版本、描述、输入输出 schema、风险、权限、超时、并发、幂等语义和执行地址。注册时做 schema/连通性验证，调用时按身份过滤；运行冻结工具版本，审计可追溯。凭据在执行侧注入，不能给模型。注册中心解决发现与治理，不只是 Map<名称, 函数>。

### 6. 三层抽象是什么？

“三层”没有行业统一答案，可明确提出自己的划分：定义层描述契约和治理信息；绑定层把本地方法/HTTP/MCP 适配为统一执行接口；运行层做鉴权、校验、预算、超时、幂等、审计与标准化结果。这样接入新协议不需要改 Agent 循环。若面试官指特定公司的三层，应先确认其术语。

### 7. 如何动态加载工具？

配置变更 → 发现工具/schema → 校验和授权 → 发布新目录快照 → 新 run 使用新版本；旧 run 保留原快照直到结束。工具移除、重名、连接失败和权限撤销需要明确策略；权限紧急撤销执行时仍应生效。MCP 动态发现不等于任意热加载 JAR，后者需类加载隔离和更强安全治理。

项目已有 MCP 配置与运行时发现，但不能据此声称已具备完整的版本化工具治理。

### 8. 如何证明提高业务效率？

做同类任务的人工基线或对照实验，比较从请求到验收的时间、人工操作分钟数、首次正确率、返工率、自动完成率和单次成功成本。记录任务难度与参与者差异，避免只展示最好样例。Token 量、工具次数、回答速度不是独立的业务收益证明。

### 9. OCR 失败怎么办？

先区分文件打不开、页面扫描差、版面/表格解析失败和关键字段识别错。可做旋转/去噪/重渲染、替代解析器、针对疑难页二次识别；关键金额/日期做规则和来源核对，保留页码/坐标与原图。仍不可靠则请求清晰原件或人工复核，不能让模型补造缺失值。

### 10. 完整业务闭环是什么？

输入 → 理解/草稿 → 校验/确认 → 真实执行 → 状态查询与异常恢复 → 可验收产物 → 用户接受/修订 → 指标与回归案例。项目可选一个聚焦场景：代码修复并通过测试，或参考图生成海报并归档验收。不要把“工具返回 200、模型说完成”当作闭环终点。

## 五、当前项目不足：源码证据与整改验收

以下是静态审阅发现，风险推演不等于已经在运行环境复现的事故。路径相对于 yu-ai-agent；基础设施路径额外注明。

### A. 大结果和文件读取只有截断，缺少可恢复读取协议（P1）

证据：capability/tools/ProjectCodeReadTool.java 的 readProjectFile 只收 fileName，最多读 100000 字节后提示 truncated，没有 offset/line/cursor。agent/hook/ToolResultTruncationHook.java 默认将结果压到 8000 字符，采用首 70%/尾 30%。两层限制可能让文件中段不可见。

agent/execution/AgentToolCallLedgerService.java 结果最多保存 200000 字符；ExecutionTraceHook 的 afterToolCalls 实际记录工具名和参数/结果长度，不能因截断 Hook 的注释就断言完整结果已由轨迹保存。

改进：统一 ToolResult 元信息、受控 artifactRef、按行/游标读取与结果搜索；文件版本绑定。验收：超过 10000 行且中间放目标字段，Agent 能定位并取回；超过模型单次预算的结果不丢关键证据；跨租户读取拒绝。

### B. 配额检查不是并发预算预占（P1）

证据：agent/execution/RunQuotaService.java 的 checkRunAllowed 先 COUNT 活跃任务、再 SUM 历史 token，返回通过或 429；web/controller/ManusAgentController.java 在会话锁之前调用。不同会话可同时读到同样余额或并发数，随后都通过。此路径没有把准入和额度占用做成同一原子操作。

改进：用户/租户级原子许可；每次模型请求预占+结算+未知费用对账，统一覆盖 Worker、Verifier、摘要等调用；token 与实际货币成本分开计量。可先用现有 PG 实现，再按吞吐选择 Redis。

验收：并发抢最后一份额度只有一个成功；重复结算、重试、崩溃和超时退款均不导致负余额或重复扣费。超长 run 不能只在入口检查一次。

### C. 幂等账本把“相同参数”与“同一次业务操作”混在一起（P1）

证据：AgentToolCallLedgerService.begin 的键是 runId + toolName + 原始参数字符串的 SHA-256；IdempotentToolCallback.wrapAll 对工具统一包装。

问题：修改文件后同参数读取可能回放旧内容；修复代码后同参数测试可能回放旧结果。反之，JSON 键顺序变化会生成不同哈希，语义相同的写操作可能绕过去重。同参并发时 readExisting 将 PENDING 转 UNKNOWN，无法区分仍在合法执行和上次崩溃；原调用随后 succeed 的 WHERE status='PENDING' 也可能不再生效。

改进：只读工具默认可重新执行或按资源版本缓存；写操作使用稳定的 logicalOperationId/业务幂等键；参数规范化仅作辅助。PENDING 由调用租约/外部状态决定，UNKNOWN 有核对流程。

验收：读→修改→再读拿到新内容；失败测试→修复→再测真正执行；同参在途请求不误标未知；成功写入后的恢复不会重复创建。

### D. 工具正常返回不等于业务成功（P1）

证据：IdempotentToolCallback.execute 在 delegate.call 正常返回时直接 ledger.succeed；部分工具用 Error 字符串或非零退出码文本表达失败，而不抛异常。因此账本 SUCCEEDED 更像“Java 调用返回”，不保证工具业务成功。

改进：引入类型化工具结果，明确传输成功、业务成功、可重试失败和结果未知。业务失败不得被成功缓存；保留错误码、退出码与证据。

验收：进程退出码非零、空解析结果、HTTP 200 内业务失败都阻断下游并正确记录。

### E. 有分布式租约，但 Agent 写入缺少执行代次校验（P1，需故障注入确认影响）

证据：chat/conversation/ConversationLockManager.java 使用 PG 租约与 owner_token，ApplicationInstanceRegistry 有心跳。租约续期更新 0 行时关闭租约，但这段实现未直接取消执行中的模型/工具。agent/execution/AgentRunService.checkpoint 和 updatePartialAnswer 按 runId/status 更新，没有执行 epoch 条件。

风险：暂停/网络分区后旧执行者恢复，新旧执行者可能先后写入同一 RUNNING run。拥有租约机制不等于所有持久化写入都已受 fencing 保护。

改进：在 claim 时生成单调 epoch，贯穿 checkpoint、终态、工具调度、取消与审批；失去所有权主动停止。creative/repository/MediaJobRepository.java 已有 version + lease_epoch 条件更新，可作为项目内参考，但不能把创作模块保障直接算到 Agent 上。

验收：暂停旧实例→租约转移→新实例推进→旧实例恢复，旧 checkpoint、终态和工具动作全部被拒绝。

### F. 独立沙箱存在，但宿主构建链路未统一隔离（P1，云端开放不可信仓库前优先）

证据：../aster-infra/src/main/java/com/zwx/asterinfra/sandbox/SandboxService.java 确有 network none、memory、CPU、pids、read-only 和 no-new-privileges。主项目 ProjectTaskTool.execute 仍直接 ProcessBuilder 执行项目脚本；TerminalOperationTool 也在宿主启动 shell。ToolFactory 直接装配这些工具。

结论：不能说“没有沙箱”，也不能说“所有命令都在 Docker 沙箱”。本机可信项目配合显式批准和托管云端不可信项目是不同安全场景。

另一个需验证的问题：TerminalOperationTool 先同步 readLine，再 waitFor(timeout)，若进程不关闭输出流，可能尚未到 waitFor 就一直阻塞，名义 30 秒超时不覆盖整个执行过程。

改进：云端代码任务进入隔离执行器，单独控制出网、挂载和凭据；输出异步采集，墙钟 deadline 独立生效，超时清理子进程树。验收覆盖恶意构建脚本、静默挂起、fork 子进程、超大输出和出网。

### G. 上下文摘要可能丢失关键任务状态（P2）

证据：MemoryCompressionHook 默认按 24000 字符触发，保留最近 6 条；摘要输入受 MAX_BLOCK_CHARS=12000 限制，摘要失败后清空旧块。它有工具配对保护，这是已有优点；但摘要输入限制与整块清除结合，可能漏掉没送入摘要的旧内容。

改进：目标/授权/验收/未完成项独立结构化保存；摘要保留来源；按模型上下文预算预留输出和工具空间；失败时用确定性保留关键字段或降级方案。

验收：长任务压缩前后约束保持，摘要服务不可用时仍不越权、不忘未完成事项。

### H. 有评测，但不足以证明稳定性与业务收益（P2）

证据：evaluation/eval-sets/README.md 记录 12 条意图、15 条 RAG 和三条任务端到端冒烟；历史 RAG 15/15 是小样本检索结果。RAG 基线路径使用 verify-retrieval 接口，不能直接代替完整回答质量或全部混合检索链路评测。真实任务评测不进 CI，意图门禁无密钥时跳过。

改进：版本化留出集覆盖无答案、跨文档、权限、噪声、故障恢复和副作用；真实调用做定期评测，确定性断言进 CI。报告样本数/重复次数、成功率区间、P95、每成功任务成本与人工用时。

验收：固定模型/数据/参数，提供基线与改造后对照；不能用 15/15 宣称生产准确率 100%，也不能因已有测试类就宣称本次测试通过。

### I. 工具动态发现已有，治理仍可深化（P2）

证据：capability/mcp/McpServerConfigurationService.toolsFor 连接已配置服务，通过 SyncMcpToolCallbackProvider 获取工具，支持 allowlist；McpToolRegistry 维护租户工具名集合。

建议补齐：工具版本快照、名称冲突处理、输出 schema/业务状态、重试幂等声明、依赖健康与熔断、精细凭据范围。是否已有其它路径覆盖这些能力需逐项核验，不能仅从注册表类推断整个项目完全没有。

## 六、推荐补强顺序与面试口径

1. 先修工具结果协议与文件续读，串起“完整结果保存—按需取回—模型预算”；同时修业务成功判定与幂等语义。价值最直接，能回答字节 6–9 题和网易工具校验。
2. 把模型费用变成可验证的原子预占/结算，并统一模型调用入口。用并发测试证明，不必先引入新中间件。
3. 强化 Agent 执行 epoch、断点恢复和取消；云端不可信执行必须先统一沙箱边界。这些是分布式和安全追问的主线。
4. 做一个完整业务场景的基线、回归与人工效率对照。优先证明一条链路可靠，再扩展功能。

推荐项目介绍：

> 我做的是基于 Java/Spring AI 的长任务 Agent 工作区。模型负责规划和工具选择，运行时负责权限、状态、持久化和恢复。当前已经有规划执行验收链路、PG 检查点/会话租约、工具账本、混合检索和独立沙箱。工程上最值得讲的是副作用工具的结果未知处理，以及为什么检查点、幂等和租约必须协同。当前我也明确知道边界：大结果续读、预算预占、部分执行链路的 fencing 和统一沙箱仍需要补齐；已有小样本评测，但还不能声称生产级准确率或大规模稳定性。

未实际完成的改进只能说“下一步方案”；未重新运行的历史测试只能说“仓库记录”，不能当作本次验证结果。
